# 04 — The Lua↔Java boundary across OC Lua 5.2/5.3/5.4, LuaJ and OC-LuaJIT

Research date: 2026-10-08. Sources are the local checkouts (GTNewHorizons/OpenComputers @ f83bd95 2026-07-29 = tag 1.12.55-GTNH; installed jar 1.12.64-GTNH; MightyPirates/OC-JNLua @ da3d4d4; mindbound/OC-LuaJIT @ a4994e6; ocelot-brain @ e98a5b2) plus the installed config `C:\Games\Minecraft\instances\Main\minecraft\config\OpenComputers.cfg`. Paths below are relative to those checkouts. "Verified" = read in source; "inference" = derived, confidence stated. Version coverage: the GitHub compare `1.12.55-GTNH...1.12.64-GTNH` lists 29 changed files (drop-file/PacketHandler work, AE2/GregTech drivers, `ColorUtils`, `ExtendedNBT`, `application.conf` incl. `maxSignalQueueSize` 1024 and drop-file limits, `Settings.scala` drop-file settings only); none of `Machine.scala`, `machine.lua`, `GraphicsCard.scala`, `ExtendedLuaState.scala`, `ArgumentsImpl.scala`, `NativeLuaArchitecture.scala`, `UserdataAPI.scala` or `LuaStateFactory.scala` changed, so every boundary/limit finding below holds for the installed 1.12.64 jar.

## Summary

1. Lua strings cross to Java as raw `byte[]` (no charset conversion); `Arguments.checkByteArray` returns that array as-is, `checkString` UTF-8-decodes it. Java `String` results go back through JNI *modified* UTF-8; `byte[]` results are pushed raw. Binary payloads must be `byte[]` both ways.
2. Lua tables passed as arguments are not copied on native runtimes: they arrive as a lazy JNLua `AbstractTableMap` proxy that costs 5–7 JNI calls per element `get` (~10 per element when iterating) and should not be retained past the callback: a retained proxy pins the Lua table inside the RAM cap until the JVM phantom-collects it and throws `IllegalStateException` once the state is closed. String elements nested in tables come back as `String` or `byte[]` depending on whether the bytes round-trip as UTF-8. On LuaJ tables are eagerly deep-copied into immutable Scala maps whose numbers are `Double` and whose string keys/values are `byte[]` slices. Measured (11 §2.3): the registry reference is held until the JVM's next GC even when the proxy is *not* retained — 100 000 table-argument calls drained a 2 MB machine to 58 KB free under an idle 1 GB heap — so tables must stay out of any per-frame path.
3. Numbers: on Lua 5.3/5.4 integers arrive as `Long`, floats as `Double`; on 5.2, LuaJ and OC-LuaJIT every number arrives as `Double`. Java `Integer/Long` results become integer-subtype values on 5.3/5.4 and doubles elsewhere (exact to 2^53).
4. A direct call costs `1/limit` of a per-tick budget (defaults 0.5/1.0/1.5 by tier; this instance: 1/2/4). Default `limit` makes the cost ~0, so throttling only exists where the callback charges `context.consumeCallBudget` itself (OC's GPU: `set` = 1/64…1/256 → 640…20,480 `set`/s). Exceeding the budget silently re-issues the call as a synchronized call on the next server tick (+12 ms `executionDelay`).
5. The raw per-call floor is measured (11 §2): 4.2–4.5 µs empty / 5–9 µs with scalar args on OC's Lua 5.2/5.3/5.4 (≈ 225 000–240 000 empty calls/s), 1.5–1.6 µs on OC-LuaJIT; per-pixel calls are infeasible for any real framebuffer. Batched byte-string command buffers are mandatory; packing costs ~0.1–0.3 µs per value on PUC, ~5× less on LuaJIT with JIT-friendly code.
6. There is no Java-side watchdog in GTNH OC or upstream. The 5 s timeout is a Lua count hook; a blocking direct callback stalls one of 4 worker threads forever, a blocking synchronous callback stalls the server tick.
7. Results pushed to Lua are allocated inside the computer's RAM cap (JNLua counting allocator); a 1 MB read-back on a 1 MB machine fails; `NativeLuaArchitecture.invoke` first converts the failure to `(true, nil, "not enough memory")` in both direct and synchronized calls, and a synchronized call crashes the machine only if that fallback push (or a later Lua allocation inside the closure) also fails. Keep pixels on the Java side.
8. `Value` userdata are optional (a config can disable them → results become nil), cost an O(live-proxies) linear scan per push, and `dispose()` never fires on OC-LuaJIT or LuaJ. Use integer handles with explicit free plus reset on `computer.stopped/started`.
9. LuaJ is a reachable fallback (`registerLuaJArchitecture=true` here) with no persistence, no memory accounting, no `__gc`; support it at "correctness only" level — a 5.2-syntax, string-based protocol covers it for free.
10. The portable encoder is: `string.pack` on 5.3/5.4, arithmetic + fixed-arity `string.char` elsewhere; no bitwise operators, no `//`, no `bit32` in hot loops (sound but unmeasured on LuaJIT), fixed-point by default, float32 via `math.frexp` only where unavoidable.
11. OC-LuaJIT persists the whole LuaJIT state including suspended coroutines; `Value`s round-trip through the same `userdata.save/load` NBT recipe as stock. Component-held state (framebuffers, handles, queues) must be persisted or invalidated by the component itself — OC's GPU persists its VRAM in its own NBT.

## Findings

### 1. Value marshalling across the boundary (JNLua / NativeLuaArchitecture)

**Lua → Java (arguments).** `component.invoke` is `ComponentAPI.scala:74-80`: address and method via `lua.checkString`, remaining args via `ExtendedLuaState.toSimpleJavaObjects(3)` → `toSimpleJavaObject` (`ExtendedLuaState.scala:106-113`):

- `BOOLEAN` → `java.lang.Boolean`; `NUMBER` → `Long` if `lua.isInteger(index)` else `Double`; `STRING` → `lua.toByteArray(index)` (raw bytes); `TABLE` → `lua.toJavaObject(index, classOf[java.util.Map])`; `USERDATA` → `lua.toJavaObjectRaw`; anything else → `null`.
- `isInteger` is `false` in the base `LuaState` (OC-JNLua `LuaState.java:921-923`, used for 5.2) and only overridden for 5.3/5.4 with `lua_isinteger` (`LuaStateFiveThree.java:56-59`). OC-LuaJIT's generated `LuaStateLuaJIT` overrides only the memory-accounting methods (`native/jnlua/gen-luastate-subclass.py:177-190`), so on 5.2, LuaJIT and LuaJ every number reaches Java as `Double`.
- Strings: `lua_tobytearray` does `lua_tolstring` + `NewByteArray` + one copy (`native/src/jnlua.c:918-960`); no charset step. `ArgumentsImpl.checkByteArray` returns the array unchanged (`ArgumentsImpl.scala:179-186`); `checkString` does `new String(bytes, UTF_8)` (`:165-172`, malformed input → U+FFFD). The component may retain the `byte[]` (it is not aliased by Lua).
- Tables: `DefaultConverter.convertLuaValue` returns an `AbstractTableMap` wrapping a registry reference (`DefaultConverter.java:371-386`). Every `get`/iteration step re-pushes the table and walks with `lua_next` (`util/AbstractTableMap.java:276-320`; `size()` is `lua_next` over the whole table when filtered, `:210-228`); one `get()` is 5–7 synchronized JNI calls (`pushValue`, `pushJavaObject`, `getTable`, `type` plus the typed read, `pop`; `:63-77`), and entry iteration re-walks with `lua_next` on both `hasNext()` and `next()` and then runs a full `get()` for `Entry.getValue()` (`:351-353`), i.e. roughly 10 per element. Keys and values are converted through `toJavaObject(Object.class)`: a string element becomes `java.lang.String` when its bytes round-trip as UTF-8 and `byte[]` otherwise (`DefaultConverter.java:361-367`), so — unlike top-level arguments, which are always `byte[]` — binary strings nested in tables are type-unstable. The registry ref is released only when the proxy is phantom-collected by the JVM (`LuaState.java:2341-2345`, `:2436-2452`). Consequences: O(n) JNI per element; a `Map` kept after the callback returns pins the Lua table inside the RAM cap until collection, blocks on the `LuaState` monitor (held by the worker during resume) on every access, and throws `IllegalStateException("Lua state is closed")` once the state is closed (`check()`, `:2436-2452`). There is no depth or size limit beyond the Lua RAM cap. Before the JNI call, machine.lua also walks every argument table recursively (`unwrapUserdata`, `machine.lua:1084`, `:1186-1202`). Measured consequence (11 §2.3): because the `luaL_ref` slot is released only when `LuaState.check()` drains the phantom-reference queue after a JVM GC, every table argument — retained or not — holds a registry entry against the machine's RAM cap until the next collection; 100 000 calls passing the same 1000-entry table drained a 2048 KB machine from ~1.9 MB free to 58–61 KB (5.2), 285 KB (5.3) and 236 KB (5.4) under an idle 1 GB heap, while a 48 MB heap (frequent young GCs) kept it at 1.87 MB; the kernel's own `collectgarbage` cannot free a reference held by Java, and the same shaded OC-JNLua 20230530.0 is in the installed 1.12.64-GTNH jar. This strengthens the rule above: copy proxies out immediately, never retain them, and keep tables out of per-frame calls altogether (byte strings only).
- `ArgumentsImpl.checkInteger/checkLong` accept any `Number` and clamp (no error) (`:60-112`, `:119-158`); `checkTable` accepts `java.util.Map` or Scala maps (`:193-201`); `toArray` converts `byte[]` to `String` (`:303-306`) — never use it for binary data.

**Java → Lua (results, signals).** `ExtendedLuaState.pushValue` (`:27-69`): `null/Unit` → nil; `Boolean`; `Byte/Short/Integer/Long` → `pushInteger`; `Float/Double` → `pushNumber`; `String` → `pushString`; `Array[Byte]` → `pushByteArray`; any other array/`Seq`/`Product` → a list table built element by element (`pushList :71-84`); `Map` → table (`pushTable :86-104`); `Value` → `pushJavaObjectRaw` only if `Settings.get.allowUserdata` (`:52`), otherwise it falls to the default branch and becomes **nil with a log warning** (`:58-60`). A fresh `IdentityHashMap` is allocated per top-level `pushValue` call, and `Registry.convert` allocates another per result array (`Registry.scala:165`).

- `pushInteger(long)` (`LuaState.java:769-778`): with a 64-bit `lua_Integer` it calls `lua_pushinteger`; on 5.2/LuaJIT that is stored as a double (exact only to 2^53); on 5.3/5.4 it is a true 64-bit integer. A `Double` 3.0 prints as `3.0` on 5.3+ and `3` elsewhere — return handles/ids as `Integer`/`Long`, never as `Double`.
- `pushString` uses `GetStringUTFChars`/`GetStringUTFLength` (`jnlua.c:713-717`, `:1909-1921`): JNI *modified* UTF-8 (NUL → `C0 80`, supplementary characters as 3+3-byte surrogate pairs). `pushByteArray` copies raw bytes (`jnlua.c:627-641`). Binary results must be `byte[]`.
- Every pushed value is allocated by the state's counting allocator (`jnlua.c:251-289`), i.e. inside the computer's RAM (see §3).

**Value userdata.** `li.cil.oc.api.machine.Value extends Persistable` with `apply/unapply/call/dispose` (`api/machine/Value.java:170-224`); `@Callback` methods on the Value class are exposed too and go through `Machine.invoke(value, …)` with the same direct/limit rules (`Machine.scala:404-414`; `luac/UserdataAPI.scala:100-105`). On the Lua side the raw JNLua userdata is hidden behind a table proxy (`machine.lua:1114-1148`): `__index` → `apply`, `__newindex` → `unapply`, `__call` → `call`, `__gc` → `userdata.dispose` (bound at `luac/UserdataAPI.scala:84-88`), `__metatable = "userdata"`, plus one callable sub-table per method. Costs: every push runs `wrapSingleUserdata`, which linearly scans **all** live proxies comparing raw userdata (`:1166-1177`), then `spcall(userdata.methods)` (reflection cache) and allocates per-method tables; every result array is walked recursively by `wrapUserdata` (`:1186-1202`). Persistence: the proxy carries a `persistKey` recipe that calls `userdata.save` → class name + gzip NBT bytes, and on load `Class.forName(name).newInstance()` + `load(nbt)` (`machine.lua:1134-1142`; `luac/UserdataAPI.scala:22-55`). A Value therefore needs a public no-arg constructor and must re-resolve its host object from NBT. Per runtime: native 5.2/5.3/5.4 — full support (if `allowUserdata`); LuaJ — pushed via `LuaValue.userdataOf` (`ScalaClosure.scala:49`), methods work and a `userdata.dispose` binding exists (`luaj/UserdataAPI.scala:38-41`), but LuaJ has no finalizers, so the proxy's `__gc` never runs, `dispose` is never reached and nothing persists; OC-LuaJIT — proxies and persistence work (shell-fill recipe, `native/kernel/patch-machine-lua.lua` "THE THIRD CHANGE"), but LuaJIT never finalizes tables, so `Value.dispose` is unreachable today (`docs/research/gc-dispose-leak.md`; fix is an open roadmap item, `docs/roadmap.md:198`).

### 2. The call path and its costs

**Path.** `machine.lua` `libcomponent.invoke` (`:1304-1308`) → `isDirect` (string concat `address..":"..method` + weak cache, `:1232-1250`) → `invoke(target, direct, …)` (`:1080-1103`). Direct: `table.pack` → `unwrapUserdata` → `component.invoke` (JNI) → `Machine.invoke` (`Machine.scala:385-402`): node lookup, `component.annotation(method)`, `consumeCallBudget(1.0 / annotation.limit)` if direct (`:390-392`), then `Component.invoke` → `Callbacks` map → ASM-generated wrapper (`CallbackWrapper.scala`) → your `@Callback` → `Registry.convert` → `NativeLuaArchitecture.invoke` pushes `true, results…` (`NativeLuaArchitecture.scala:59-69`) → `wrapUserdata` → `table.unpack`. Exceptions map to `(false, msg)` for `IllegalArgumentException` and to `(true, nil, msg)` for everything else (`:70-129`).

**Budget.** `callBudget` is reset to `maxCallBudget` every server tick in `Machine.update` (`:532`), also while the worker thread is running (it is `@volatile`, `:80`). `maxCallBudget` is the *mean* of `getCallBudget` over all `CallBudget` drivers in the computer — both CPU and every RAM stick implement it, keyed by item tier (`:123-126`; `DriverCPU.scala:69`; `DriverMemory.scala:40`). Values: upstream/GTNH defaults `[0.5, 1.0, 1.5]` (`application.conf:162-166`, `Settings.scala:71-77`); **this instance: `[1, 2, 4]`** (`OpenComputers.cfg:143-147`). `consumeCallBudget` throws `LimitReachedException` when `cost > callBudget` and is a no-op inside synchronized calls (`:286-294`). Default `limit = Integer.MAX_VALUE` (`api/machine/Callback.java:88`) → cost 4.7e-10 per call, i.e. unthrottled unless the callback charges itself.

**What happens on exhaustion.** `NativeLuaArchitecture.invoke` returns 0 results for `LimitReachedException` (`:76-77`); machine.lua treats `result.n == 0` as "limit reached" and re-issues the call via `coroutine.yield(function() … end)` (`:1087-1103`), which `runThreaded` reports as `ExecutionResult.SynchronizedCall` (`:245-247`). The server thread executes it in the next `Machine.update` (`:597-631`) and reschedules the worker after `executionDelay` = 12 ms (`:966-969`; `application.conf:207`). So the (N+1)-th over-budget call costs "rest of tick + 12 ms" and runs on the server thread with budget checks disabled. Any sleep/`pullSignal(0)` yield also pays the 12 ms (`Sleep(0)` → `Yielded` → scheduled with `executionDelay`, `:1007-1016`), so a frame loop that yields per frame is capped around 60–80 iterations/s by scheduling alone.

**OC's own GPU.** Costs per tier: `set` 1/64, 1/128, 1/256; `copy` 1/16…1/64; `fill` 1/32…1/128; `setBackground/Foreground` 1/32…1/128 (`GraphicsCard.scala:64-69`), charged via `context.consumeCallBudget` only when drawing to the screen (index 0), not to VRAM pages (`resolveInvokeCosts :100-106`, `:481-531`; `setBackground/setForeground/setPaletteColor` guard the charge with `bufferIndex == RESERVED_SCREEN_INDEX` themselves, `:309-311`, `:333-335`, `:362-364`). `bitblt` cost scales with dirty area and uses a two-phase "throw once, then execute" trick so a single call can exceed the budget (`:197-253`). Resulting `gpu.set` rates: T1+T1 defaults 32/tick = 640/s; T3 defaults 384/tick = 7,680/s; T3 in this instance 1,024/tick = 20,480/s. Buffers are dropped on `computer.stopped`/`computer.started` (`:538-545`) and VRAM contents are persisted in the component's own NBT (`:618-673`).

**Raw per-call floor (estimate; since measured by 11 §2: 4.2–4.5 µs empty and 5–9 µs with two integer arguments and one result on OC's Lua 5.2/5.3/5.4, 1.5–1.6 µs / 1.8–2.4 µs on OC-LuaJIT, identical on JDK 8 and 17).** The Lua-side wrapper is ~8 function layers, four `table.pack/unpack`, two recursive walks and a string concat; OC-LuaJIT's trampoline benchmark measures a pcall+vararg pair at 120 ns on PUC 5.3 (`bench/trampoline.lua` ITER=2·10^7, 2.39 s in `bench/results-2026-09-01.md`), so the wrapper is ~1.5–3 µs. The JNI side is 10–15 crossings (two `checkString` each allocating a `byte[]` + `String`, one or two calls per argument, one per result with an `IdentityHashMap`) ≈ 1.5–3 µs, plus ~0.5–1 µs of Scala lookups/allocations. Estimate 4–8 µs per direct call with scalar args → ceiling ~1–2·10^5 calls/s per computer — confirmed by 11 §2 (225 000–240 000 empty and 110 000–195 000 scalar calls/s on PUC); "tens of thousands in practice" holds only for 100 KB payloads (20 000–45 000/s). Measured in ocelot-brain (same `Machine`/budget code: `ocelot-brain Settings.scala:23-45`, defaults `application.conf:162-166`; 19 §1 confirms the budget machine is identical to GTNH's).

**Break-even for a pixel API.** Per-pixel calls: 320×200 = 64,000 calls/frame → ≤2 fps at the ceiling, before any budget. Batched: packing one pixel into a byte string costs ~0.1–0.3 µs on PUC (strings benchmark: 12 MiB rebuilt + checksummed in 0.96 s on 5.3, 0.6 s on 5.4; `bench/results-2026-09-01.md`), ~0.02–0.05 µs on LuaJIT with fixed-arity `string.char`/multi-assignment `string.byte` (strings2: 0.238 s), but ~0.6 µs with the naive `{byte(s,i,i+63)}`/`char(unpack(t))` pattern (3.8 s, JIT side-trace explosion). One call amortizes over the batch, so batching wins from batch size 2 and the call overhead is <2% at ≥256 pixels. A 128 KB 16-bpp 320×200 frame then costs ~10–20 ms of pure packing on 5.3 (≤50 fps with no program logic left), while a 640×480×32 bpp frame (1.2 MB) costs ~100 ms and exceeds a 1 MB machine's RAM. Pixel pushing is viable only for small/low-bpp surfaces; the API must be command-level (rects, lines, sprite/texture handles, VRAM blits, vertex buffers) so that per-pixel work never touches Lua.

### 3. Limits: sizes, signals, memory accounting, timeouts

- **Argument/result sizes.** No explicit cap for component calls; `maxNetworkPacketSize` (8192) and `maxNetworkPacketParts` (8) apply only to modem/linked-card messages (`NetworkCard.scala:117`, `LinkedCard.scala:61`). Practical caps: JNI `jsize` and the Lua RAM cap.
- **Signals.** `Machine.signal` (`Machine.scala:335-369`) drops the signal (returns `false`) when the queue holds `maxSignalQueueSize` entries; `Settings.scala:486` floors it at 256, this instance pins 256 (`OpenComputers.cfg:268`), and 1.12.64 raised the shipped default to 1024 (`application.conf` only, GTNH PR #226). Allowed arg types (`Context.java:158-184`, `convertArg :317-333`): null, Boolean, Byte/Short/Integer/Long (unchanged), Character → Integer, other `Number` (Float included) → Double, String, `byte[]`, `NBTTagCompound`, maps with string keys and values (a `java.util.Map` is converted entry-wise, nested maps dropped). Unsupported → nil + warning. Latent bug: `Machine.save` serializes only Boolean/Long/Double/String/byte[]/Map/NBT args and writes byte `-1` for anything else (`:862-879`), which `load` turns into nil (`:782`); so `Integer/Short/Byte/Character` args of a *queued* signal become nil after a world reload, while `Float` survives because `convertArg` already boxed it to `Double` — push `Long`/`Double`. A signal wakes a sleeping machine on the next tick (`:584-585`) plus `executionDelay`.
- **Memory accounting.** `limitMemory` (on by default) creates the state with a cap and the counting allocator `l_alloc_checked` (`LuaStateFactory.scala:353`; `jnlua.c:251-289`), one `getluamemory`/`setluamemory` JNI pair per allocation. Cap = `kernelMemory + RAM × ramScale`, `ramScale = 1.8` on 64-bit (`NativeLuaArchitecture.scala:152-163`, `:317`; `application.conf:265`). RAM per stick is 192–1024 KB upstream, **256–8192 KB here** (`OpenComputers.cfg:251-258`), `maxTotalRam` 128 MB here. Every string/table a callback returns is allocated inside that cap, so a 1 MB read-back on a 1 MB machine fails: `lua_pushlstring` gets NULL → Lua "not enough memory" → `LuaMemoryAllocationException`; the synchronized closure calls the same `component.invoke` (`machine.lua:1094-1100`), so in *both* direct and synchronized calls `NativeLuaArchitecture.invoke` catches it first and tries to return `(true, nil, "not enough memory")` (`:59-90`); in a direct call a failure of that fallback surfaces as a Lua error, and in a synchronized call only a failure of the fallback push (or of a later Lua-side allocation inside the closure) reaches `runSynchronized`'s `OutOfMemoryError` and `Machine.update`'s crash (`:186-191`; `Machine.scala:621-622`). Large read-backs must be chunked and sized against `computer.freeMemory()`; better, never read whole framebuffers back. Table results are worse: 16+ bytes per element plus one JNI push each. LuaJ has no accounting at all (`LuaJLuaArchitecture.scala:100-108`); OC-LuaJIT has its own counting allocator with the same intent (`docs/accounting-sync.md`).
- **Timeouts.** `computer.timeout` = 5 s (`application.conf:132`; `OpenComputers.cfg:302`) is exposed as `system.timeout()` (`SystemAPI.scala:42-47`) and enforced entirely in Lua: the kernel sets `deadline = realTime() + timeout` before each resume of the user coroutine (`machine.lua:1519`) and arms a count hook `debug.sethook(co, checkDeadline, "", hookInterval)` (`:1532`; `hookInterval ≥ 1000` instructions, calibrated at boot `:1-40`); `checkDeadline` raises the `too long without yielding` sentinel with a 0.5 s grace (`:42-54`). The window resets only when the program yields to the kernel (sleep/pullSignal/synchronized call). No Java-side watchdog exists (no match for "watchdog" in OC or ocelot-brain). Hence: a direct callback that blocks for *t* seconds is invisible to the hook but eats *t* of the program's 5 s; one that blocks forever hangs one of `computer.threads = 4` executor threads (`Settings.scala:59`, `Machine.scala:1136`) for the server's lifetime; a synchronized callback that blocks stalls the server tick. OC-LuaJIT replaces the standing hook with an injected one (`docs/watchdog.md`) but keeps the same semantics. Direct callbacks also run concurrently with the server thread and with other computers' workers (`Callback.java:44-57` warns the node network is not thread-safe).

### 4. LuaJ fallback

`LuaJLuaArchitecture` is registered when natives are missing or `registerLuaJArchitecture`/`forceLuaJ` is set (`LuaStateFactory.scala:33-35`); GTNH ships it off (`application.conf:1636`) but **this instance has it on** (`OpenComputers.cfg:427`). Differences (`ScalaClosure.scala`, `LuaJLuaArchitecture.scala`): numbers → always `Double` (`:73`); strings → raw byte slice (`:74-77`); tables → eager recursive copy into an immutable Scala `Map` whose keys and values go through the same conversion, so array keys are `Double` and string keys/values are `byte[]` slices (`:78-80`) — `Map.get("name")` on a table argument returns null on LuaJ; `Value` → `LuaValue.userdataOf` (`:49`); results pushed via `LuaValue.valueOf(byte[])` (`:47`). No persistence: `load` stops and restarts the machine (`:254-259`), `save` is empty (`:261`). No RAM cap. No `__gc`, so `Value.dispose` never runs. Sandbox is the same `machine.lua` (`:235`), LuaJ is 5.2-level (bit32 yes, `string.pack` no — the sandbox entries are nil-safe `machine.lua:901-903`). The shipped LuaJ is OC-LuaJ 20220907.1 (`dependencies.gradle:4`); its `Lua._VERSION` is `"Luaj 0.0"`, so the sandbox reports `_VERSION == "Luaj"` (`machine.lua:812`), and its `StringLib` registers 14 functions (`byte, char, dump, find, format, gmatch, gsub, len, lower, match, rep, reverse, sub, upper`) with no `pack/unpack/packsize` (MightyPirates/OC-LuaJ, branch `new`, `luaj-core/src/main/java/org/luaj/vm2/Lua.java` and `lib/StringLib.java`). Verdict: OpenGPU should *work* on LuaJ but need not be fast there; the only Java-side requirement is to accept `Double` for integer arguments (use `Arguments.checkInteger`, never pattern-match on `Long`), to tolerate `Double` table keys, and never to rely on string-key lookup in table arguments across runtimes (use arrays, or copy the table out with key normalisation).

### 5. Runtime differences relevant to a shipped Lua helper library

Libraries opened per state: 5.2 = BASE, BIT32, COROUTINE, DEBUG, ERIS, MATH, STRING, TABLE (`LuaStateFactory.scala:63-73`); 5.3/5.4 = same minus BIT32 plus UTF8 (`:81-91`, `:99-109`); OC-LuaJIT = the 5.2 set, deliberately without UTF8 (`OC-LuaJIT/.../LuaJITStateFactory.java:94-108`). `createState` removes `unpack`, `loadstring`, `math.log10`, `table.maxn`, `dofile`, `loadfile` and replaces `math.random` (`:372-421`). The sandbox (`machine.lua:740-1044`) exposes `string.dump` (`:888`), `string.pack/unpack/packsize` when present (`:901-903`), `bit32` when present (`:965`), `utf8` when present (`:1033`), `load` with mode forced to `"t"` unless `allowBytecode` (`:754-759`; default false, **true in this instance** `OpenComputers.cfg:203`), no `io`/`os` beyond OC's own `os` subset, and user `__gc` metamethods are stripped unless `allowGC` (`:776-808`; default false, true here `:209`). `math.frexp/ldexp/pow/cosh` are nil-guarded for 5.3+ (`:917-943`); OC-JNLua's meson build passes no `LUA_COMPAT_*` flags (`native/meson.build`), so assume `math.frexp` is absent on 5.3/5.4.

OC-LuaJIT specifics that constrain a helper library: the `jit` global is not exposed (`bench/oc/ingame-ladder.lua:30-33`) and the sandbox `_VERSION` is `"Lua 5.2"` exactly as on stock 5.2 (`lj52shim.c:2747-2759`, `machine.lua:812`, `roadmap.md:197`), so LuaJIT cannot be detected by `_VERSION` at all; a helper library must use a behavioural probe (e.g. `_VERSION == "Lua 5.2"` with `bit32` present and no `string.pack`/`math.type`, then a feature or timing probe such as whether `load` accepts a `string.dump` chunk) or a marker/capability that OpenGPU or the architecture chooses to expose; `bit32` functions are plain C functions (`lj52shim.c:2579-2730`) that the tracer cannot inline — use arithmetic in hot loops (a sound but unmeasured recommendation: neither `bench/strings.lua` nor `bench/strings2.lua` calls `bit32`); naive multi-return-into-table and `char(unpack(t))` patterns are 4× slower than PUC 5.3 while fixed-arity `char(b1..b8)` / 8-wide `byte` reads are 3.7× faster (`bench/results-2026-09-01.md`, addendum; both measured on a stock standalone `luajit`, not the in-machine CHECKHOOK build with the counting allocator — see the derating note below); the JIT is off during kernel init only; a closure that wraps `next` over a hash table is not replayable across a save, so iterators handed out by the library should snapshot keys into an array ("THE FOURTH CHANGE"; `-Docluajit.forin` diagnostic in `LuaJITArchitecture.java:189-260`). The in-machine benchmark ladder shows the allocator accounting tax is real (19–68 ns per allocator call on string-heavy runs, `bench/results-ladder-2026-09-29.md:582-589`), so standalone string throughput numbers should be derated ~1.5–2× in-game.

### 6. Portable encoding, throughput and handle strategy

**Encoding.** Ship one Lua module with two code paths selected at load time:

- 5.3/5.4: `string.pack("<I2"/"<i4"/"<f", …)` in bulk (`pack("<ffff", x, y, z, w)` per vertex), concatenated with `table.concat`.
- 5.2 / LuaJIT / LuaJ: arithmetic only — `v = floor(v) % 65536; char(v % 256, floor(v / 256))`; int32 likewise; float32 via `math.frexp` (sign/exponent/23-bit mantissa split with `floor`/`%`), used only for matrices and uniforms. Fixed-point (e.g. 16.8 or 24.8 signed) for coordinates/colors is exact on every runtime and JIT-friendly; prefer it as the default vertex format.
- Never use bitwise operators or `//` in a chunk that must parse on 5.2/LuaJIT; if the 5.3 fast path needs them, compile it with `load(src)` as OC-LuaJIT's `bench/compat.lua` does (text `load` is always allowed).
- Chunk builders: fixed-arity `string.char` of 4–8 bytes per call (JIT-friendly), pieces in an array, `table.concat` per 1–4 KB; keep `table.unpack` arity ≤ 4000 (LuaJIT's C-stack limit is 8000).
- Java side: parse with `ByteBuffer.wrap(args.checkByteArray(i)).order(LITTLE_ENDIAN)`; validate lengths; the array can be retained.
- Throughput estimates (standalone, derate 1.5–2× in-machine): byte-wise packing ≈ 10–15 MB/s on 5.3, ≈ 20 MB/s on 5.4, ≈ 50 MB/s on LuaJIT (idiomatic) / ≈ 3 MB/s (naive), `string.pack` path on 5.3/5.4 ≈ 30–80 MB/s (inference), LuaJ unmeasured and expected several times slower than PUC. A 10k-vertex buffer at 12 B/vertex (fixed-point) is ~120 KB → ~10 ms on 5.3, ~2 ms on LuaJIT: fine per frame.
- Alternatives rejected: Lua tables as bulk carriers (O(n) JNI on native, O(n) boxing copy on LuaJ, plus the Lua-side recursive walk); varargs (one JNI call per value, LuaJIT 8000-arg cap); numeric strings (allocation-heavy, slower to parse).

**Handles.** Recommend small integer handles (≤ 2^31) returned as `Integer`/`Long` (integer subtype on 5.3+, exact doubles elsewhere), scoped per GPU device and tagged with the owning computer's address. Pros: identical on all four runtimes; immune to `disableUserdata`; no per-push proxy scan; trivially persistable in the component's NBT; cheap to validate. Cons: no automatic reclamation (`Value.dispose` would only fire on native PUC anyway, and user `__gc` is stripped unless `allowGC`), so provide explicit `free(h)`/`freeAll()` and reset every handle on `computer.stopped`/`computer.started` exactly like `GraphicsCard.onMessage` (`:538-545`); expose `handles()` for leak debugging. Value userdata can be offered later as sugar (`buf:draw(...)`) but must not be the only way to reach a resource, and must be written with a no-arg constructor + NBT re-resolution so persistence works on stock and OC-LuaJIT.

**Persistence interaction.** Stock native persistence serializes the kernel coroutine and, if mid-synchronized-call, the pending closure/result (`NativeLuaArchitecture.scala:396-437`); OC-LuaJIT persists the same roots as one bundle through OC's `PersistenceAPI` (`LuaJITArchitecture.java:342-375`) and restores suspended Lua code exactly, so a render loop paused between `submit()` and `present()` resumes holding its integer handles. Nothing on the Java side is persisted for free: the component must save handle tables, surface metadata and (optionally, compressed) pixel contents in its `save(nbt)` as OC's GPU does for VRAM (`GraphicsCard.scala:646-673`), or invalidate all handles on load and push a `gpu_reset`-style signal so programs re-create resources. Queued-but-unexecuted command buffers should be flushed before save or dropped with the same signal. Values held in Lua at save time are re-created via `userdata.load` on every runtime that persists, so a Value must never hold a reference that cannot be rebuilt from NBT.

## Design implications for OpenGPU

1. **API shape:** command-level, batched, binary. One `submit(byte[])` per frame (or per few KB) carrying draw/state commands, plus `present()`. Per-pixel calls exist only as debugging conveniences and should charge the budget heavily.
2. **Arguments:** bulk data only as byte strings (`checkByteArray`); tables only for small metadata (<100 entries) and copied out inside the callback with key normalisation; never retain a `Map` argument and never rely on string-key lookup into it (keys are `byte[]` on LuaJ, nested strings are `String`-or-`byte[]` on native runtimes).
3. **Results:** metadata as scalars/small tables; pixel/attachment read-back only as `byte[]`, chunked, bounded by a caller-supplied byte limit and documented against `computer.freeMemory()`; never `String` for binary.
4. **Numbers:** accept any `Number` for integers; return ids as `Integer`; return coordinates as `Double` only when fractional.
5. **Direct callbacks must be microsecond-cheap and non-blocking:** enqueue into a locked/lock-free per-device command queue consumed by the server tick or a dedicated render thread; signal completion (`machine.signal("opengpu_frame", Long frameId)`) or let Lua poll. Apply backpressure by returning `nil, "queue full"` rather than blocking. Use `limit`/`consumeCallBudget` to cap `present()` to a sane frame rate per CPU tier (budget 1.0 → `limit` = frames per tick on T2).
6. **Thread-safety:** framebuffers are mutated from up to 4 worker threads and read by the server thread (client sync) — double-buffer with atomic swap or lock per device.
7. **Handles:** integers + explicit free + lifecycle reset on computer start/stop; optional Value sugar later.
8. **Lua helper library:** pure 5.2 syntax, runtime detection by feature probe (`string.pack`/`math.type` → 5.3+; `_VERSION == "Luaj"` → LuaJ; `"Lua 5.2"` is ambiguous between stock 5.2 and OC-LuaJIT and needs a behavioural probe or an OpenGPU-exported marker), two encoder paths, no bit ops in hot loops, array-snapshot iterators, no reliance on `__gc`, shader source as text (bytecode is runtime-specific and `allowBytecode`-gated, not refused outright).
9. **Persistence:** component persists its own state; define `gpu_reset` semantics so programs survive the no-persist cases (LuaJ, dropped queues).
10. **Testing:** build the throughput harness on ocelot-brain first (same Machine semantics) with budgets set to both `[0.5,1,1.5]` and `[1,2,4]`; measure calls/s, bytes/s per runtime, and RAM headroom for read-backs.
