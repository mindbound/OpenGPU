## 1. Is OpenGPU worth taking on?

**Verdict: yes, with the shape fixed up front.** OpenGPU is worth building as a deterministic, host-neutral software graphics engine whose 2D path is the product, whose 3D path replicates *commands* (not pixels) to a client-side mirror of the same engine where the client can afford it (T2 on typical hardware, under a per-tick budget; 12 §1) and streams lossy/LOD pixels elsewhere, and whose hardware-GL backend is an optional late addition behind an exercised seam. Built that way it meets all three success criteria on the stack the research verified (Java 8/LWJGL2 and Java 17–21/lwjgl3ify, Angelica core profile, OC 1.12.64-GTNH). Built as "server renders everything and streams pixels" it fails multiplayer 3D by 10–70× (07 §1, 03 §4); built as "clients render with GL" it puts the one surface 07 rates High/High (Angelica/Iris/SDL-GPU churn, 2.2.8→2.2.30 in two months) on the critical path of every frame.

What is **cheap** (verified, low risk): the 2D engine (0.2–0.5 ms per 320×200 frame, 06 §3, 07 §1); dirty-tile + Deflate streaming at 5–80 KB/s per viewer, the traffic class of OC's own screens (03 §4, 07 §5); the Lua boundary (byte strings in, `Integer` handles out, 2 direct calls per frame, 04 impl. 1–7 — now measured: a direct call costs 1.5–1.6 µs on OC-LuaJIT and 4.2–4.5 µs on stock Lua 5.2/5.3/5.4, a 100 KB string argument 19–28 µs, so `submit(60–100 KB)` + `present()` is ≈ 30–40 µs of executor time per frame on stock Lua, ≈ 0.1 % of a tick at 20 fps, 11 §2.1); the client display path (`glTexSubImage2D` + one Tessellator quad, the pattern OC-GTNH's `DynamicFontRenderer` already ships under Angelica, 02 §3/§5); headless testing, because ocelot-brain carries the same upstream-1.8.9 `Machine`/budget/retry/`bitblt` code as OC 1.12.64-GTNH (diffed in 19: the divergences are energy, `SaveHandler` persistence transport, tick cadence, the 1024-vs-256 queue default and GTNH's `computer.realTime` sandbox line) and OC-LuaJIT's harness already boots OpenOS in it (05 §3).

What is **hard** (07 §6): the shader compiler (lexer, parser, typer, interpreter, ASM backend, fuzzer; 10–14 weeks on its own, 08-C §8.5); the client mirror's load-bearing determinism and its client-CPU budget (a T3 3D frame costs the mirror 8.6–13.4 ms on typical hardware, 12 §1, which is why it ships in M3 behind a per-tick budget); multi-viewer transport (residency, two encodings, catch-up, token buckets); a GL backend that survives Angelica.

What is **uncertain** (must be measured in M0 before any tier is frozen): in-machine Lua encoding cost on 5.3, 5.2 and OC-LuaJIT (07 §2, 10 F9); deflate ratios for real 3D scenes (12 §1 measured 1.7–2.0× on synthetic RGB565 frames, confirming 07 verif. C6's estimate); raster constants on older server cores (06's raster bench and 11's call-overhead measurements both ran on the Core Ultra 9 285HX that also hosts the game instance; 07's "Ryzen 7 7840U bench box" is OC-LuaJIT's September laptop and contributed only VM-ratio data; 2–5× slower raster and 1.5–3× slower per-call constants are plausible on an older server core *[inference]*, 11 §3); the OpenOS free-memory baseline on one 192 KB stick, which decides whether the 2D product can promise a T1 case (10 F6). Two former unknowns are closed: per-call overhead is **measured** (11 §2: 4.2–4.5 µs empty / 5–9 µs with scalar args on OC's Lua 5.2/5.3/5.4, 1.5–2.4 µs on OC-LuaJIT; 100 KB string in 22–28 µs, round trip 34–51 µs; 1000-entry table in 84–118 µs on PUC / 16 µs on LuaJIT, table out 0.9–1.6 ms; identical on JDK 8 and 17 and under both budget tables), and `GlCaps` under lwjgl3ify is closed by 14 (lwjgl3ify's `org.lwjglx.opengl.ContextCapabilities` mirrors LWJGL3's `GLCapabilities` by reflection; Angelica's GLSM and OC-GTNH already probe through it).

What would make it **not worth it**: if the user's real goal is GPU-class 3D (1280×800, hundreds of thousands of triangles) for many simultaneous viewers on public servers — that is Proposal B's territory and its risk profile, and no software design reaches it; or if M0 shows in-machine encoding ≥ 15 ms per 1 k triangles on Lua 5.3 *or 5.2* (the per-call half of the original condition is closed: 4–9 µs measured against a ≥ 50 µs threshold, 11 §2), which would make even batched 3D unusable on stock OC (OC-LuaJIT would still work, which narrows the audience). Neither is the likely outcome.

## 3. Recommended architecture

**Base: Proposal C** (08-C §1–§8), with twelve grafts from A and B. One sentence: *the server always owns the truth, the wire carries whichever of pixels or commands is cheaper per viewer per tick, every viewer that can afford it runs the same deterministic core as a mirror and the rest receive lossy pixels, and real GL is a later drop-in.*

### 3.1 Where rendering runs by default

- **Server (authoritative).** Every presented frame of a *watched* display is executed by `opengpu-core` on an OpenGPU-owned `ForkJoinPool` (sized `max(1, cores/2)`, bounded; the Internet card's own-pool precedent, 07 §3). The presented frame is quantized to the display's wire format (index8 or RGB565, 07 §5) *as part of present*, and that quantized frame is what readback, persistence, keyframes and the CRC32 refer to — so `TILES` and `CMDS` viewers see byte-identical pictures. The pool is one per JVM (in single player the mirror shares it, with its own budget, 12 §4), and the encoded frame leaves from the pool thread (§3.5).
- **Lazy rendering for unwatched displays** (graft from B via both judges). A display with zero viewers, no pending `readPixels`, and no save in progress does not rasterize: in *frame* mode only the newest sealed frame is kept (frames are self-contained), in *canvas* mode frames accumulate in a bounded log (256 KB or 64 frames) that is rendered and compacted when the cap, a subscribe, a readback or a save arrives. This removes 07's "server renders everything whether or not anyone watches" cost without giving up exactness.
- **Client mirror (M3).** Each client holds the identical core jar. Per display it applies `TILES` (pixel deltas) or replays `CMDS` on a mirror `Device` (budgets off, resources resident), producing the same quantized frame; a CRC mismatch requests a keyframe, two consecutive mismatches force `TILES` for that display (12 §5). The mirror runs on one client worker thread under a **per-tick replay budget** (`client.mirrorBudgetMs`, default 8 ≈ 16 % of a core; a 4 ms slice per individual replay), spent in order of on-screen size and driven by a per-display EWMA of measured replay time that ignores the first frames after a program change (HotSpot warm-up); displays outside the budget receive the lossy/LOD lineage (`PREFER_TILES`); resident mirrors are LRU-capped (`client.maxMirrors` 8, `client.maxMirrorHeapMB` 64). A T2 3D frame costs the mirror ≈ 1.3–1.6 ms on the bench CPU (≈ 2.3–3.8 ms on typical hardware), a T3 frame ≈ 4.8–5.6 ms (≈ 8.6–13.4 ms), 12 §1 — hence the mirror ships in M3 with the `:jit` backend it depends on (the interpreter would cost 13–64 ms per shaded T2 frame) and M2's 3D goes out as `TILES` under the governor.
- **Single player and the LAN host never run the mirror**: for viewers on a local channel (`NetworkManager.isLocalChannel()`) the encoder sends undeflated `TILES` outside the token bucket, because the in-memory pipeline has no codec and a 512 KB copy is cheaper than any replay (12 §4). The display TE captures `world.isRemote` at `validate()`; nothing on a pool thread consults `SideTracker`/`getEffectiveSide`, which are thread-name checks that return CLIENT on worker threads (12 §4).
- **GL backend** (M5, optional): `Backend` implementation on the client that executes `CMDS` on the GPU into an FBO, with the mirror as the fallback on link failure. It is the only part of the design that touches 02 §5's "extra obligations" list.

### 3.2 Lua API and encoding

Two components, mirroring OC's gpu/screen split (00 impl. 1): card **`opengpu`** (`DriverItem`, `Slot.Card`, `Visibility.Neighbors`, `HostAware` Case/Server only — `worksWith(stack, host) = isComputer || isServer`, `DriverItem.java:66-80`; robot, tablet, microcontroller and drone hosts live in isolated internal networks where `bind` can never find a display block and their built-in screens are fixed GUI-only text buffers (15 §3), an item-hosted display being a possible M5+ feature — `createEnvironment` returns `null` client-side, registered in FML `init` because OC locks the driver registry in its own `postInit`, `Proxy.scala:112-115`) and display block **`opengpu_screen`** (`TileEntityEnvironment` + `SidedEnvironment`: node on the five non-front faces to anything, on the front only to an adjacent `api.internal.Keyboard`; `Visibility.Network` on the origin, every multi-block constituent keeps its own node — 15 §2). The display does *not* implement `api.internal.TextBuffer` in v1 (deferred to M5; it would require compiling against ≥ 1.12.58 for the `dropFile(byte[])` signature, 00 §3).

Callback groups, all `direct=true` unless noted, every one calling `consumeCallBudget` *before* any side effect so the `LimitReached` retry is idempotent (00 §1):

| Group | Callbacks | Rules |
|---|---|---|
| display | `bind(addr)` (non-direct), `get/setResolution`, `getTier`, `getCaps`, `set/getPalette(bytes)` | resolution ≤ min(card tier, screen tier) |
| resources | `create{Buffer,Texture,RenderTarget,Program,Kernel,Pipeline}`, `upload(h,off,bytes)`, **`updateTexture(h,x,y,w,h,bytes)`**, **`updateBuffer(h,off,bytes)`** (B graft: viewers receive only the changed region, unlike OC's `TextBufferRamInit`, 01 impl. 9), `free`, `freeAll`, `handles`, `getMemory`, `getProgramInfo(h)` | `Integer` `slot\|generation` handles < 2^31, zero invalid, never `Value` userdata (04 §6); `createProgram`/`createPipeline` hash-cached (B graft); `getProgramInfo`, `handles`, `getMemory`, `getCaps` return numbers/strings or small fixed tables (≤ a few dozen entries), never per frame — returning a table costs ≈ 1.2 µs per entry (11 §2.3) |

**Signals** (A graft for the set, C's rule for the types): `opengpu_frame(card, frameId:Long, status:String)` raised **from the pool thread** (`Machine.signal` locks only `state`/`signals`, never the machine monitor, `Machine.scala:335-339`; `architecture.onSignal` is a no-op on native Lua, LuaJ and OC-LuaJIT, 12 §6) through an `AtomicReference<Context>` on the card that every callback refreshes and that `onDisconnect(this.node)`, `computer.stopped` and `computer.started` clear, with an epoch counter that invalidates in-flight jobs; jobs hold the card, never the `Context`, so a dead `Machine`/TE/world is never retained and a moved card cannot signal the wrong computer (12 §6). Signals are coalesced to one pending per device *before* `signal` is called, because the queue is 256 on the user's instance (`CFG:268`) and on pack 2.8.4, 1024 on pack 2.9.0 and in the 1.12.64 jar default (`maxSignalQueueSize`, floor 256 at `Settings.scala:486`; 10 F1, 19 §3); the design assumes 256 and the harness tests both sizes. `opengpu_error(card, frameId:Long, msg)`; `opengpu_reset(card, reason)`. Arguments are `Long`/`String`/`Double` only, because `Machine.save` writes byte `-1` for `Integer` args and `load` turns them into nil — upstream behaviour present in both GTNH and ocelot (04 §3, 19 §3). Touch input keeps OC's names and argument order (`touch/drag/drop/scroll(screen, x, y, button|delta, player)`) with **0-based integer pixel coordinates** boxed as `Long` (`Double` under `setPrecise`, allowed on every tier), computed by OC's own bezel-and-letterbox projection (`Screen.scala:100-139`) with the framebuffer resolution in place of `renderWidth/renderHeight`, rejected (not clamped) outside the picture, emitted as `computer.checked_signal` after an 8-block reach check against any constituent (00 §3, 15 §4); keyboard input is forwarded as `keyboard.keyDown/keyUp/clipboard` node messages exactly as `TextBuffer.ServerProxy.sendToKeyboards` does, so OC's keyboard component applies its own reach check (03 §2) — from *every* constituent block's node, so a keyboard touching any block of a multi-block display, on any face, receives keys; `hasKeyboard` (GUI gating, synced to the client in the description packet) and `getKeyboards()` use the same six-face, all-constituents rule (15 §2).

**Command stream v1**: C §3's table-driven little-endian format (`"OGPU"` header, u8 opcodes with fixed-size operands, `0xFF END`; `CLEAR … DRAW_INDEXED, FILL_RECT, BLIT, LINE, TEXT, COPY, DISPATCH, WRITE_BUFFER`). Everything Lua encodes is an integer or 16.16 fixed point, so one arithmetic + fixed-arity `string.char` encoder works on 5.2, 5.3, 5.4, OC-LuaJIT and LuaJ; it is written JIT-friendly — monomorphic locals, fixed-arity calls, no varargs or `char(unpack(t))` in the hot loop (4× slower on LuaJIT), no `//`, bitwise operators or `bit32` — so that OC-LuaJIT traces it and is the headline performance tier while stock PUC Lua is the guaranteed floor; `opengpu.lua` adds a `string.pack` fast path via `load()` only where present (`load` of *source* only — the pack ships `allowBytecode=false`, so `load(string.dump…)` raises there, 10 F8; LuaJIT detection uses `_VERSION`, `bit32`, absence of `string.pack`/`math.type` and a marker OpenGPU exports, never a bytecode probe) and never calls `computer.realTime()` (GTNH-only since 1.12.43, absent in ocelot and upstream, 19 §8 — pace with `computer.uptime()` or feature-detect) (04 §5–6). Bulk data crosses only as top-level Lua strings (`checkByteArray`, zero decoding). The only table argument is `PipelineDesc`, and it must stay the only one and be copied out immediately (with key normalisation because keys are `byte[]` on LuaJ, 04 §4): every table argument holds a JNLua registry reference against the machine's RAM cap until the JVM's next GC (11 §2.3: 100 k table calls drained a 2 MB machine to 58 KB under an idle heap), and returning a table costs ≈ 1.2 µs per entry. Per frame: 1 `submit` + 1 `present`, ~100 bytes of uniforms for a resident mesh (07 §2).

**Runtime targets**: Lua 5.3 is what a freshly crafted CPU runs on both the GTNH pack and the user's instance — on the pack *despite* `defaultLua53=false`, because 5.3 is registered first and an unstamped CPU resolves to `architectures.head` (10 F4); Lua 5.2 is one sneak-right-click away, is the pack maintainers' declared default (PR #10252) and lacks `string.pack` and integers, so **5.3 and 5.2 are both must-pass**; **OC-LuaJIT is a first-class arm** of the matrix and the tier whose figures are quoted as the performance headline (the owner's addon, not shipped by the pack); Lua 5.4 is a user-instance-only leg (`enableLua54=false` on the pack); LuaJ is a correctness-only fallback (`registerLuaJArchitecture=false` on the pack, selectable only on the user's instance). One portable API for all five — no LuaJIT-only code path.

**Budget charges** (opt-in via `consumeCallBudget`, as OC's GPU does, 06 §1): `submit` 1/32·2^-tier + len/1 MB; `present` 1/8, 1/16, 1/32; simple-2D 1/64..1/256; readback 1/4 per 64 KB; `createProgram` 1/4; uploads len/256 KB with `bitblt`'s two-phase throw-then-`context.pause` pattern (A graft, `GraphicsCard.scala:221-253`) so a 1 MB texture costs a one-tick stall, never an error. Tuned against `[0.5, 1, 1.5]` first — the pack's shipped table on 2.8.4, 2.9.0-beta-3 and 2.9.0-RC-2 (`config/OpenComputers.cfg:143-147`) and OC's default; under these charges T1 affords 4 `present`, 32 simple-2D ops and 2 readback chunks per tick (10 F7). `[1,2,4]` is the user's local override and only a regression leg. The stall protocol is measured (11 §2.2): the over-budget call executes on the tick thread next tick with a refilled budget and the executor resumes 12 ms later, so an over-budget `present` costs one tick of latency and nothing else, and the per-call cost itself does not depend on the budget table. Both tables are exercised in ocelot, which runs the identical `consumeCallBudget`/retry/`bitblt` code (19 §1, §7).

### 3.3 Shader language and compiler

GLSL ES 1.00 subset with Appendix-A restrictions mandatory (06 §4): constant-bound `for` only, no `while`/recursion/dynamic indexing, precision qualifiers ignored, built-ins `gl_Position gl_PointSize gl_FragCoord gl_FrontFacing gl_FragColor`, `discard`, `texture2D`; compute kernels use the same grammar with a `kernel` entry point, `global_id()`, read-only inputs and exactly one write-only output indexed by the global id (no local memory, barriers or atomics; reductions as two dispatches — deterministic regardless of scheduling, 06 §5). Pipeline: hand-written lexer → Pratt parser → typed AST → static instruction count → scalarised `ProgramIR` (every `vecN` becomes N float temporaries, 06 §3). Executors share the IR through one shape, `IrEmitter<T>` (B graft): the **interpreter** in `:core` (reference, ocelot/test executor, fallback), the **JIT** `IrEmitter<Class<?>>` in `:jit` (M3), and the **GLSL 330 emitter** `IrEmitter<String>` (M5).

JIT rules (05 §1, 06 §4, 07 risk 9): shaded **and relocated** ASM 9 (`LaunchClassLoader` loads `org.objectweb.asm.` parent-first; the launcher's ASM is 5.0.3 on Java 8, 9.x under lwjgl3ify); `V1_8` classes with a non-loading `getCommonSuperClass`; defined through a private `ClassLoader` subclass parented to the mod loader (OC-Wasm `Compiler.java:190-204`; no `Unsafe`, no `Lookup.defineClass`), one loader per program, cached by `hash(source, pipeline state)`, never persisted; one class per (program × pipeline state) so every per-pixel call site stays monomorphic (what 06 verif. C4's data requires); methods < 6 KB bytecode (`HugeMethodLimit` 8000); emitted opcodes limited to arithmetic, locals, engine-array access and `StrictMath` — no `invokedynamic`, reflection or allocation; `CheckClassAdapter` and a grammar fuzzer with an interpreter-vs-JIT oracle in tests. Static caps: source ≤ 16 KB, ≤ 4 096 scalar ops per fragment, 16 384 per vertex, 65 536 per work-item, loops ≤ 1 024 iterations nested ≤ 3, ≤ 4 samplers, ≤ 64 uniform vec4 slots, ≤ 4 compiles/s per card. The same child-loader strategy serves the client mirror (12 §3: GTNHLib's `StaticASMEventHandler$ASMClassLoader` already runs this pattern on the client stack, and no installed coremod attaches a `java.lang.instrument` agent); the client compiles shader *source* received in `RESOURCE` records on the mirror worker, never on the render thread, with the same cache key, and never receives bytecode.

**Determinism rules are a public contract**, because the mirror depends on them: `strictfp` on all core math; transcendentals through **own `float` polynomials** (preferred) or `StrictMath` (fdlibm, pure Java since JDK 21, `-ffp-contract=off` natives on 8/17) — never `Math` intrinsics (1–2.5 ulp and platform-dependent, 06 §6; the aarch64 stubs have differed from x86, JDK-8210461, JDK-8210858); basic arithmetic is portable across x86-64 and aarch64 because Java forbids FMA contraction and HotSpot keeps FP reductions in source order (JDK-8320725; 12 §5); 28.4 fixed-point edge functions with the top-left rule, pixel centres at +0.5, ±1024 px guard band, near-plane clipping only; `float` depth tested before shading; integer blend `(x + (x>>8)) >> 8`; tiles own their pixels, bins built serially; palette quantization through a 32 K-entry RGB555 LUT with ordered dither (C §6). Conformance CI asserts byte-identical frames for 1 vs 8 threads, JDK 8 vs 17 vs 21, server vs mirror, on x86-64 **and on an aarch64 JDK 17/21 leg** (`ubuntu-24.04-arm`), since aarch64 clients exist only under lwjgl3ify (12 §5); the GL backend is held to ≤ 2 LSB on ≥ 99 % of pixels, edges excepted.

### 3.4 Networking

One channel name `"OpenGPU"`: an `FMLEventChannel` for client→server input and server-thread control packets, OC-style raw `DataOutput` payloads with a deflate flag byte, heap `ByteBuf`s (`Unpooled.wrappedBuffer(byte[])`) released by hand (03 §3); frame packets are `FMLProxyPacket`s on the same name handed by the pool thread to `NetworkManager.scheduleOutboundPacket` (§3.5, 13 §4). Handlers run on the main thread in 1.7.10 on both sides (03 §6), so the client handler only copies bytes and hands them to a decode worker. Packets stay ≤ 256 KB (keyframes split by rows) so the design holds under Forge's portable 2 097 050-byte cap; Hodgepodge's 256 MiB is never relied on; client→server never exceeds 32 766 bytes (00 §5, 03 §3). Because frames leave from the pool, per-connection order is `execute()` order rather than tick order (13 §1.5): every packet carries `(displayId, generation, frameId)`, the client ignores stale generations and frames for displays it has not loaded yet (chunk data may arrive after the first frame), and a generation bump is emitted by the first pool job that renders under the new generation.

Per display, per tick, the encoder (on the pool) picks **`TILES` vs `CMDS` by a cheap estimate** (judge note): `dirtyTiles × tileBytes × ratioEWMA` versus `cmdLen + missingResourceBytes(viewer)`; only the winner is encoded. `TILES` encodings are **shared across viewers with the same (LOD, lossy) class, at most four lineages per display** (A graft), so extra viewers cost 5–20 µs of send, not an encode; `CMDS` bytes are encoded once and each viewer's packet prepends only the dirty-rect `RESOURCE` records it lacks (per-viewer residency generations). Per viewer: a token bucket (16 KB/tick ≈ 320 KB/s, burst 512 KB, server aggregate 2 MB/s — the OC2 `StreamingLoadBalancer` shape, 01 §7). An over-budget viewer is **skipped, never split**, and later receives a `CATCHUP` over the union of tiles changed since its last acknowledged seq, from a ring of the last 8 per-frame tile-hash arrays (A graft; 260 × 8 bytes per frame at 320×200) instead of C's full `KEY`. `CMDS` goes only to a viewer whose mirror is in sync (M3; in M2 the `CMDS`/`RESOURCE` stream is produced and recorded for the virtual client but not sent); otherwise `TILES`/`CATCHUP`. Keyframes on subscribe, CRC mismatch, every 30 s, and after resolution/palette changes. **M2** adds A's **lossy 4×4 block lineage** (~26 KB per 320×200 frame → ~260 KB/s at 10 fps) and **half-resolution LOD** beyond 24 blocks with hysteresis, because they are the fallback the mirror sheds to and the answer for streamed-texture 3D where `CMDS` degenerates to pixel cost anyway: lossless T3 3D is ≈ 5 MB/s at 20 fps (2.0× deflate, 12 §1 [measured]) and the 16 KB/tick bucket admits ≈ 1 fps of it. Viewers on a local channel bypass all of this (§3.1).

Recipients: chunk watchers (the only effective OC filter today, 00 §3) within `displayRange` (default 64 blocks, hysteresis 8), **additionally capped by `misc.maxNetworkClientPacketDistance` when > 0** via `API.config`, because operators already use that knob and OC applies it to server→client traffic despite the config comment (closes the 01/03 open question). Every C2S packet is validated: chunk watching, reach ≤ 8 blocks, `isFinite`, size, and touch coordinates range-checked against the display's current resolution; key packets are reach-checked by OpenGPU as well as by OC's keyboard component (15 §2.5).

Expected bandwidth per viewer (07 §1, 03 §4, all **[est.]** until M0 measures ratios): 2D UI 5–10 / 20 / 80 KB/s by tier in `TILES`; 3D with resident meshes 4–40 KB/s in `CMDS`; repaint bursts 25–40 KB (T2) / 200–340 KB (T3); lossless T3 3D in `TILES` ≈ 255 KB per frame (12 §1 [measured]), i.e. ≈ 5 MB/s at 20 fps — the lossy/LOD lineage's reason to exist.

### 3.5 Threading

Four actors, one coarse monitor per device (OC's own model for `Hologram` and `TextBuffer.ServerProxy`, 00 §5):

- **OC worker threads** (shared pool of 4): `consumeCallBudget` → validate (0.05–0.2 ms per 60 KB, 07 §1; the 4.3 µs call plus ≈ 25 µs for a 100 KB copy leave ≈ 170 µs of that budget for validation on stock Lua, 11 §2) → copy `byte[]` → enqueue under the monitor; `present` seals a `FrameJob`; ≤ 0.2 ms, never renders, never touches the node network or world. A third frame in flight returns `nil,"busy"`; repeat offenders get `context.pause()`. The shipped `waitFrame` yields on `computer.pullSignal` with a timeout, never spins (the 5 s watchdog is a Lua hook that cannot interrupt Java but does kill a spinning program, 04 §3); a `pullSignal(0)` yield resumes ≈ 63 times/s (3.2 per tick, 11 §2.2), so a per-frame yield does not cap a 20 fps loop, whereas a per-frame *non-direct* call would (1 per tick).
- **OpenGPU pool**: runs the ordered per-device job queue (uploads, frames, dispatches) with tile-parallel subtasks, then quantize, CRC32, tile diff, deflate; a 10 ms per-device slice after which the frame aborts with `opengpu_error`; raises `opengpu_frame` through the card's `AtomicReference<Context>` after the epoch check (§3.2), **and sends the frame itself** to the display's viewer snapshot via `NetworkManager.scheduleOutboundPacket` after a pre-send size check (an over-cap `S3FPacketCustomPayload` disconnects the viewer, 13 §1.6), skipping viewers whose `channel().isWritable()` is false or whose token bucket is empty. It never touches the world, player lists, `SideTracker` or `getEffectiveSide` (12 §4).
- **Server thread**: `update()` refreshes each active display's viewer snapshot (immutable list of `NetworkManager`s chosen by OC's chunk-watcher + range rule, `PacketBuilder.scala:79-102`), sends control packets, processes input and runs hash-gated persistence — 5–20 µs per display per tick. It does **not** send frames: the pool hands each encoded frame to `scheduleOutboundPacket(FMLProxyPacket)`, the thread-agnostic queue every FML send ends in (13 §1.4-1.5); `FMLEventChannel.send*` is never called off the server thread because its target attributes race (13 §1.3). This removes the 0–50 ms (avg 25 ms) wait for the next tick that 07 §1 budgeted — Lua-call→pixels on LAN drops to ≈ 10–30 ms average (13 §4.3 [derived]). A `net.sendFromPool=false` switch restores tick-thread sending for diagnosis.
- **Client**: main-thread handler copies; decode worker applies tiles or (from M3) replays commands on the mirror under the per-tick budget; resident mirrors are LRU-capped (`client.maxMirrors` 8, `client.maxMirrorHeapMB` 64; ≈ 2.4 MB heap per T2 and ≈ 8.9 MB per T3 mirror, 12 §2); render thread uploads dirty rows once per frame and draws the quad.

### 3.6 Persistence

Card item NBT holds only tier, bound screen, palette and the handle table (a few KB); the display TE's `writeToNBTForClient` writes only `displayId`, resolution, tier and `hasKeyboard`. Resource bytes, shader *source* and the last presented (quantized) frame go deflated to an OpenGPU-owned side-file store `<world>/opengpu/state/<dim>/<cx>.<cz>/<address>`, written asynchronously from a snapshot taken under the device monitor — our own `SaveHandler`, since OC's is not API (00 §5, 07 risk 5). **Writes are content-hash gated** (A graft): `save()` schedules a write only when the snapshot hash changed, so description packets and Waila lookups cost a hash compare; this answers J2's objection to C's `savingForClients` check without touching any OC internal and never reproduces OC's 0.1 s machine pause per description packet. In-flight jobs are dropped at save and surface as `opengpu_frame(..., "dropped")`; a missing or corrupt side file invalidates every handle and raises `opengpu_reset(card, "load")`. Lua holds only integers and byte strings, so OC-LuaJIT's whole-state serializer never sees an OpenGPU object and a loop suspended between `submit` and `present` resumes with valid handles because generations are persisted (04 §6); LuaJ (no persistence) gets `opengpu_reset` on every reboot (a no-natives fallback path on the pack, a selectable architecture only on the user's instance, 10 F8); all handles reset on `computer.stopped/started` like `GraphicsCard.onMessage`.

### 3.7 Angelica measures

Shipped client path = 02 §5's certified baseline, what OC-GTNH's `DynamicFontRenderer`/`ScreenRenderer` do today: CPU `int[]` ARGB; `glTexImage2D(GL_RGBA8)` once; `glTexSubImage2D(GL_BGRA, GL_UNSIGNED_INT_8_8_8_8_REV)` of dirty rows on the render thread, frame-counter keyed (Iris may call a TESR twice); `GL_NEAREST`, `GL_TEXTURE_MAX_LEVEL=0`; TESR modelled on `ScreenRenderer`, `glPushAttrib` of the five bits it changes (stack depth 32 in 2.2.21), lightmap 240/240, one Tessellator quad; no display lists, `glBegin`, GLSL, FBO or `GLSync`. Chassis via a stateless `@ThreadSafeISBRH(perThread=false)` ISBRH with no `Tessellator.draw()` (`BlockRenderer.scala:16`), which also keeps the TESR out of Iris's shadow pass under the default config (02 §2; closes the shadow-pass question). `getRenderBoundingBox()` returns the **maximum multi-block extent from the very first call** and `getMaxRenderDistanceSquared()` is constant per class, because Celeritas classifies per class on first sight and caches the AABB per instance (02 §3, 03 §1). `opengpu.client.*` is never excluded from transformation, and never carries `@Lwjgl3Aware` or a `Lwjgl3ify-Aware` manifest attribute (all three resolve `GLContext.getCapabilities()` to a throwing stub under lwjgl3ify, 14 §2.7). Angelica is `compileOnly …:2.2.21:api`, optional at runtime. Only LWJGL2 `GL11/GL12/OpenGlHelper` calls, which lwjgl3ify renames and GLSM maps on both legs (02 §4). `GlCaps` is one final class that reads the LWJGL2 `GLContext.getCapabilities()` plus `OpenGlHelper` flags lazily on the render thread and caches primitives; the same code serves LWJGL 2.9.4, lwjgl3ify (2.1.16–3.0.37, via the `org.lwjglx` shim) and Angelica's SDL-GPU backend (via `GLCapabilitiesOverride`); only fields present in LWJGL 2.9.4, the shim and LWJGL 3.4.3 are read (14 §2.3, unit-tested); `glGetString` is logged, never branched on (14 §3). ## 5. Questions for the user

Ordered by how much the answer changes the design; each with the default the plan assumes.

1. **Who are the viewers?** Public GTNH servers over the internet with several watchers per display, or LAN/single-player? *Default: public internet* — this is what justifies the lossy/LOD governor in M2 and the `CMDS` mirror in M3; for LAN/single player the local-channel bypass already gives lossless `TILES` at every tier (12 §4), the mirror could be dropped entirely and M3 shrinks by ~3 weeks.
2. **Exact readback and identical pixels for every viewer — required?** *Default: yes* (exact `readPixels`, bit-identical server/mirror); it is what makes the deterministic core load-bearing. If "approximately the same picture" is acceptable, Proposal B's GL-first path becomes viable and the trade-off flips.
3. **Is the v1 3D promise acceptable?** A client watching five T3 3D displays would spend 24–28 ms per tick on the bench CPU and 43–67 ms on typical hardware (more than a core) replaying the mirror; the per-tick budget keeps it at ≤ 8 ms by shedding displays to the lossy/LOD lineage, so the real v1 promise is lossless remote 3D at T2, lossy/LOD at T3, and lossless T3 only on LAN/single player or via M5 GL (12 §1, §7). **And do you want the GL backend (M5) at all, including SDL-GPU?** *Default: that promise; mirror in v1 (M3) behind its exit criteria; M5 optional; SDL-GPU not a v1 target.*
4. **Tier table**: T1 160×100 index8 @ 10 fps, T2 320×200 index8 @ 20, T3 640×400 RGB565 @ 20 (07 §5), ARGB internally — accept? *Default: accept; tune for the pack's `callBudgets=[0.5,1,1.5]` and regression-test `[1,2,4]` (10 F1); VRAM caps follow the pack's `vramSizes=[1,2,3]`, not the instance's `[1,2,4]`; 1280×800 only via M5 GL.*
5. **Minimum machine RAM a full OpenGPU program must run in** (the pack's `ramSizes` start at 192 KB; a T1 case holds 192–512 KB apparent, 10 F6; yours start at 256 KB)? *Default: the 2D product targets one 192 KB stick with resident resources and ≤ 16 KB readback, subject to the M0 OpenOS-baseline measurement; 3D assumes ≥ 1 MB apparent, i.e. a T2 case with two 512 KB sticks or any T3 case on the pack.*
6. **Should stock OC GPUs/OpenOS be able to `bind` the pixel screen as a text console** (`api.internal.TextBuffer`, 56–58 methods, compile against ≥ 1.12.58)? *Default: no in v1; OpenGPU ships its own `term` library; M5 revisits.*
7. **Angelica: optional (plain GL) or hard dependency** (enables `TesrMeshProvider`/`TesrShaders` batching and GLSM getters)? *Default: optional, `compileOnly :api`.*
8. **OC-LuaJIT** (your addon, the headline performance tier): will it expose a capability marker (so `opengpu.lua` can detect it without a bytecode probe — `_VERSION` is `"Lua 5.2"` on both and the pack's `allowBytecode=false` rules out `string.dump`, 04 §5, 10 F8) or a fast byte-buffer primitive (FFI is sandboxed)? Will the `Value.__gc` fix land? Could it release JNLua table proxies eagerly at the end of `Machine.invoke` (11 §5), which stock OC cannot? *Default: behavioural probe, pure-Lua JIT-friendly `string.char` encoder, integer handles only so `__gc` never matters, no table in the frame path on any runtime.*
9. **Input topology** (15): should right-clicking an OC keyboard block that touches an `opengpu_screen` open the OpenGPU GUI (needs a `PlayerInteractEvent` handler on OC's keyboard block)? Is an item-hosted display for robots/tablets wanted, or is Case/Server the permanent scope? `setPrecise` on every tier or T3-only like OC? *Default: yes, in M1; Case/Server for v1, item-hosted display not planned; every tier.*
10. **Build/project conventions**: `modGroup io.github.mindbound.opengpu`, published `-api` jar, a Scala 2.13 test-only ocelot subproject with a vendored assembled jar, CI on the GTNH shared workflow plus a Java 8 `:core` leg and (from M3) an aarch64 runner, the 06 bench sources moved into the repo, `runClient21` pinned to lwjgl3ify 3.0.37 (what GTNH 2.9.0-RC-2 ships; the shim is identical from 3.0.25, 14 §2.4) — OK? *Default: yes to all.*
11. **Raise the Lua-default mismatch with the GTNH OC fork?** The pack's `defaultLua53=false` is inert (5.3 is registered first, 10 F4); a one-line fork fix would make 5.2 the real default. OpenGPU's design does not depend on the answer (both are must-pass). *Default: not OpenGPU's business; mention it to the fork maintainers if convenient.*
