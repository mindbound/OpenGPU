## Summary

1. The cheapest correct display path on 1.7.10 is vanilla's own: one GL texture per display, updated with `glTexSubImage2D(GL_BGRA, GL_UNSIGNED_INT_8_8_8_8_REV)` from a Java `int[]` (what `DynamicTexture`/`TextureUtil.uploadTexture` do), drawn as a single fullbright quad from a `TileEntitySpecialRenderer`. Upload cost is bandwidth-trivial (640×480 RGBA at 20 Hz ≈ 25 MB/s); the real costs are CPU-side copies and the TESR being invoked up to twice per frame under Iris.
2. OC's `ScreenRenderer` is a good template for placement/culling/orientation/fade of a multi-block face; OC-GTNH deliberately renders it uncached every frame because display lists misbehave under Angelica.
3. Angelica creates a **core-profile, forward-compatible GL 3.3–4.6 context** and emulates all legacy GL (FFP, display lists, `glPushAttrib`, `GL_QUADS`) in software via a bytecode redirector. OpenGPU must only use GL calls that reach the driver through that redirector (normal mod code) and must assume that Celeritas classifies tile-entity render bounds per class on first sight and caches each instance's AABB, refreshing it only when the TE's coordinates, block or metadata change (never on chunk rebuild).
4. In Forge 1.7.10, custom-payload handlers (both `SimpleNetworkWrapper` and `FMLEventChannel`) run on the **main client/server thread**, not the Netty thread; packets are queued by `NetworkManager` and drained once per tick. Heavy decode must be moved *off* the main thread by hand, and results posted back with `Minecraft.func_152344_a`.
5. Real limits in stock Forge 10.13.4.1614: server→client custom payload ≤ 2,097,050 bytes (frame limit 2,097,151), client→server ≤ 32,766 bytes, no FML fragmentation, no protocol-level compression, Nagle enabled (`TCP_NODELAY=false`), ≤1001 packets processed per connection per tick. The installed GTNH-style instance changes three of these through Hodgepodge 2.7.216 and CoreTweaks 0.3.3.2: server→client payload/frame cap raised to 256 MiB, `TCP_NODELAY=true` on both sides, and the per-tick drain cap replaced by a 5 ms time budget. The client→server 32,766-byte cap is unpatched. Design for both envelopes; compress with `java.util.zip` yourself, as OC does.
6. Per-player bandwidth is the binding constraint: budget ~10–50 KB/s sustained per viewer. A 320×200 UI with tile-delta + palette + deflate fits in ~5–30 KB/s; a software-rendered 3D scene does not without aggressive caps (≤10 fps, ≤320×200, dithered 8-bit/lossy), so OpenGPU needs a subscription model (distance, per-viewer rate) rather than OC's "everyone watching the chunk" (OC's per-tick screen flush deliberately overrides the `(viewDistance+1)*16` default with a range of `maxWirelessRange(Tier.Two)²` — installed 512² = 262,144 blocks — so the only effective filter is chunk watching unless `misc.maxNetworkClientPacketDistance` is set; installed 0).

## Findings

### 1. Displaying a dynamic framebuffer on a block face

**Vanilla texture path [V].** `DynamicTexture(int w, int h)` allocates `int[w*h]` and calls `TextureUtil.allocateTexture` (`MC/net/minecraft/client/renderer/texture/DynamicTexture.java:26-32`); `updateDynamicTexture()` is `TextureUtil.uploadTexture(id, data, w, h)` (`:36-39`). `allocateTextureImpl` does `glTexImage2D(GL_TEXTURE_2D, level, GL_RGBA, w>>level, h>>level, 0, GL_BGRA, GL_UNSIGNED_INT_8_8_8_8_REV, null)` per mip level (`TextureUtil.java:202-227`). `uploadTexture` binds and calls `uploadTextureSub` (`:48-52`), which copies the `int[]` into a static 4,194,304-int (16 MiB) direct `IntBuffer` (`:24`, `:326-338`) in chunks of `4194304/width` rows and issues `glTexSubImage2D(..., GL_BGRA, GL_UNSIGNED_INT_8_8_8_8_REV, dataBuffer)` (`:174-189`). This format pair is byte-identical to Java ARGB ints on little-endian hosts and is the driver fast path. Note that these are GL 1.2 tokens (`GL12.GL_BGRA`, `GL12.GL_UNSIGNED_INT_8_8_8_8_REV`, `:187`, `:225`) used unconditionally, and that mipmapped allocations also set `GL12.GL_TEXTURE_MAX_LEVEL` and `GL14.GL_TEXTURE_LOD_BIAS` (`:217-220`), so the practical floor for this path is GL 1.2 packed pixels (plus GL 1.4 for the LOD bias), not bare GL 1.1 (see §5). Caveats: every upload re-applies min/mag filter and wrap (`:177-178`, `:307-319`, `:256-268`) and, if `gameSettings.anaglyph` is on, allocates and converts a full copy (`:330-333`). For OpenGPU, write your own uploader (same GL calls) that sets parameters once, uses a per-display direct buffer, and uploads only dirty rows/rectangles (`glTexSubImage2D` with x/y offsets).

**Cost model [I].** Bytes per full upload = W·H·4: 320×200 → 256,000 B; 640×400 → 1,024,000 B; 640×480 → 1,228,800 B. At 20 Hz: 5.1, 20.5, 24.6 MB/s; at 60 Hz: 15, 61, 74 MB/s. Any PCIe/iGPU link (≥ several GB/s) absorbs this. CPU-side: `IntBuffer.put(int[])` bulk copy ≈ 2–5 GB/s → 0.3–0.6 ms for 1.2 MB; palette→ARGB expansion ≈ 0.3–1 ns/px → 0.1–0.3 ms for 307k px; driver copy similar. The avoidable cost is a GPU sync stall when the texture updated this frame was sampled last frame; mitigate with two textures ping-ponged per display, or (optional, GL15) a `GL_PIXEL_UNPACK_BUFFER` with `GL_STREAM_DRAW` and `glTexSubImage2D(..., long offset)` (Angelica's GLSM maps that overload: `ANG/glsm/src/main/java/com/gtnewhorizons/angelica/glsm/GLStateManager.java:5316-5324`, but refuses it inside display lists).

**Formats [V/I].** Unsized `GL_RGBA` internal format (`TextureUtil.java:225`) is legal in core profile; `GL_LUMINANCE`/`GL_ALPHA` are not (GLSM promotes alpha formats, `GLStateManager.java:2005-2011`). For indexed/palette modes, expand to ARGB on the CPU (cheap, universal); a GPU palette lookup (R8 texture + 256×1 palette + fragment shader) needs `OpenGL20`/ARB shaders (§5) and is optional.

**Filtering/mipmaps [V/I].** Vanilla defaults to `GL_NEAREST`/`GL_NEAREST` without mipmaps (`TextureUtil.java:316-317`). OC uses `GL_NEAREST` mag and configurable min filter (`OC/client/renderer/font/DynamicFontRenderer.scala:109-114`; installed `textLinearFiltering=false`). For the 1:1 GUI use NEAREST. For the in-world face, minification aliasing is visible; use `GL_LINEAR_MIPMAP_LINEAR` min + NEAREST mag with mipmaps regenerated after each upload via `glGenerateMipmap` (EXT/ARB/GL30 FBO extensions, availability = `OpenGlHelper.framebufferSupported`, `MC/net/minecraft/client/renderer/OpenGlHelper.java:92`). Do not use vanilla's CPU `generateMipmapData` (per-channel `Math.pow`, `TextureUtil.java:104-163`). Under Angelica, GLSM auto-generates mipmaps after `glTexSubImage2D` when `GL_GENERATE_MIPMAP` is set on the texture (`GLStateManager.java:4287-4293`).

**TESR dispatch, culling, lighting [V].** `RenderGlobal.renderEntities` loops `tileEntities` and calls the dispatcher only if `tile.shouldRenderInPass(pass) && frustum.isBoundingBoxInFrustum(tile.getRenderBoundingBox())` (`MC/net/minecraft/client/renderer/RenderGlobal.java:534-541`; passes 0 and 1 come from `EntityRenderer.java:1300` and `:1413`). `TileEntityRendererDispatcher.renderTileEntity` then applies the distance cull `getDistanceFrom(cam) < getMaxRenderDistanceSquared()` (default 4096 = 64 m, `MC/net/minecraft/tileentity/TileEntity.java:193-196`), sets lightmap coords from the block's light, sets `glColor4f(1,1,1,1)`, and calls `renderTileEntityAt` with camera-relative coordinates (`TileEntityRendererDispatcher.java:117-127`). `getRenderBoundingBox` defaults to the block's collision box, else `INFINITE_EXTENT_AABB` (`TileEntity.java:399-420`) — so a custom multi-block box is required for correct culling. Only tile entities that have a special renderer and sit in chunk sections that were rebuilt get into the list (`MC/net/minecraft/client/renderer/WorldRenderer.java:187-195`). There is no batching: each TESR is immediate-mode. **This is the vanilla/Forge path only.** In the installed instance Angelica 2.2.21's Celeritas renderer replaces `RenderGlobal`'s loop and cannot be switched off (there is no `enableSodium`/`enableCeleritas` key in `AngelicaConfig.java` or `angelica-modules.cfg`): TESRs are collected per render section at chunk-mesh time, and the section's whole TESR list is skipped when the camera-to-section distance exceeds the **maximum `getMaxRenderDistanceSquared` captured when the chunk was meshed** (`ANG/src/main/java/com/gtnewhorizons/angelica/rendering/celeritas/AngelicaChunkBuilderMeshingTask.java:194-206`; `ANG/src/main/java/com/gtnewhorizons/angelica/rendering/celeritas/CeleritasWorldRenderer.java:454-460`; classes implementing `OverridesGetDistanceFrom` are treated as unbounded). Each surviving TE is then distance-checked live (`CeleritasWorldRenderer.java:481`) and frustum-tested against its cached per-instance AABB (`:532-540`, see "Angelica specifics" below). OC's pattern of returning 0 for non-origin blocks and 4096 for the origin is therefore only re-evaluated on chunk rebuild; OpenGPU's `getMaxRenderDistanceSquared` should be constant per class, or the design must re-mesh after merges. Angelica's `MixinTileEntity` also overwrites `TileEntity.getRenderBoundingBox` so that a null collision box yields the 1×1×1 block box rather than `INFINITE_EXTENT_AABB` (`ANG/src/mixin/java/com/gtnewhorizons/angelica/mixins/early/rendering/MixinTileEntity.java:35-47`), so the "else infinite" fallback above does not hold under Angelica. Fullbright: OC sets `OpenGlHelper.setLightmapTextureCoords(lightmapTexUnit, 0xFF, 0xFF)` and disables lighting (`OC/client/renderer/tileentity/ScreenRenderer.scala:64-66`); this also reads as emissive under Iris shader packs, which sample the lightmap.

**OC `ScreenRenderer` [V].** `renderTileEntityAt` (`ScreenRenderer.scala:40-101`): render only the multi-block origin (`:44-46`); distance cull `playerDistanceSq()/min(width,height) > maxScreenTextRenderDistance²` (`:48-51`; installed 20 m, fade from 15 m; `playerDistanceSq` is distance to the AABB, `:195-238`); back-face reject via the facing normal (`:55-58`); `glPushAttrib(GL_ALL_ATTRIB_BITS)`, fullbright, blend (`:62-66`); distance fade via `GL14.glBlendColor` + `GL_CONSTANT_ALPHA` when `GLContext.getCapabilities.OpenGL14` (`:34`, `:78-84`). `draw()` (`:147-193`) calls `transform()` which rotates by `yaw`/`pitch` (`:103-114`), translates to the bottom-left of the face and flips Y (`:117-121`), insets by the 2.25/16-block bezel (`:158-162`), aspect-fits the buffer with letterboxing (`:164-178`), and offsets z by 0.01 to avoid z-fighting (`:185`). Multi-block merging is deterministic on both sides (`OC/common/tileentity/Screen.scala:183-246`; client waits 40 ticks for chunk data, `:45`, `:261-264`; origin = lexicographically smallest, `:355-358`); after a merge the client calls `world.markBlockRangeForRenderUpdate` over the new bounds (`:218-221`); non-origin blocks return render distance 0 (`:331`); the origin's AABB is cached and spans the whole screen (`:313-328`). Registration: `ClientRegistry.bindTileEntitySpecialRenderer(classOf[tileentity.Screen], ScreenRenderer)` (`OC/client/Proxy.scala:75`).

**How OC draws text and when it re-renders [V].** `TextBufferRenderCache.render` regenerates glyphs only when dirty, then draws the whole buffer **every frame**; the comment says "Keep this uncached: display lists do not replay Tessellator vertex state reliably under Angelica" (`OC/client/renderer/TextBufferRenderCache.scala:16-31`; present since the fork's first commit f83bd95, 2026-07-29). Drawing is `TextureFontRenderer.drawBuffer` (`OC/client/renderer/font/TextureFontRenderer.scala:87-168`): background quads merged per run of equal color (`:101-123`), then one `Tessellator` batch per glyph atlas per row (`:135-160`), under `glPushAttrib(GL_ALL_ATTRIB_BITS)` (`:92`). Glyph atlases are 256×256 RGBA8 textures filled by `glTexSubImage2D` (`DynamicFontRenderer.scala:107-115`, `:152-153`). Dirty flags come from the client packet handlers via `ClientProxy.markDirty` (`OC/common/component/TextBuffer.scala:619-676`). Upstream 1.7.10 OC compiled a display list per buffer when dirty; the GTNH fork removed that [I, from the comment]. Lesson: a pixel display replaces O(chars) quads per frame with one quad plus an upload, which is cheaper on the draw side and shifts cost to the upload.

**OC holograms [V].** `HologramRenderer` is the other streamed-content TESR: it uses VBOs (`GL15.glBindBuffer/glBufferData`, `OC/client/renderer/tileentity/HologramRenderer.scala:233-238`), `glPushClientAttrib`/`glPushAttrib` (`:77-78`), additive blending and distance fade (`:79-85`), and has a fallback renderer registered when VBOs are unavailable (`OC/client/Proxy.scala:62-64`); render distance scales with hologram scale (`OC/common/tileentity/Hologram.scala:441`).

**Angelica specifics for TESRs [V].** With Celeritas, TESR visibility uses two caches that must not be conflated. (a) **Classification is per class:** `TileEntityRenderBoundsRegistry.classify` inspects `getRenderBoundingBox()` of the first instance seen and marks the whole class STATIC or INFINITE, unless the class name was registered DYNAMIC (config `dynamicBoundsTileEntities`, registered from `ClientProxy.java:130`, or `registerDynamicClass`) (`ANG/src/main/java/com/gtnewhorizons/angelica/rendering/TileEntityRenderBoundsRegistry.java:29-61`; the installed `angelica-modules.cfg:65-68` lists only the two OpenBlocks guide classes). (b) **The AABB itself is cached per instance:** `MixinTileEntity.angelica$getCachedRenderBoundingBox` returns the cached box as long as `xCoord/yCoord/zCoord`, `getBlockType()` and `getBlockMetadata()` equal the cached values, and recomputes it otherwise (`ANG/src/mixin/java/com/gtnewhorizons/angelica/mixins/early/rendering/MixinTileEntity.java:86-113`; the class verdict is cached per instance once, `:116-122`). It is never invalidated by chunk rebuilds or `markBlockRangeForRenderUpdate`. `CeleritasWorldRenderer.isTileEntityVisible` uses the live box only for DYNAMIC classes and the cached box for STATIC ones (`CeleritasWorldRenderer.java:532-540`). Consequence for a multi-block display whose origin AABB grows after merging (OC's pattern, same coords/block/meta before and after): the chunk-rebuild path does read the live box to decide global vs section-local placement (`AngelicaChunkBuilderMeshingTask.java:176`), so OC's `markBlockRangeForRenderUpdate` after merge (`OC/common/tileentity/Screen.scala:218-221`) fixes placement, but the frustum test keeps using the stale 1-block cached box unless the class is DYNAMIC. Returning a constant max-extent box from the first call is therefore required, not merely prudent. Iris renders tile entities again in the shadow pass (`ANG/src/main/java/net/coderbot/iris/pipeline/ShadowRenderer.java:748-817`; installed `cullShadowTileEntities=true`), and Angelica adds TESR batching mixins (`ANG/src/main/java/com/gtnewhorizons/angelica/mixins/Mixins.java:179-183`) and a retained TESR mesh API (`ANG/src/main/java/com/gtnewhorizons/angelica/api/tesr/`, `@API provides "angelica|tesr"`). Installed 2.2.12 notes "Fix tile entity pass markers skipped on newer class files" and "Fixes TESR texts (travel anchors) depth test bug" [W].

### 2. Fullscreen GUI with native resolution and input forwarding

**OC's GUI [V].** `gui.Screen` (`OC/client/gui/Screen.scala:10-124`) composes `traits.InputBuffer` (keyboard, `OC/client/gui/traits/InputBuffer.scala`) and `traits.DisplayBuffer` (layout, `DisplayBuffer.scala`). It is opened purely client-side from the block (`OC/common/block/Screen.scala:345-352`, `player.openGui` only when `world.isRemote`; GUI handler `OC/client/GuiHandler.scala:43-44`), so there is no server-side container; reach validation (8 blocks = `distanceSq <= 64` to any constituent screen block, `OC/common/component/TextBuffer.scala:403-412`) is applied server-side instead — but not uniformly: mouse, clipboard, drop-file, analyzer and init packets are reach-checked in `TextBuffer`/`PacketHandler`, whereas keyboard packets are forwarded unchecked and only reach-checked later inside the receiving keyboard component (see "Keyboard" below). `doesGuiPauseGame=false` (`InputBuffer.scala:36`) keeps the integrated server ticking. Layout: `changeSize` computes `scale = min(1, fit)` in *scaled GUI units* and centers (`Screen.scala:109-123`); the background bezel is a display list (`OC/client/renderer/gui/BufferRenderer.scala:199-258`) and the text is drawn through `buffer.renderText()` (`:260-268`).

**Keyboard [V].** `handleKeyboardInput` reads LWJGL `Keyboard.getEventKey/getEventCharacter/getEventKeyState` (`InputBuffer.scala:72-100`), enables repeat events in `initGui` (`:40`), excludes ESC and F11 (`:78`), tracks pressed keys to emit `keyUp` on close (`:64-70`), suppresses modifier auto-repeat (`:116-125`), and pastes with the OC keybinding or middle click via `GuiScreen.getClipboardString` (`:92-94`, `:102-114`). Packets: `sendKeyDown/Up(address, char, code)` (`OC/client/PacketSender.scala:177-195`); the server resolves the buffer by node address and calls `buffer.keyDown` **with no reach check** (`OC/server/PacketHandler.scala:189-207`; unchanged on GitHub master), and `ServerProxy.keyDown/keyUp` forward unconditionally as `keyboard.keyDown/keyUp` node messages to adjacent keyboards (`TextBuffer.scala:831-837`, `:909-916`; only `clipboard` and `dropFile` are reach-checked in `TextBuffer`, `:839-847`). The 8-block check for keys happens afterwards in the receiving keyboard component: `server/component/Keyboard.onMessage` calls `isUseableByPlayer(p)` (`OC/server/component/Keyboard.scala:66-91`, `distanceSq <= 64` measured from the **keyboard's** host position, with a `usableOverride` hook, `:137-139`) before it raises `key_down/key_up/clipboard` signals. For OpenGPU this means keyboard reach enforcement lives in whatever consumes `keyboard.*` messages; if the OC keyboard component is bypassed, the check must be reproduced there, not in the screen handler. Clipboard is chunked at 16 KiB with a cooldown (`client/PacketSender.scala:197-216`); the server re-checks size (`server/PacketHandler.scala:209-217`).

**Mouse [V].** `mouseClicked`/`mouseClickMove` (drag only if >10 ms since last, `Screen.scala:48-55`) go through `clickOrDrag` → `toBufferCoordinates` (`:72-91`), which converts scaled GUI coordinates to fractional character cells and sends a packet only when the cell (or half-cell vertically) changed (`:74-79`) — client-side drag coalescing. `mouseMovedOrUp` sends `mouseUp` (`:57-70`); wheel uses raw `Mouse.getEventX/Y` and `getEventDWheel` (`:25-37`). Packets: `MouseClickOrDrag(address, float x, float y, bool drag, byte button)`, `MouseScroll`, `MouseUp` (`client/PacketSender.scala:236-268`). Server side (`server/PacketHandler.scala:236-272`, NaN/Inf rejected via `isFinite`) → `ServerProxy.sendMouseEvent`, which returns early unless `isUseableByPlayer` (8 blocks, `TextBuffer.scala:887-888`), then emits `computer.checked_signal` with `("touch"|"drag"|"drop"|"scroll", x, y, button|delta[, playerName])`, integers `+1` or doubles in precise mode (`TextBuffer.scala:849-863`, `:887-907`). In-world clicks: `block.Screen.rightClick` sends a touch when the GUI is not opened (`OC/common/block/Screen.scala:353-357`), with the client computing display coordinates from the hit vector, bezel, and letterboxing (`OC/common/tileentity/Screen.scala:100-139`).

**What a pixel GUI needs [V/I].** `GuiScreen.width/height` are *scaled* units: `Minecraft.displayGuiScreen` sizes the screen with `ScaledResolution` (scale factor from `guiScale`, constrained to ≥320×240 logical, `MC/net/minecraft/client/gui/ScaledResolution.java:24-44`) and `EntityRenderer.setupOverlayRendering` sets `glOrtho(0, scaledW, scaledH, 0, 1000, 3000)` + translate z −2000 (`MC/net/minecraft/client/renderer/EntityRenderer.java:1739-1749`). To draw 1:1 pixels, `glScaled(1/scaleFactor, ...)` (or push your own projection) and center with integer magnification (1×/2×/3×) when the display fits. Mouse events delivered to `mouseClicked` are truncated to scaled ints (`GuiScreen.handleMouseInput`: `Mouse.getEventX()*width/displayWidth`, `MC/net/minecraft/client/gui/GuiScreen.java:329-333`), losing `scaleFactor` pixels of precision — override `handleMouseInput` and use physical `Mouse.getEventX()`/`displayHeight - getEventY() - 1` directly. Send pixel coordinates as u16 pairs; coalesce drags per changed pixel (or per N ms); keep OC's signal names and argument order so existing OpenOS/`event` code keeps working, and route keyboard through OC's keyboard component adjacency exactly as OC does rather than inventing a second keyboard path.

### 3. Forge 1.7.10 networking

**Channel types [V].** OC uses an event-driven channel: `NetworkRegistry.INSTANCE.newEventDrivenChannel("OpenComputers")` with `channel.register(PacketHandler)` on each side (`OC/common/Proxy.scala:95-96`, `OC/client/Proxy.scala:48`); handlers subscribe to `ClientCustomPacketEvent`/`ServerCustomPacketEvent` (`OC/client/PacketHandler.scala:33-35`, `OC/server/PacketHandler.scala:49-51`) and parse `e.packet.payload` with a `DataInputStream`; byte 0 is a compression flag that wraps an `InflaterInputStream` (`OC/common/PacketHandler.scala:305-333`), and the payload `ByteBuf` is released by hand because FML does not (`:321-324`, OC issue #3703). `SimpleNetworkWrapper` is the same embedded-channel machinery with a discriminator codec and `IMessageHandler` (`MC/cpw/mods/fml/common/network/simpleimpl/SimpleNetworkWrapper.java:85-93`, `:129-142`); either is fine, but OC's raw-stream approach avoids per-message object churn and allows one packet to carry many sub-commands (`TextBufferMulti`, parsed until `EOFException`, `OC/client/PacketHandler.scala:614-641`).

**Builders and compression [V].** `SimplePacketBuilder` vs `CompressedPacketBuilder` (`DeflaterOutputStream` with `Deflater.BEST_SPEED`), both producing `new FMLProxyPacket(Unpooled.wrappedBuffer(payload), "OpenComputers")` (`OC/common/PacketBuilder.scala:142-163`, header byte `:178-182`). Note `FMLProxyPacket.toS3FPacket` calls `payload.array()` (`MC/cpw/mods/fml/common/network/internal/FMLProxyPacket.java:132-135`), so payloads must be heap buffers.

**Targeting and ranges [V].** `sendToAllPlayers` → `channel.sendToAll` (`PacketBuilder.scala:68`). `sendToPlayersNearTileEntity` iterates `WorldServer.playerEntities`, requires `PlayerManager.isPlayerWatchingChunk(player, chunkX, chunkZ)` and distance ≤ `(viewDistance+1)*16` blocks, further capped by `misc.maxNetworkClientPacketDistance` if > 0 (`:79-102`; installed value 0 = off). `sendToNearbyPlayers` is dimension + Euclidean distance (`:104-121`). Text-buffer updates are flushed **once per tick** with an explicit range argument of `maxWirelessRange(Tier.Two)²` (`OC/common/component/TextBuffer.scala:158-161`): upstream default 400² = 160,000, but the installed `OpenComputers.cfg:879-882` has `maxWirelessRange=[16, 512]`, so the argument is 512² = 262,144 blocks, which `PacketBuilder.scala:91` squares again. The `(viewDistance+1)*16` default applies only when no range is passed (`PacketBuilder.scala:85`), so for screen traffic the only effective filters are `isPlayerWatchingChunk` and `misc.maxNetworkClientPacketDistance` when > 0 (installed 0 = off): every chunk watcher receives every tick's screen delta regardless of server view distance. Effects use `maxNetworkClientEffectPacketDistance` (installed 64). FML's own `TargetPoint`/`ALLAROUNDPOINT` only checks dimension and distance, not chunk watching (`MC/cpw/mods/fml/common/network/FMLOutboundHandler.java:176-210`).

**Batching and late joiners [V].** Server-side GPU calls (which run on OC worker threads) append sub-commands to a per-buffer `CompressedPacketBuilder` under `owner.synchronized` (`TextBuffer.scala:74-79`, `:739-829`); `update()` sends and resets it each tick (`:158-161`). Clients that load a screen request a full sync (`TextBufferInit`, `:432-437`, `:528-532`) and retry every 100 ticks until initialized (`:70-72`, `:163-169`, `:102-105`); the server answers only that player, only if they watch the host chunk and the block is the origin, with the full buffer as compressed NBT (`OC/server/PacketHandler.scala:38-44`, `:355-372`; `OC/server/PacketSender.scala:748-755`). Off-screen "VRAM" buffers are synced the same way (`TextBufferRamInit` NBT + `bitblt` commands, `PacketSender.scala:676-701`).

**Size limits in stock Forge 10.13.4.1614 [V].** Server→client `S3FPacketCustomPayload`: the Forge-patched constructor throws if payload > 0x1FFF9A = **2,097,050 bytes** ("Max size of ANY MC packet is 0x1FFFFF minus max size of this packet"), length is a Forge varshort (`MC/net/minecraft/network/play/server/S3FPacketCustomPayload.java:25-45`; `ByteBufUtils.readVarShort` = 15 bits + optional high byte, `MC/cpw/mods/fml/common/network/ByteBufUtils.java:64-89`); the transport frame is a ≤3-byte varint, "length wider than 21-bit" otherwise (`MC/net/minecraft/util/MessageDeserializer2.java:55`, `MessageSerializer2.java:17-19`), so 2,097,151 is the hard frame cap. Client→server `C17PacketCustomPayload`: constructor throws at ≥ 32767 and the reader only accepts `0 < len < 32767` → **≤ 32,766 bytes** (`MC/net/minecraft/network/play/client/C17PacketCustomPayload.java:28-57`; the file is 97 lines). Channel names ≤ 20 chars (`readStringFromBuffer(20)`, `:49`). FML 1.7.10 has **no multipart splitting** (no `FML|MP`; `FMLProxyPacket` only has `toS3FPacket`/`toC17Packet`, `FMLProxyPacket.java:127-135`). The "1048576" figure is the vanilla 1.8+ limit, not this build. 1.7.10 also has **no protocol compression** (the `NetworkManager.java:309` pipeline is timeout/splitter/decoder/prepender/encoder/packet_handler with no compression handler; the only `Deflater`/`Inflater` users under `MC/net/minecraft/network/` are the per-packet chunk compressors `S21PacketChunkData` and `S26PacketMapChunkBulk` plus `PacketBuffer`'s NBT helpers; `network-compression-threshold` arrived in 1.8).

**Size limits in the installed instance [V].** Hodgepodge 2.7.216 patches the server→client side: `hodgepodge.cfg:638` `increasePacketSizeLimit=true` and `:697` `packetSizeLimit=268435456` (256 MiB) drive the mixins `MixinS3FPacketCustomPayload_LengthLimit` (replaces the 0x1FFF9A constant in the `(String, byte[])` constructor with `FixesConfig.packetSizeLimit` and redirects `ByteBufUtils.readVarShort/writeVarShort` to `PacketSerializationHelper.readExtendedVarShortOrInt/writeExtendedVarShortOrInt`), `MixinMessageDeserializer2` and `MixinMessageSerializer2` (replace the 21-bit/3-byte frame constants), all in `mods/hodgepodge-2.7.216.jar` (verified via `javap`). So between Hodgepodge peers server→client custom payloads up to 256 MiB are accepted, and the 2,097,050-byte cap binds only for clients without Hodgepodge or with the option off. `C17PacketCustomPayload` is **not** patched: client→server stays ≤ 32,766 bytes everywhere.

**Transport behaviour [V].** Stock: `TCP_NODELAY=false` on both client and server sockets (`MC/net/minecraft/network/NetworkManager.java:303`, `MC/net/minecraft/network/NetworkSystem.java:89`): Nagle may hold small segments until the previous one is ACKed, so many tiny per-tick packets add latency; one ≥1–2 KB packet per display per tick is better. Each `scheduleOutboundPacket` is a `writeAndFlush` (`NetworkManager.java:148-201`). The receiver drains at most 1001 queued packets per connection per tick (`for (int i = 1000; !queue.isEmpty() && i >= 0; --i)`, `:238`). Installed instance: both are overridden. Hodgepodge `hodgepodge.cfg:1167` `tcpNoDelay=true` (`MixinTcpNoDelay` redirects `Boolean.valueOf` in both `ChannelInitializer.initChannel` bodies) and CoreTweaks `coretweaks.cfg:178-181` `tcp_no_delay` enabled force `TCP_NODELAY=true` on client and server; `hodgepodge.cfg:76` `changeReceivedPacketCountLimitToTimeLimit=true` with `:724` `receivedPacketTimeLimit=5000000` (`MixinNetworkManager_ReceivedProcessingLimit`) rewrites the `processReceivedPackets` loop into a 5 ms time budget per connection per tick. So on GTNH-style installs Nagle is off and the per-tick limit is processing time rather than a packet count; the "one coalesced packet per display per tick" recommendation still stands (it bounds work per tick and keeps deflate ratios high), but the Nagle rationale only applies to non-Hodgepodge peers.

**Bandwidth budget [W/I].** Vanilla 1.7.10 traffic per player is dominated by chunk data; a scraped measurement gives ≈31.6 KB/s mean with ≈159 KB/s bursts over 100 s [W, low confidence], and hosting guides budget on the order of 100–300 kbit/s per player. Treat **10–50 KB/s sustained per viewer** as the envelope OpenGPU may add without being the dominant consumer, with bursts (key-frames) ≤ ~200 KB. (The OC config's `maxNetworkPacketSize=8192` is the in-game modem packet size, `OC/Settings.scala:357`, unrelated to Forge packets.)

### 4. Delta/compressed framebuffer streaming

Let W×H be the resolution, b bytes per pixel in the wire representation (4 ARGB, 2 RGB565, 1 indexed-8, 0.5 indexed-4), T the tile edge (16), c the deflate ratio for the content, f the frame rate. Raw full frame R = W·H·b. Tile-delta frame bytes ≈ Σ_changed (4 + T²·b·c); bandwidth B = f × bytes/frame. Representative numbers at 320×200 (64,000 px, 260 tiles) [I]:

- Static UI with a blinking cursor or a few widget updates (1–4 tiles, indexed-8, c≈0.3): ≈0.1–0.3 KB/frame → **~2–6 KB/s at 20 fps**. The same with raw ARGB would be ~4 KB/frame → 80 KB/s, so palette or RGB565 plus deflate is mandatory.
- Full redraw of a flat-colour text UI (key-frame, indexed-8, c≈0.05–0.15): **3–10 KB** per key-frame.
- Scrolling text (every tile changes): 3–10 KB/frame → 60–200 KB/s at 20 fps. With a `copy(src→dst rect)` opcode (OC has `TextBufferMultiCopy`, `OC/server/PacketSender.scala:612-621`) the scroll costs ~12 bytes plus one new row of tiles (~1.5 KB) → **~30 KB/s at 20 fps, 15 KB/s at 10 fps**.
- Software 3D (noisy gradients): RGB565 c≈0.6–0.9 → ~90 KB/frame → 1.8 MB/s at 20 fps; indexed-8 with ordered dither c≈0.5 → ~32 KB/frame → 640 KB/s at 20 fps / 320 KB/s at 10 fps; 4-bit dithered ≈19 KB/frame → ~190 KB/s at 10 fps; a DXT1-style 0.5 B/px block code ≈ 26 KB/frame after deflate → ~260 KB/s at 10 fps. 640×400 is 4× all of the above. Conclusion: 3D output is only affordable for the local player/LAN or with adaptive quality (half-res mip for distant viewers, ≤10 fps, 8-bit dithered).

Techniques, in priority order: (1) keep only the latest state per tick on the server (dirty-tile bitmap + per-tile 64-bit hash) so wire cost is bounded by W·H per tick regardless of Lua call rate; (2) wire pixel format chosen per display mode (palette index when the mode is paletted, RGB565 for true-colour), optional RLE pre-pass, then `Deflater(BEST_SPEED)` over the whole per-tick packet as OC does; (3) opcodes for `fill`, `copy`, and blits of client-cached resources (sprites/fonts uploaded once, like OC VRAM `bitblt`) so 2D UIs mostly stream commands, not pixels; (4) key-frame on subscription, on explicit client request after chunk/TE reload, and periodically (e.g. every 10–30 s) for drift protection, with a 32-bit frame sequence so a client can detect loss and ask again; TCP ordering means deltas never arrive out of order on one connection; (5) rate caps: hard cap at 20 Hz (server tick), per-display fps config, per-viewer distance LOD (full-rate ≤ 16 m, half-rate/half-res to the render cap at 64 m, unsubscribed beyond) with hysteresis; (6) one packet per display per tick, ≤ ~64 KB typical, far below the 2 MB cap; any larger key-frame should be split by rows into several packets rather than relying on fragmentation that FML lacks.

### 5. GL capability baseline (Java 8 + LWJGL 2.9.4) and Angelica

`org.lwjgl.opengl.GLContext.getCapabilities()` returns a `ContextCapabilities` for the thread's current context (under lwjgl3ify the `org.lwjglx` shim returns one process-wide static snapshot instead, readable from any thread, 14 §2.2) with booleans `OpenGL11…OpenGL44` and `GL_ARB_*`/`GL_EXT_*` (used by OC: `ScreenRenderer.scala:34`, `OC/util/RenderState.scala:11`; by vanilla: `OpenGlHelper.initializeTextures`, `MC/net/minecraft/client/renderer/OpenGlHelper.java:72-199`, and the snooper, `Minecraft.java:2613`). It must be called on the render thread after the display is created, which on Forge happens in `net.minecraftforge.client.ForgeHooksClient.createDisplay()` (`Minecraft.java:473`; it calls `Display.create(new PixelFormat().withDepthBits(24))`, `MC/net/minecraftforge/client/ForgeHooksClient.java:318-330`, a default compatibility context); the bare `Display.create()` at `Minecraft.java:494` runs only in the `catch (LWJGLException)` fallback. `ForgeHooksClient.createDisplay` is the hook Angelica overwrites (below) [V]. Minecraft 1.7.10's own floor is GL 1.1 fixed-function plus multitexture (`GL13` or `ARB_multitexture`, `OpenGlHelper.java:75-88`) **plus the GL 1.2 pixel-format tokens that `TextureUtil` uses unconditionally** (`GL12.GL_BGRA`, `GL12.GL_UNSIGNED_INT_8_8_8_8_REV`, `GL12.GL_TEXTURE_MAX_LEVEL`, and `GL14.GL_TEXTURE_LOD_BIAS` for mipmapped textures, `TextureUtil.java:187`, `:217-220`, `:225`); everything else is optional and detected: `openGL14`/`EXT_blend_func_separate` (`:90-91`), FBOs via GL30/ARB/EXT (`framebufferSupported`, `:92-140`), shaders via `OpenGL21` or `ARB_shader_objects+ARB_vertex_shader+ARB_fragment_shader` (`:165-196`), `shadersSupported = framebufferSupported && shaders` (`:198`). VBOs (GL15) are assumed by OC's hologram renderer with a fallback (`OC/client/Proxy.scala:62-64`) [V].

**Angelica changes the context [V].** `MixinForgeHooksClient_CoreProfile.createDisplay` overwrites Forge's display creation and creates a **core-profile, forward-compatible** context with `ContextAttribs(…).withProfileCore(true).withForwardCompatible(true)`, probing from the platform maximum (4.6; 4.1 on macOS) down to 3.3 (or GL ES 3.2 when configured) (`ANG/src/mixin/java/com/gtnewhorizons/angelica/mixins/early/angelica/MixinForgeHooksClient_CoreProfile.java:63` builds `new ContextAttribs(3,3).withProfileCore(true).withForwardCompatible(true)`; `:77-78` platform max; `:99-110` probe loop). Version pinning is an optional config, not a recorded result: `pinnedGLVersion` (default 0 = auto-detect) is tried first only when ≥ 33, falling back to probing if it fails (`:84-97`; `ANG/src/main/java/com/gtnewhorizons/angelica/config/AngelicaConfig.java:422-431`, which also has `disableGLVersionPinning`). `RenderSystem` throws on a non-core context only when the context reports the `OpenGL32` capability: it reads `GL_CONTEXT_PROFILE_MASK`, enables FFP shader emulation for a core profile and otherwise throws "Non-core GL context … FFP emulation requires a core profile and nothing would render" (`ANG/glsm/src/main/java/com/gtnewhorizons/angelica/glsm/RenderSystem.java:174-184`). Consequently `glBegin`, display lists, the matrix stack, `glPushAttrib`, `GL_QUADS`, `GL_LUMINANCE` etc. do not exist at the driver; GLSM emulates them (README "Core Profile" section; `DisplayListManager` VBO-based display-list emulation; `GLStateManager.glPushAttrib/glPopAttrib` software stacks, `GLStateManager.java:3851-3880`). The emulation is reached by a bytecode redirector that rewrites `org/lwjgl/opengl/*` call sites to `GLStateManager` in every class passing through the Forge class loader (`ANG/glsm/src/main/java/com/gtnewhorizons/angelica/glsm/redirect/GLSMRedirector.java:36-96`; targets/exclusions in `ANG/glsm/src/main/java/com/gtnewhorizons/angelica/glsm/loading/EarlyRedirectorCore.java:30-50`); calls made via reflection, `MethodHandle`s or scripts bypass it and must self-redirect (`ANG/src/main/java/com/gtnewhorizons/angelica/api/GLRedirects.java` javadoc). GL functions GLSM does not map are, by default, logged once as "Unmapped GL call … on a non-GL backend this will crash at runtime" and still dispatched to LWJGL (`GLSMRedirector.java:74-79`, `:111-119`); the system property `angelica.unmappedGL` (default `WARN`; `OFF`/`WARN`/`FAIL`/`STRICT`, `ANG/glsm/src/main/java/com/gtnewhorizons/angelica/config/SystemProperties.java:26`, `:79-95`) can make them throw instead. The redirector also treats the LWJGL3 entry points `org/lwjgl/opengl/GL.getCapabilities/setCapabilities/getFunctionProvider/create` as "aware, non-dispatching" (`GLSMRedirector.java:85-96`), i.e. it expects both the LWJGL2 `GLContext.getCapabilities()` and the LWJGL3 `GL.getCapabilities()` API surfaces to exist in the wild. Texture uploads are mapped (`glBindTexture` `:1963-1990`, `glTexImage2D` `:2041-2117`, `glTexSubImage2D` `:5284-5324`) and recorded if issued inside a display list — never upload inside one. Installed 2.2.21 adds "Give each GL drawable its own GLSM context" (2.2.21), "Properly handle display lists with the push/pop optimizations" (2.2.19), "Render pass and state stack optimizations" (2.2.18), "Fix some GLSM bypasses" (2.2.14), and texture-filtering/mipmap fixes (2.2.15–2.2.17) [W].

**Implications for optional hardware acceleration [I].** The portable baseline is a CPU rasterizer → `int[]` → texture → one quad; it needs nothing beyond GL 1.2 (BGRA packed pixels) + multitexture and is what works on LWJGL2/Java 8, lwjgl3ify/Java 17–21, and Angelica alike. Capability probing (resolved by 14): the LWJGL2 API cited here (`GLContext.getCapabilities()`/`ContextCapabilities`) plus `OpenGlHelper` flags works on both legs — under lwjgl3ify the `LwjglRedirectTransformer` remaps `org/lwjgl/` to `org/lwjglx/`, whose `GLContext.getCapabilities()` returns a process-wide snapshot populated before any mod code runs, and Angelica's own GLSM reads that same object (14 §2.1-2.2, §2.5); the LWJGL3 names Angelica's redirector special-cases matter only for `@Lwjgl3Aware` classes. So: no per-LWJGL implementations, no `glGetString` branching; never mark OpenGPU classes `@Lwjgl3Aware` or the jar `Lwjgl3ify-Aware`; read only fields present in LWJGL 2.9.4, the shim and LWJGL 3.4.3 (14 §2.3, §2.7). A GPU path (GLSL vertex/fragment programs rendering to an FBO, or compute via image load/store) must gate on `shadersSupported`/`framebufferSupported`-equivalent checks on vanilla, and on Angelica must use only GLSM-mapped `GL20/GL30` calls, own all program/VAO/FBO state it touches, restore GLSM's expectations afterwards, and be tested against Iris (which rebinds programs around block-entity rendering). Make it a pluggable backend, default off under Angelica/Iris until validated.

### 6. Threading rules

**Client render thread == client tick thread [V].** `Minecraft.runGameLoop` runs `runTick()` then rendering on the same thread (`MC/net/minecraft/client/Minecraft.java:1008-1115`); the scheduled-task queue is drained at the start of `runTick` (`:1658-1669`) and fed by `func_152344_a(Runnable)`/`func_152343_a(Callable)` (`:2978-3009`) — the 1.7.10 equivalent of `addScheduledTask`. All GL calls, TESR/GUI drawing, and `Minecraft.theWorld/thePlayer` access belong there.

**Where packet handlers actually run [V].** FML's `NetworkDispatcher` is inserted *before* vanilla's `packet_handler` (`MC/cpw/mods/fml/common/network/handshake/NetworkDispatcher.java:120-124`). Its `channelRead0` runs on the Netty thread but only wraps `S3F`/`C17` custom payloads for registered channels into an `FMLProxyPacket` and forwards them (`:193-212`, `:289-294`, `:325-330`). Vanilla `NetworkManager.channelRead0` queues any non-priority packet in `receivedPacketsQueue` (`MC/net/minecraft/network/NetworkManager.java:118-131`; `Packet.hasPriority()` is false by default and `FMLProxyPacket` does not override it, `MC/net/minecraft/network/Packet.java:80-83`). The queue is drained by `processReceivedPackets` (`NetworkManager.java:221-248`), which is called on the **client main thread** from `PlayerControllerMP.updateController` (`MC/net/minecraft/client/multiplayer/PlayerControllerMP.java:317`, during `Minecraft.runTick`) and on the **server thread** from `NetworkSystem.networkTick` (`MC/net/minecraft/network/NetworkSystem.java:153-183`, called at `MC/net/minecraft/server/MinecraftServer.java:730`). `FMLProxyPacket.processPacket` then synchronously pushes the packet through the mod's embedded channel (`FMLProxyPacket.java:77-113`): codec `decode` → `IMessage.fromBytes` (`MC/cpw/mods/fml/common/network/FMLIndexedMessageToMessageCodec.java:65-77`) → `SimpleChannelHandlerWrapper.channelRead0` → `IMessageHandler.onMessage` (`MC/cpw/mods/fml/common/network/simpleimpl/SimpleChannelHandlerWrapper.java:270-280`), or `NetworkEventFiringHandler` → `FMLEventChannel.fireRead` → event bus (`MC/cpw/mods/fml/common/network/FMLEventChannel.java:98-110`). **So in Forge 1.7.10 both decoding and handling run on the main thread on both sides**; the "handlers run on the Netty thread" rule is true from 1.8 onward, where vanilla moved to immediate processing plus `PacketThreadUtil`. A Forge developer's forum statement corroborates this [W: "In 1.7.10 it is not needed, since the packet handler code already runs on the main thread"]. OC accordingly touches world objects directly in its handlers (`OC/client/PacketHandler.scala:586-612`).

**Consequences for OpenGPU [I].** (a) World/TE access in handlers is safe without scheduling. (b) The downside is that inflating and applying a frame happens inside the tick: ~2–5 ms to inflate ~1 MB plus delta application, per display, per tick. To keep the main thread light, the handler should only `payload.readBytes(...)` into a `byte[]` (then release the `ByteBuf`), enqueue it to a per-display decode worker, and let the worker produce the next `int[]` frame in a double buffer; the render thread swaps it in and uploads during the TESR (or once per frame in `RenderWorldLastEvent`, so the Iris shadow pass does not upload twice). Use `Minecraft.func_152344_a` only when a world-side effect is needed. (c) Server side has no scheduled-task API in 1.7.10; use `ServerTickEvent` with a synchronized queue as OC does (`OC/common/EventHandler.scala:82-90`, `:149-156`). Lua callbacks execute on OC worker threads (installed `computer.threads=4`), so the server-side framebuffer needs a lock or a copy-on-flush scheme; OC guards its pending command builder with `owner.synchronized` and even pauses computers before saving (`TextBuffer.scala:473-488`). (d) Encoding (hash, diff, deflate) can run on a server worker pool, but `FMLEventChannel`/`SimpleNetworkWrapper` `send*` set shared channel attributes before writing (`FMLEventChannel.java:135-140`) and are not thread-safe; either send from the server thread or hand the finished `FMLProxyPacket` directly to `player.playerNetServerHandler.netManager.scheduleOutboundPacket`, which is queue-based and executes the write on the event loop (`NetworkManager.java:148-201`; `NetworkDispatcher.write` converts to S3F, `NetworkDispatcher.java:429-437`) — the latter is verified by code reading (13 §1.5); the M0 runtime test is confirmation.

## Design implications for OpenGPU

1. **Display pipeline:** client keeps one `int[]` (ARGB) frame + one or two GL textures per display; upload with `GL_BGRA/GL_UNSIGNED_INT_8_8_8_8_REV` sub-rectangles once per rendered frame, parameters set once at allocation; draw one quad from a TESR modelled on `ScreenRenderer` (origin-only, bezel inset, aspect-fit, yaw/pitch transform, fullbright lightmap, back-face reject, distance fade), plus the same quad at 1:1 in a GUI that undoes `ScaledResolution`.
2. **Never use display lists or glPushAttrib(ALL) for the hot path;** save/restore only the state you change (texture binding, blend, depth mask, lighting). This is cheaper on vanilla and avoids GLSM emulation traps under Angelica.
3. **Report a constant, conservative render AABB** for the origin TE (max multi-block extent) from the very first `getRenderBoundingBox` call, and a `getMaxRenderDistanceSquared` that is constant per class, because under Angelica/Celeritas the class is classified STATIC/INFINITE/DYNAMIC from the first instance, each instance's AABB is cached and refreshed only when its coordinates, block or metadata change (never on chunk rebuild), and the section-level TESR cull uses the maximum render distance captured at mesh time; a box or distance that grows after a multi-block merge is not seen by the frustum test unless the class is registered DYNAMIC. Non-origin blocks should still return 0 distance, but note that under Celeritas that value is also captured at mesh time. Keep `renderTileEntityAt` idempotent and upload-free (it may run twice per frame with Iris).
4. **Networking model:** one event-driven channel; raw `DataOutputStream` packets with a compression flag byte; one packet per display per tick containing opcodes (`key`, `tiles`, `fill`, `copy`, `blit`, `palette`, `resolution`); heap `ByteBuf`s; explicit release on receive; server-side reach/visibility validation of every client packet; client-initiated full sync with retry, as OC does.
5. **Subscription instead of broadcast:** track viewers per display (chunk watcher ∧ distance ≤ render cap ∧ facing), send key-frames on (re)subscribe, apply per-viewer rate/LOD, and expose server-side caps (max fps, max bytes/s per player, max resolution) in config. Target ≤ 10–50 KB/s per viewer; fail soft by dropping frames, never by splitting into many small packets (on stock Forge: Nagle and the 1001-packet tick cap; on Hodgepodge/CoreTweaks installs Nagle is off and the cap is a 5 ms time budget, but many small packets still cost per-packet overhead and worse deflate ratios). State both size envelopes in the design: 2,097,050 B server→client on stock Forge vs 256 MiB with Hodgepodge, and 32,766 B client→server everywhere.
6. **Formats:** paletted modes (4/8-bit) and RGB565 on the wire, ARGB only on the client; dirty-tile hashing at 16×16; `Deflater(BEST_SPEED)`; scroll/copy opcodes so terminal-style UIs stay cheap; a client-side resource cache (sprites, fonts) with `bitblt` opcodes, following OC's VRAM precedent.
7. **Threads:** handlers on the main thread (1.7.10 reality) but decode on workers; render-thread-only GL; server framebuffer protected against OC worker threads; encoder may run on a worker but sends happen on the server thread.
8. **Capability probing:** a `GlCaps` singleton filled on the render thread after startup (LWJGL capability object + `OpenGlHelper` flags + an "Angelica present / core profile" flag read from `GL_CONTEXT_PROFILE_MASK` or Angelica's presence) selecting the CPU baseline by default and enabling GPU backends only when all required features are present. The same LWJGL2 `GLContext.getCapabilities()`/`ContextCapabilities` code serves Java 8 and lwjgl3ify (Java 17–21), where lwjgl3ify's `org.lwjglx` shim supplies a process-wide snapshot (14 §2.2): one final class, no interface with per-LWJGL-major implementations, no `glGetString(GL_VERSION)`/`GL_MAJOR_VERSION` branching (log the strings only); never `@Lwjgl3Aware`, never `Lwjgl3ify-Aware: true` in the manifest, and read only fields present in LWJGL 2.9.4, the shim and LWJGL 3.4.3 (14 §2.3, §2.7, §3).
