Researcher note: written 2026-10-08. Local checkouts cited as `path:line`. Scratchpad clones (shallow, read-only) live under `C:\Users\astro\AppData\Local\Temp\claude\C--Users-astro-Downloads-OpenGPU\170a14cc-5cc1-40e0-a7ec-6130b748eabf\scratchpad\<name>` and are cited as `<name>/path:line`. Confidence tags: [V] verified in source/bytecode, [D] documentation or README only, [I] inference.

## Summary

1. Every display mod that works in multiplayer keeps a **client-side mirror** of display state and ships **commands or deltas**, never raw frames: OC batches all GPU ops of a tick into one Deflate-compressed `TextBufferMulti` packet; OC VRAM `bitblt` sends only a rectangle plus buffer id when the page is clean (a page modified since its last screen blit is re-shipped in full as NBT in the same batch); Plethora sends only dirty objects per tick; OCLights2 replays the draw-command list on the client; OC2 ships H.264 P-frames with keyframes under a byte budget.
2. The two naive designs (OpenGlasses: one full-widget packet per mutation, outside OC's call budget; VM Computers: one PNG per frame) are the anti-patterns, but the "32,767-byte payload limit" they are associated with is the **client->server** cap (`C17PacketCustomPayload`); on MC 1.7.10 the server->client `S3FPacketCustomPayload` cap is 1,048,576 bytes only in the unpatched vanilla class: Forge 10.13.4.1614 binpatches it to 2,097,050 bytes, and the installed Hodgepodge 2.7.216 raises it to 256 MiB (`packetSizeLimit=268435456`), while client->server stays at 32,766/32,767 [V, 00 §5, 03 §3, 07 §1, 13 §3]. The OpenGlasses crash report is from the 1.12 codebase and VM Computers' cap guards a client upload. OC's own screen batches are unchunked Deflate `FMLProxyPacket`s; OCLights2 chunks its GZIP stream; OC-GTNH 1.12.58+ chunks client->server `DropFile` uploads at 31 KiB. OpenGPU needs chunking for client->server uploads over 32 KiB and for any server->client payload over the stock Forge cap of 2,097,050 bytes (03 §3's 256 KB per-packet soft limit is the design rule regardless), not routinely at 32 KB.
3. Only OC2 (160 KiB/s server-wide budget, per-tick replenish) and CC:Tweaked (1 MB/tick pre-compression) implement an explicit bandwidth budget. OC instead throttles through Lua call budgets, charged only when pixels reach the screen (`set` = 1/256 of a tick on T3; writes into VRAM pages are budget-free; a dirty full-screen bitblt costs 2.0 against a 1.5 T3 credit, which throws `LimitReachedException` once and then proceeds without a pause).
4. Resolutions people actually use: OC text 160x50 (semi-pixels 160x100, braille 320x200 two-colour), CC drawing-chars up to 328x243 in 16 colours, CraftOS-PC 306x171 in 256 colours, OCLights2 256x144 / 512x288, CCLights2 (current master) 64 px/block in walls up to 16x9 blocks (1024x576 derived, px/block configurable), CC-DirectGPU ~656x324, OC2 640x480 RGB565. A 320x200 to 640x480 target is the consensus band.
5. Rendering on the 1.7.10 client is fixed-function everywhere (Tessellator quads, `glVertex3f`, `DynamicTexture` + `glTexSubImage2D`); GTNH OC draws its text buffer uncached each frame with a comment blaming display lists under Angelica, but its robot and GUI renderers still use display lists and the installed Angelica 2.2.21 ships a display-list emulation, so how fragile display lists are today is unverified. A framebuffer-as-texture (dirty-rect `glTexSubImage2D`) is the Angelica-safest path; CC:Tweaked's TBO shader and OC2's depth-projection shader are modern-GL designs to borrow ideas from, not code.
6. Deterministic replay is the only way to let clients rasterize while the server answers `getPixel`: CCLights2 (current master, MC 1.20.1, pushed 2026-09-26) compiles a GLSL subset to a register program interpreted deterministically on the server and every client (~10 ns/op/pixel, README figure), which is the closest existing analogue to OpenGPU's shader-to-bytecode plan.
7. Ocelot-brain already implements OC's VRAM/bitblt and hologram, so an OpenGPU core that is a pure-JVM library (no MC dependency) can be plugged into both OC-GTNH and the emulator.

## Findings

### 1. OpenComputers GTNH fork: text buffer, VRAM/bitblt, hologram

Scope: checkout `C:\Users\astro\Downloads\OpenComputers-GTNH` at f83bd95 (2026-07-30, ~1.12.55). Installed jar is 1.12.64-GTNH. A diff of the checkout against master (`ocgtnh-master`, 1e4559f = 1.12.64) shows no change to `GraphicsCard`, `GpuTextBuffer`, `TextBuffer`'s screen path or `PacketBuilder` [V], so the checkout is representative for GPU/screen/packets. It is not representative for the `TextBuffer` API: 1.12.58 (#216) changed `li.cil.oc.api.internal.TextBuffer.dropFile(String, String, EntityPlayer)` to `dropFile(String, byte[], EntityPlayer)` (`api/internal/TextBuffer.java:593`, matched by `javap` of the installed jar) and added chunked client->server `DropFile` packets (`client/PacketSender.scala:98-109`: Deflate BEST_SPEED, `grouped(31*1024)` chunks with Start/Chunk/End flags; `server/DropFileManager.scala` with per-player rate limiting) [V]; 1.12.60 changed AFK handling in `common/PacketHandler.scala`. Any OpenGPU class implementing `api.internal.TextBuffer` must target the 1.12.58+ signature, and OC itself now contains a chunked-transfer precedent.

**Screen model.** Tiers are 50x16 / 80x25 / 160x50 characters at 1/4/8-bit colour depth (`src/main/scala/li/cil/oc/Settings.scala:525-526`). A screen is a `TextBuffer` component with a `ServerProxy`/`ClientProxy` pair (`src/main/scala/li/cil/oc/common/component/TextBuffer.scala:95-97`).

**Transfer.** Every mutation appends a sub-command to `pendingCommands`, a `CompressedPacketBuilder(PacketType.TextBufferMulti)` (`TextBuffer.scala:74-78`, `:742-828`), flushed once per tick in `update()` (`TextBuffer.scala:157-160`). `CompressedPacketBuilder` wraps a `DeflaterOutputStream` at `Deflater.BEST_SPEED` (`src/main/scala/li/cil/oc/common/PacketBuilder.scala:153`). Recipients are players watching the chunk (`isPlayerWatchingChunk`, `PacketBuilder.scala:95`) within range; the range argument passed is `maxWirelessRange(T2)^2` (`TextBuffer.scala:159`), which is 262,144 with the installed config (`maxWirelessRange=[16,512]`, `OpenComputers.cfg:879-882`; 160,000 at the default `[16,400]`, `application.conf:1312`) and is then squared again (`PacketBuilder.scala:91`), so in practice every chunk watcher receives every screen update [V]. The one clamp is `misc.maxNetworkClientPacketDistance` (`PacketBuilder.scala:87-90`), applied to every OC server->client packet radius; it is 0 = disabled in the installed config (`OpenComputers.cfg:830`, default 0) but a server that sets it silently cuts screen updates beyond that distance. `maxNetworkPacketSize` (8192 in the user's config) applies only to Lua-level network-card packets (`src/main/scala/li/cil/oc/server/network/Network.scala:586-587`), not to Forge packets.

**Call budgets.** Direct callbacks that target the screen consume budget: `set` 1/64, 1/128, 1/256 per call by GPU tier, `fill` 1/32..1/128, `copy` 1/16..1/64 (`src/main/scala/li/cil/oc/server/component/GraphicsCard.scala:64-69`). The `set` cost is per call irrespective of string length; only energy scales with length (`GraphicsCard.scala:482-489`). Crucially, `resolveInvokeCosts` (`GraphicsCard.scala:100-107`) calls `consumeCallBudget`/`consumePower` only when the active buffer index is `RESERVED_SCREEN_INDEX`; when a VRAM page is the active buffer, `set`/`fill`/`copy`/colour changes return without consuming any budget or energy (the generic direct-call charge from `Machine.invoke` is 1/`Integer.MAX_VALUE`, `api/machine/Callback.java:88`), so OC's real throttle is "pay when pixels reach the screen" via the bitblt cost below [V]. Budgets per tier default to 0.5/1.0/1.5 (`src/main/resources/application.conf:162-166`); the user's instance raises them to 1/2/4 (`C:\Games\Minecraft\instances\Main\minecraft\config\OpenComputers.cfg:143-147`). The machine's budget is the average of the `CallBudget` values of all budget-providing components (CPU and memory items), not the CPU alone (`src/main/scala/li/cil/oc/server/machine/Machine.scala:123-126`); `consumeCallBudget` throws `LimitReachedException` when a single cost exceeds the remaining budget (`Machine.scala:286-293`). So a T3 GPU in an all-T3 machine can issue 384 screen-targeted `gpu.set` calls per tick at defaults (1024 with the user's config), and arbitrarily many into a VRAM page; a full 160x50 repaint as 50 row-strings costs ~0.2 budget. The throughput ceiling for Lua-side pixel pushing is therefore Lua string assembly and the 20 Hz tick, not the budget [I].

**VRAM buffers (GTNH-specific, also in upstream 1.8).** `allocateBuffer(w,h)` creates a `GpuTextBuffer` page bounded by `totalVRAM = maxResolution * vramSizes(tier)` (`GraphicsCard.scala:74`, `:135-153`; `vramSizes` default `[1,2,3]`, user config `[1,2,4]`, `OpenComputers.cfg:521-525`). `bitblt` between pages is free; a *clean* page blitted to the screen costs 0.001; a *dirty* page blitted to the screen costs `bitbltCost * 2^tier * (area/maxArea)` with `bitbltCost = 0.5` (`GraphicsCard.scala:70-73`, `:197-208`; the source comment explains the dirty cost as "a single bitblt can send a screen of data"). Against a tier credit of `(tier+1)*0.5`, a full dirty T3 page (2.0 > 1.5) throws `LimitReachedException` once; on the retry (`budgetExhausted` set) the cost is zeroed and the machine is paused only if `overBudget > tierCredit`, i.e. only when the page is larger than 1.5x the screen (`GraphicsCard.scala:229-249`). For a full-size page the pause branch is unreachable at any tier at the default `bitbltCost`: T3 overBudget is 0.5 < 1.5, and T1/T2 full pages (0.5, 1.0) exactly equal their credit and never throw. With the user's `vramSizes[2]=4`, a 4x-screen dirty T3 page costs 8.0 and pauses `((6.5-1.5)/1.5)/20` = 0.217 s [V]. Client-side, the page is mirrored, but **not** uploaded only once: every page->screen `bitblt` calls `dstScreen.addBuffer(srcRam)` (`src/main/scala/li/cil/oc/common/component/GpuTextBuffer.scala:169-170`), which fires `onBufferRamInit` whenever the page is new to that screen *or* `ram.dirty` is set (`common/component/traits/VideoRamRasterizer.scala:24-28`); the `ServerProxy` then serialises the whole page with `ram.save(nbt)` (clearing `dirty`, `GpuTextBuffer.scala:39-42`) and appends a `TextBufferRamInit` carrying the full NBT (`common/component/TextBuffer.scala:799-804`, `src/main/scala/li/cil/oc/server/PacketSender.scala:689-695`), followed by the `TextBufferBitBlt` that carries only `col,row,w,h,owner,id,fromCol,fromRow` (`PacketSender.scala:676-687`). Any `set`/`fill`/`copy`/colour change or VRAM-to-VRAM blit marks the page dirty again (`GpuTextBuffer.scala:28-32`, `:177`), so each mutate-then-blit cycle re-sends the full page plus the rectangle in the same per-tick `TextBufferMulti` batch; only blits of unmodified pages go by reference, and the client applies them locally (`GpuTextBuffer.scala:72-80`) [V]. Pages persist to NBT via `GraphicsCard.save/load` (`GraphicsCard.scala:618-670`, `NBT_PAGES`) using the per-page helpers (`GpuTextBuffer.scala:34-43`); a loaded page starts dirty so it is re-shipped on first blit. Ocelot-brain implements the same (`C:\Users\astro\Downloads\ocelot-brain\src\main\scala\totoro\ocelot\brain\entity\traits\GenericGPU.scala:63-67`).

**Client rendering.** `TextBufferRenderCache.render` regenerates glyphs for dirty lines and draws the buffer uncached every frame, with the comment "display lists do not replay Tessellator vertex state reliably under Angelica" (`src/main/scala/li/cil/oc/client/renderer/TextBufferRenderCache.scala:27`). `drawBuffer` merges same-background runs into quads, then draws glyph quads (`src/main/scala/li/cil/oc/client/renderer/font/TextureFontRenderer.scala:38-78`); glyphs live in a dynamic atlas updated with `glTexSubImage2D` per new character (`font/DynamicFontRenderer.scala:107-153`). Text stops rendering beyond `maxScreenTextRenderDistance` 20 blocks (`application.conf:26`, user config `:89`). The font (`src/main/resources/assets/opencomputers/font.hex`) contains all 256 braille glyphs U+2800..U+28FF [V], which is what makes 2x4 "braille mode" possible from Lua.

**Hologram projector.** Volume is 48x48x32 voxels with 2-bit colour (T1 one colour, T2 a 3-entry palette), stored as two `Int` bit-columns per (x,z) (`src/main/scala/li/cil/oc/common/tileentity/Hologram.scala:36-61`, `:99-113`). Dirty columns are tracked; each tick the server sends either the dirty bounding area or the individual dirty columns, choosing by a byte-cost comparison (`changes > 0.8 * area`) (`Hologram.scala:396-418`), both as compressed packets (`PacketSender.scala:243-277`). `setRaw` (bulk upload) forces a 0.2 s pause, documented as a worst case of ~30 KB/s/client (`application.conf:1227-1234`). The client pre-generates a static VBO containing every possible face (48*48*32*6 quads, interleaved T2F_N3F_V3F, `GL_STATIC_DRAW`) once; on change it rebuilds and re-uploads a second per-hologram buffer (`dataBuffer`, `w*w*h*6*4*2` ints) that holds **both** a per-vertex colour array (read via `glColorPointer(3, GL_UNSIGNED_BYTE, 4, 0)`) and the index list of visible faces, with one `glBufferData(GL_DYNAMIC_DRAW)`, and draws with `glDrawElements(GL_QUADS, ..., indexOffset)` (`src/main/scala/li/cil/oc/client/renderer/tileentity/HologramRenderer.scala:165-180`, `:255-335`, `:343-355`) [V]. The draw path is fixed-function client-state arrays (`glEnableClientState`, `glInterleavedArrays`, `glColorPointer`), not a shader-era VBO pipeline. This is the only `GL15`/VBO/`glDrawElements` user in OC-GTNH (grep over `src/main/scala`) [V]; whether it is exercised and correct under the installed Angelica 2.2.21 was not verified here (unverified [I]; nothing in the checkout or the Angelica repo was cited for it).

### 2. OpenGlasses 1.6.9-GTNH (GTNH source, installed jar)

Source: `GTNewHorizons/OCGlasses` (`OCG/`, tag 1.6.9-GTNH = bb1a1bb, 2026-08-11). The first pass missed it because it is a GitHub fork named OCGlasses [V]. It is upstream `master` (98d4e3b, 2015, the 1.7.10 line; the earlier clone took upstream's default 1.12.2 branch `OG2-MC1.12.2`) plus 45 GTNH commits since 2020-10-27, and the installed jar matches the tag (same classes plus the generated `OCGlassesTags`, `VERSION = "1.6.9-GTNH"`) [V]. Licence MIT (`OCG/LICENSE:1`); upstream's zlib licence covers only `OG2-MC1.12.2` [V]. Maintained by GTNH.

**Architecture (retained scene graph).** `OpenGlassesTerminalTileEntity extends TileEntityEnvironment` holds `HashMap<Integer, Widget> widgetList` and exposes `direct = true` callbacks with no `limit`: `addRect, addDot, addItem, addTextLabel, addTriangle, addQuad` (HUD), `addCube3D, addDot3D, addLine3D, addTriangle3D, addQuad3D, addFloatingText` (world), `removeObject, removeAll, getObjectCount, getBindPlayers, newUniqueKey`; Computronics adds `sendChatAs, sendMessageTo`, which are not direct (`OCG/…/tileentity/OpenGlassesTerminalTileEntity.java:49-302`) [V]. Each `add*` returns a table of `luafunction` objects (`SetColor, SetAlpha, SetPosition(3D), SetSize, SetScale, SetRotation, SetText, SetVertex, SetVisible, SetVisibleThroughObjects, SetViewDistance, SetLookingAt, SetItem` and getters), each an OC `Value` userdata (`OCG/…/surface/Widget.java:47-60`, `lua/LuaFunction.java:11`). OC calls userdata through `udinvoke` with no call-budget charge (OC-GTNH `src/main/resources/assets/opencomputers/lua/machine.lua:1105-1122`), and `add*` cost the default 1/`Integer.MAX_VALUE` (`src/main/java/li/cil/oc/api/machine/Callback.java:88`, charged at `src/main/scala/li/cil/oc/server/machine/Machine.scala:389-391`), so only Lua speed throttles widget traffic [V].

**Transfer.** `addWidget` and `updateWidget(int)` (called by every setter, e.g. `SetColor.java:18`) build a `WidgetUpdatePacket(id, widget)` with the widget's full state and send it at once through `ServerSurface.sendToUUID` to every player bound to the terminal, with no range or dimension check (`OpenGlassesTerminalTileEntity.java:312-323`, `OCG/…/surface/ServerSurface.java:137-158`) [V], from the machine's worker thread, i.e. exposed to the off-thread `sendTo` race of 13 §1 [I]. The packet is `action, count`, then per widget `type, Widget.write, id`, in an uncompressed `ByteBuf` (`OCG/…/network/packet/WidgetUpdatePacket.java:69-112`, `network/Packet.java:33-35`); the base class creates a Gson per packet but never uses it [V]. There is no batching, delta or compression, so a program that mutates many widgets per tick emits one packet per mutation per bound player. Only the full-list sync on equip grows with the scene (`ServerSurface.java:127-130`; 41 bytes per rectangle, so Forge's 2,097,050-byte cap needs about 51,000) [I]. The related upstream bug "Payload may not be larger than 32767 bytes" when many widgets are added from a geolyzer scan (Starchasers/OCGlasses#92, still open) is against OpenGlasses 2.2-50 on MC 1.12 / Forge 14.23.5.2847, a different codebase (OG2 branch), and 32,767 bytes is the client->server custom-payload cap; on MC 1.7.10 the server->client `S3FPacketCustomPayload` limit is 2,097,050 bytes under Forge 10.13.4.1614's binpatch (1,048,576 only in the unpatched vanilla class) and 256 MiB with the installed Hodgepodge 2.7.216 [V, 00 §5, 03 §3]. It is therefore not evidence of a server->client widget-packet limit in 1.6.9-GTNH; the per-mutation, unthrottled, uncompressed packet pattern is the problem in its own right [D/I].

**Rendering.** `ClientSurface` draws `renderables` in `RenderGameOverlayEvent.Post` for `HELMET` and `renderablesWorld` in `RenderWorldLastEvent` relative to `renderViewEntity` (GTNH #26), with lighting off, blend on and depth writes off, then forced back rather than restored (`OCG/…/surface/ClientSurface.java:68-113`) [V]. HUD shape widgets draw one `Tessellator` batch each (`face/Quad.java:47-63`; text uses `FontRenderer` at z=100, items `RenderItem`); world widgets use raw `glBegin/glEnd` (`Cube3D$RenderCube3D`: 24 `glVertex3f` inside `glPushMatrix/glScalef`, `world/Cube3D.java:123-158`) [V]. Pure fixed-function immediate mode, with no display lists, VBOs or Angelica-specific code [V]. The only `glPushAttrib` is GTNH #21's fix for a "black screen" left by item widgets (reproduced with Thaumcraft warp effects): `GL_ENABLE_BIT | GL_LIGHTING_BIT | GL_DEPTH_BUFFER_BIT` around `RenderItem.renderItemAndEffectIntoGUI` (`OCG/…/utils/RenderUtils.java:33-37`) [V]. A mixin (`MinecraftResizeMixin`, GTNH #22) reports the GUI-scaled size (`ScaledResolution`) to the server (`ScreenResizePacket`, Lua signal `glasses_resized`), so HUD coordinates are scaled GUI pixels, not window pixels (`OCG/…/mixins/early/minecraft/MinecraftResizeMixin.java:26-42`) [V].

### 3. OCLights2 / CCLights2

**OCLights2** (`BlueAmulet/OCLights2`, fork of `ds84182/CCLights2`; MC 1.7.10, Forge 10.13.2.1291, version 0.4.5; Minecraft Mod Public License 1.0.1; last commit 2020-01-17) [V `oclights2/build.gradle`, `LICENSE.md`]. Unmaintained.

- API: `TileEntityGPU` exposes `@Callback(direct=true)` `fill, plot, line, rectangle, filledRectangle, triangle, filledTriangle, oval, drawText, createTexture, bindTexture, drawTexture, freeTexture, setPixels, import/export (PNG), blur, translate, rotate, scale, push, pop, startFrame, endFrame, getPixelColor, getFreeMemory...` (`oclights2/src/main/java/ds/mods/OCLights2/CommandEnum.java`, `block/tileentity/TileEntityGPU.java:119-350`). Texture handles are integer ids; VRAM is `new GPU(1024*8)` units with a texture costing `w*h/32` (`TileEntityGPU.java:68`; upstream README).
- Execution: every call builds a `DrawCMD`, executes it **on the server** into a `java.awt.image.BufferedImage` via Graphics2D with an `AffineTransform` stack (`gpu/GPU.java:69-80`, `:287-330`) so `getPixelColor` can answer, and appends it to a send list.
- Transfer: `updateEntity` flushes the send list every tick unless inside `startFrame/endFrame` (`TileEntityGPU.java:876-885`). `PacketSenders.sendPacketsNow` serializes `cmd ordinal + typed args`, GZIPs and splits into chunks of `Short.MAX_VALUE-100` bytes with a (packetId, index, count) header (`network/PacketSenders.java:37-82`, `network/PacketChunker.java:31-64`), and broadcasts with `sendToAllAround(..., 4096.0)` blocks, i.e. effectively the whole dimension.
- Client: `ClientDrawThread` replays the commands into a client `GPU`/`Texture` BufferedImage on a background thread, polling every 1 ms (`ClientDrawThread.java:12-66`); `Texture.texUpdate` copies to an `int[]` and the TE renderer / GUI uploads it with `TextureUtil.uploadTexture` into a 512x288 `DynamicTexture` (`gpu/Texture.java:595-602`, `client/render/TileEntityExternalMonitorRenderer.java:35,85`).
- Resolutions: monitor 256x144 (GUI only), external monitor 32 px per block tiled (`TileEntityMonitor.java:31`, `TileEntityExternalMonitor.java:137`), tablet transceiver 512x288 (`TileEntityTTrans.java:32`).

**CCLights2 upstream** (`ds84182/CCLights2`, created 2013-03-26, pushed 2026-09-26) now targets MC 1.20.1 / CC:Tweaked 1.120.2 per its README (fetched 2026-10-08); the README does not describe itself as a rewrite or give a date for the change [D]. Relevant features: a **GLSL-subset shader language** (Shadertoy `mainImage` or WebGL1 `main`; float/int/vec/mat/struct/arrays/loops; no bitwise, no derivatives) "compiled once to a small register program" and "interpreted per pixel, on the server and on every client (deterministically, so all players see the same picture)" at "roughly 10 ns per instruction per pixel", bounded per call by `shaderMaxOpsPerPixel` and `shaderMaxPixels` (no defaults given); `startFrame()/endFrame()` "batch commands so clients receive them at once"; external monitors add "64 pixels (configurable)" per block in walls "up to 16x9 blocks" (1024x576 is this report's derived figure, 16*64 x 9*64, and changes with the px/block setting); blend modes, clipping, PNG/JPEG/GIF import [D]. Original 2013 forum post: 1/2/4 bpp modes, "all rendering happens on both the server and the client", "programs must sleep after rendering" [D]. License: none stated (GitHub API `license` = NOASSERTION).

### 4. Plethora (CC, 1.12.2) overlay glasses canvas

`SquidDev-CC/plethora` 3c9b415 (2021-08-06), MIT. Per-player `CanvasServer` holds `Int2ObjectMap<BaseObject>` plus parent/child sets; objects carry `id, parent, type, dirty` (`plethora/src/main/java/org/squiddev/plethora/gameplay/modules/glasses/BaseObject.java:13-20`, `CanvasServer.java:22-37`). Lua API is retained objects: `addRectangle, addLine, addDot, addText, addTriangle, addPolygon, addLines, addItem, addGroup, getSize` on the 2D canvas and `create, addFrame, addBox, addLine, addItem` on 3D (`methods/MethodsCanvas2D.java:27-186`, `MethodsCanvas3D.java:27-108`), all `worldThread=false` (run off the server thread). Sync: on every server tick START, `getUpdateMessage()` collects objects whose `pollDirty()` is true plus removed ids into one `MessageCanvasUpdate` unicast to the owning player (`CanvasHandler.java:90-100`, `CanvasServer.java:81-101`); a full `MessageCanvasAdd` is sent on attach. ### 5. CC:Tweaked monitors (MPL-2.0, mc-1.20.x/1.21)

Transfer: `NetworkedTerminal.write()` produces a `TerminalState` whose `contents` is 2 bytes per cell (char byte, then `bg<<4|fg`) plus a 16x3-byte palette; an 80x25 terminal is ~4 KB, a maximal 8x6-block monitor at text scale 0.5 (164x81 cells) ~26 KB, matching the config comment "a full-sized monitor sends about 25 KB" [D, fetched source]. `MonitorBlockEntity` enqueues itself when `serverMonitor.pollTerminalChanged()`; `MonitorWatcher.onTick` drains the queue, sending `MonitorClientMessage` to all players tracking the chunk and subtracting `state.size()` from `Config.monitorBandwidth` (default 1,000,000 bytes per tick, "measured before compression", independent of recipient count; 0 disables); leftovers wait for the next tick; new chunk watchers get a full state on watch [D]. Defaults: monitorWidth 8, monitorHeight 6, monitorDistance 65.

Rendering: `MonitorRenderer {BEST, TBO, VBO}` (`cctweaked` partial clone, `git show HEAD:...MonitorRenderer.java`). The TBO path uploads 3 unsigned bytes per cell (char, fg, bg) into a `GL_TEXTURE_BUFFER` bound as `usamplerBuffer Tbo` and a std140 uniform block `MonitorData { vec3 Palette[16]; int Width, Height; ivec2 CursorPos; int CursorColour; }`; the fragment shader computes the cell from the interpolated font position, `texelFetch`es the three values, samples a 6x9 glyph from a 256 px font atlas and recolours through the palette, so the whole monitor is one quad (`monitor_tbo.fsh`, `MonitorTextureBufferShader.java:38-101`). Buffers are re-uploaded only on change (`MonitorBlockEntityRenderer.java:139-152`). Current `bestRenderer()` returns VBO (`MonitorBlockEntityRenderer.java:278-279`), i.e. the TBO path is kept as an opt-in. Both require GL 3.1+ and Mojang's shader pipeline, neither of which exists on 1.7.10 LWJGL2 without Angelica.

### 6. CraftOS-PC graphics mode and CC:Graphics

CraftOS-PC (emulator) `term.setGraphicsMode(0|1|2)`: mode 1 is 16-colour, mode 2 is 256-colour palette; the pixel grid is 6x9 per character cell (306x171 on a 51x19 terminal, query via `term.getSize(mode)`); `setPixel(x,y,c)` is 0-based; `drawPixels(x,y,lines[,w,h])` accepts strings with one byte per pixel; the doc says the pixel functions in general are "a couple orders of magnitude faster when operating on strings rather than tables" (C-side `memset/memcpy`), and gives the explicit "about 100 times faster" figure only for `getPixels(..., strings=true)`; `setFrozen(true)` suppresses presentation while drawing to avoid tearing [D, craftos-pc.cc/docs/gfxmode]. ### 7. Framebuffer-streaming mods

**VM Computers** (`Delta2Force/MCVmComputers`, Fabric 1.16.5, GPL, abandoned pending rewrite) [V]. The VM runs client-side in VirtualBox; a thread polls `IDisplay.takeScreenShotToArray(..., PNG)` (`mcvm/src/main/java/mcvmcomputers/client/utils/VMRunnable.java:79`). Once per client render frame (`generatePCScreen()` is injected at the head of `MinecraftClient.render`, `GameloopMixin.java:84`, `:143`) the owning client deflates the PNG and, only if the result is <= 32,766 bytes, sends it to the server (`ClientSidePacketRegistry.sendToServer`), which relays it to all players watching the owner (`client/ClientMod.java:180-213`, `MainMod.java:80-96`); larger frames are not sent and the client posts a red chat message ("screen_too_big_mp") once, via a `failedSend` flag, and a green "screen_ok_mp" when frames fit again. The 32,766 figure is the client->server custom-payload cap, not a server->client one. No deltas, no rate limiting, no shared budget. It demonstrates the failure mode OpenGPU must avoid.

**OpenComputers 2** (`fnuecke/oc2`, MIT, branch 1.21.1, active 2026-10-07) projector [V]. The VM sees a memory-mapped `SimpleFramebufferDevice` 640x480 RGB565 (`STRIDE = 2`) with a dirty `BitSet` per pair of rows (`oc2/common/src/main/java/li/cil/oc2/common/vm/device/SimpleFramebufferDevice.java:16-42`, `:172-173`; `ProjectorDevice.java:33-36`). Each server tick with changes, the block entity converts dirty lines to a YUV420J `Picture`, encodes with jcodec `H264Encoder(new CQPRateControl(12))` as a P-frame or forced IDR keyframe, then Deflates at BEST_COMPRESSION (`ProjectorBlockEntity.java:93-100`, `:348-388`). A `StreamingLoadBalancer` round-robins projectors, replenishes a byte budget each tick from `projectorAverageMaxBytesPerSecond = 160 * 1024` (`Config.java:131`), allows short over-budget bursts, encodes on a worker pool, charges `frame.length * recipients` and forces a keyframe when a player starts watching (`ProjectorLoadBalancer.java:20-119`, `StreamingLoadBalancer.java:40-115`). Frames are capped at 1 MiB; clients decode on a thread pool into a `DynamicTexture`. Rendering is a deferred screen-space projection: for up to 3 visible projectors the client renders a 256 px depth-only view from the projector, then a full-screen pass reconstructs world position from the main camera depth, projects into each projector's clip space, shadow-tests against the projector depth and samples the 640x480 image with pixel snapping (`client/renderer/ProjectorDepthRenderer.java:67-98`, `resources/assets/oc2/shaders/core/projectors.fsh`). This is the most complete bandwidth design in the survey; the rendering half is modern-GL only.

**WebDisplays + MCEF** (`montoyo/webdisplays` 1.12.2-1.1, public domain, unmaintained; `montoyo/mcef` 1.12.2-1.20) [V]. The server syncs only metadata: `CMessageScreenUpdate` actions `URL, RESOLUTION, DELETE, MOUSE, TYPE, UPGRADES, JS_REDSTONE, OWNER, ROTATION, RUN_JS, AUTO_VOL` (`webdisplays/src/main/java/net/montoyo/wd/net/client/CMessageScreenUpdate.java:25-35`); each client runs its own Chromium instance at up to `maxResolutionX/Y` 1920x1080 (`WebDisplays.java:143-144`). Pixel upload path in MCEF: `CefRenderer.onPaint` receives a BGRA buffer and dirty rects, does `glTexImage2D` on resize/full repaint, otherwise `glPixelStorei(GL_UNPACK_ROW_LENGTH/SKIP_PIXELS/SKIP_ROWS)` + `glTexSubImage2D` per dirty rect (`mcef/src/main/java/org/cef/browser/CefRenderer.java:144-161`). OC integration is metadata and input only (`TileEntityOCInterface`: `getSize, getResolution, getURL, click` with `@Callback(limit = 4)`, `entity/TileEntityOCInterface.java:22-94`). Zero pixel bandwidth, but content is not deterministic across clients. Waterframes/WATERMeDIA follow the same pattern (client-side LibVLC/FFmpeg decode of a synced URL; the library "can't run on a server") [D, lower confidence].

**OpenScreens** (`itsmeow/OpenScreens`, 1.12.x, MIT, 2019) and **OCDevices** FlatScreen (1.12.2) add holographic/flat/tilted screen blocks that reuse OC's text buffer; they are form-factor variants, not pixel engines [D]. **Computronics 1.9.10-GTNH** has no graphics components: Camera is a ray-distance sensor, Colorful Lamp a single RGB; its one relevant precedent is the audio pipeline (`AudioPacketDFPWM{frequency, byte[] data}` streamed from server to clients passing `canHearReceiver` range checks) [V, javap]. **OpenPrinter 0.3.1-GTNH** prints text pages to items; no pixel path [V, class list]. **ccGPU**: no mod with that exact name was found; the nearest are CC-DirectGPU, CCLights2, CC:Graphics, and Tom's Peripherals / High Level Peripherals (GPU peripheral with a GLSL-like shader run on each viewer's GPU, 1.16+) [D, low confidence].

**CC-DirectGPU** (`tiktop101/CC-DirectGPU-Mod`, NeoForge 1.21.1, 1.20.1 abandoned, proprietary ARR; the repo holds only README and examples) [V]. Peripheral API with `displayId`/`textureId` handles, framebuffer ops (`clear, fillRect, drawText, drawCube, clearZBuffer`) and explicit `updateDisplay(displayId)` to present; pixel data crosses the Lua boundary as Base64 strings; it ships dictionary-compression helpers (`compressWithDict`) and JPEG decode; listings claim 164x81 px per block up to 4x (656x324) with 16x16-block arrays [D]. Closed source, so its transport is unknown.

### 8. Pure-Lua pixel workarounds and software 3D

**MineOS Screen library** (OC) keeps six flat tables (3 current, 3 new frame); `update()` diffs new vs current, groups runs of cells with equal background and equal foreground (or spaces), and emits `setBackground` once per group, `setForeground` on change, and one `set` per run; it never uses `fill`/`copy`. The author's "hundreds and thousands of times faster" claim is unmeasured. Braille (2x4, 320x200 at one fg/bg pair per cell) is possible because OC's font has the glyphs, but the only community report found was a failed attempt [D]. **ComputerCraft.** Pine3D (`Xella37/Pine3D`, MIT, 2438-line single file) rasterizes in Lua and presents through `betterblittle`, which packs 2x3 pixel groups into CC's drawing characters 128-159 choosing the best two of 16 colours per cell (`pine3d/betterblittle.lua:1-40`). ## Design implications for OpenGPU

1. **Retained client mirror + command/delta stream, with an explicit present.** Every robust design (OC, VRAM, Plethora, OCLights2, OC2) mirrors state on the client and ships commands or deltas once per tick. OpenGPU should buffer all GPU calls of a tick (or of an explicit `present()`/`endFrame`) into one compressed packet per screen, exactly as `TextBuffer.pendingCommands` does, and expose `startFrame/endFrame` semantics so Lua can avoid tearing (OCLights2, CraftOS-PC `setFrozen`, CC-DirectGPU `updateDisplay`).
2. **Know the real payload limits and chunk where they bite.** On MC 1.7.10 the server->client `S3FPacketCustomPayload` allows 2,097,050 bytes under Forge 10.13.4.1614 (its binpatch replaces the unpatched vanilla class's 1,048,576; the installed Hodgepodge 2.7.216 raises it to 256 MiB, `packetSizeLimit=268435456`), and the 32,766/32,767-byte cap applies to client->server `C17PacketCustomPayload` only (unpatched client class strings: "Payload may not be larger than 1048576 bytes" vs "Payload may not be larger than 32k"; Forge-patched and Hodgepodge values from 00 §5, 03 §3, 07 §1, 13 §3); 1.7.10's `FMLProxyPacket` has a single `toS3FPacket()` and does no multipart splitting [V]. OC's own screen batches are unchunked Deflate packets, and OCLights2 never needed its `Short.MAX_VALUE-100` chunks for the server->client limit. So screen traffic (server->client) at 320x200x16bpp (128 KB raw per keyframe, far less after Deflate) fits without chunking; chunking is required for client->server uploads over 32 KiB (e.g. clipboard/file drops, where OC-GTNH 1.12.58+'s `sendDropFile` with `grouped(31*1024)` chunks is the precedent) and for any server->client payload over the stock Forge cap of 2,097,050 bytes (a raw 640x480 RGBA8 keyframe is 1.2 MB and fits; 03 §3's 256 KB per-packet soft limit is the design rule regardless, since Hodgepodge's 256 MiB is not guaranteed on every peer). Design the packet layer so a chunker can be inserted, but do not pay for it on every screen update.
3. **Budget bytes, not just calls.** Copy OC2's `StreamingLoadBalancer`: a server-wide bytes/second budget (OC2 uses 160 KiB/s), replenished per tick, charged by `frame.length * recipients`, round-robin across devices, keyframe on new watcher, encoding off the server thread. Pair it with OC-style call-budget costs so Lua programs are throttled fairly on the Lua side as well (OpenGPU callbacks should be `direct = true` with costs modelled on `GraphicsCard.setCosts` and a bitblt-like "dirty area" cost). Note that OC's actual model is "pay when pixels reach the screen": writes into VRAM pages are budget-free and the cost is charged at `bitblt` in proportion to the dirty area (`GraphicsCard.scala:100-107`, `:197-208`); OpenGPU can copy that shape (free off-screen drawing, cost at `present()` proportional to bytes shipped) rather than charging every draw call.
4. **Recipients = chunk watchers, not radius broadcasts.** OC sends to `isPlayerWatchingChunk` players; OCLights2's 4096-block radius is the anti-pattern. CC:Tweaked also sends full state on chunk watch, which maps onto OpenGPU keyframes.
5. **Frame encoding.** For a 2D framebuffer, dirty-rect deltas (OC2's dirty line BitSet, MCEF's dirty rects) plus Deflate are enough; H.264 is overkill for palette/UI content and adds jcodec (~2 MB) to the jar, but OC2 proves it fits in a server tick budget when done on worker threads. A palette or RGB565 (OC2) framebuffer halves bandwidth versus RGBA8 and matches OC's 8-bit colour tier.
6. **Determinism decides where rasterization runs.** If clients rasterize (cheapest bandwidth: command stream only) the server cannot answer `getPixel`/readback unless it also executes the same deterministic pipeline, which is exactly CCLights2's choice (same register-program interpreter on both sides) and OCLights2's (same Java2D code on both sides). OpenGPU's plan to compile shaders to JVM bytecode fits this, with one caveat: only `+ - * /`, `sqrt`, comparisons and conversions are bit-reproducible across JVMs (`strictfp` semantics, mandatory since Java 17; on Java 8 declare the generated classes `strictfp`). `java.lang.Math.sin/cos/tan/exp/log/pow` are specified only to within 1 ulp and are commonly JIT intrinsics that differ between platforms and JVM versions; only `java.lang.StrictMath` (fdlibm) guarantees identical results. A shader compiled to bytecode must therefore route transcendental functions through `StrictMath` (or its own fixed implementations) so the same compiled shader can run on the server (for readback/compute) and on clients (for display) with bit-identical output. Budget: CCLights2 reports ~10 ns per interpreted op per pixel; bytecode compilation should beat that by 5-20x [I].
7. **Client rendering under Angelica.** GTNH OC removed display-list caching for the text buffer specifically (`TextBufferRenderCache.scala:27`; upstream MightyPirates `master-MC1.7.10` still uses `glNewList/glCallList` there, so this is a GTNH change), but it still uses display lists in `RobotRenderer.scala:73,105,230,237` and `client/renderer/gui/BufferRenderer.scala:36,87`, and the installed Angelica 2.2.21 (`scratchpad/Angelica-2.2.21`, tag a8c29fa) ships a VBO-based display-list emulation with immediate-mode recording (`glsm/.../DisplayListManager.java`, `recording/ImmediateModeRecorder.java`, added 2026-08-09 in #2002) and wraps `glDrawElements`/`glInterleavedArrays` in GLSM [V]. The OC comment cannot be dated from the 1-commit shallow checkout, so "display lists are fragile under current Angelica" is an inference, not a verified fact [I]. OpenGlasses' immediate mode is the pattern to avoid regardless. The safest 1.7.10 path is a `DynamicTexture` per screen updated with `glTexSubImage2D` on dirty rects (MCEF, OCLights2) drawn as a single textured quad via Tessellator, which both LWJGL2 and Angelica's GLSM handle. The OC hologram is a weak precedent for client-side geometry: it is a legacy client-state-array path (`glEnableClientState` + `glInterleavedArrays` + `glColorPointer` + `glDrawElements(GL_QUADS)`) that re-uploads its colour+index buffer on every change, and its behaviour under Angelica 2.2.21 was not verified here. CC:Tweaked's TBO shader is the model for a later "cells as texels" path if an Angelica shader pipeline is exposed; OC2's depth-projection should be out of scope.
8. **Lua-facing bulk data format.** CraftOS-PC measured strings two orders of magnitude faster than tables for pixel data; CC-DirectGPU resorts to Base64; OC's `Arguments.checkByteArray` already accepts raw Lua strings as `byte[]` (used by `hologram.setRaw`). OpenGPU should take byte strings (palette indices or packed RGB565) for `drawPixels`/`uploadTexture`, with a `limit`/non-direct callback for large uploads.
9. **Handles and VRAM accounting.** Mirror OC's `allocateBuffer/freeBuffer/buffers/totalMemory/freeMemory` model for textures, framebuffers and compiled shaders (OCLights2 and CCLights2 use the same shape and `reset()` for leaked resources). Persist VRAM to NBT like `GpuTextBuffer.save` so reloads do not blank screens. Resend on client attach, but improve on OC's `TextBufferRamInit`, which re-ships the whole page every time a modified page is blitted (`VideoRamRasterizer.scala:24-28`): OpenGPU should track dirty rectangles per client-visible resource so a mutate-then-present cycle ships only the changed region.
10. **Emulator parity.** Ocelot-brain implements `GpuTextBuffer`/bitblt and the hologram; OpenGPU's core (command protocol, rasterizer, shader compiler) should be a plain JVM library with an adapter for OC-GTNH and one for ocelot-brain, otherwise the user's OC-LuaJIT harness cannot exercise it.
11. **Target resolution.** Existing practice clusters at 256x144 .. 640x480 for whole screens and 32 .. 164 px per block; OC's 20-block text render cutoff and CC's 65-block monitor distance bound the useful pixel density. A default of 320x200 per screen (OC-font-compatible with 160x50 cells x 2x4) scaling to 640x400 on multi-block screens, 8-bit palette or RGB565, is consistent with every data point above.
12. **Expect Lua-side diffing.** MineOS exists because OC's API is naive; if OpenGPU does server-side dirty tracking (as OC2 and OC VRAM do), Lua programs do not need their own mirror.
