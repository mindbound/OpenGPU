## Summary

1. **Client CPU is the binding constraint, and it is per tick, not per client frame.** A mirror replay costs what the server's render costs: **[derived]** from 06 §3's measured 8–9 ns per textured pixel at 2× overdraw, a T2 (320×200) 3D frame is ≈ 1.3–1.6 ms and a T3 (640×400) frame ≈ 4.8–5.6 ms on the bench CPU, and ≈ 1.8–2.4× more on a typical player CPU (PassMark single-thread 4,612 for the 285HX vs 2,559 for a Ryzen 5 3600 and 1,910 for an i5-8250U; inference, §1). Because the tier FPS cap is 20 = the tick rate, each watched display costs at most one replay per tick, so five T3 displays are **24–28 ms per tick on the bench box and 43–67 ms on typical hardware** — the latter is more than one core and cannot be hidden behind Minecraft's render thread, which itself needs a core (`Minecraft.runGameLoop` ticks and renders on one thread, `Minecraft.java:1008-1115`). 09's "30–55 ms per tick" figure is therefore right in magnitude; its mitigation is not: a "≤ 4 ms per *client frame*" self-limit allows up to 12 × 4 = 48 ms of replay per tick at 60 fps and shrinks only when the client is already slow. It must become a **per-tick replay budget** (default 8 ms, ≈ 16 % of one core), adaptive on a measured EWMA, with displays ranked by on-screen size.
2. **In M2 as planned (interpreter only, JIT in M3) the mirror cannot run user shaders at all**: 07 §1's interpreter constant (100–500 ns per fragment) puts a T2 frame at 13–64 ms and a T3 frame at 51–256 ms per display. The mirror is only viable for shaded content once the `:jit` backend exists on the client, i.e. in M3, and the M2 exit criterion ("textured 1 k-triangle scene … under 3 ms") is implicitly a fixed-function (built-in textured/Gouraud) path, which should be said.
3. **TILES is not a graceful fallback for 3D at T3**: a lossless 640×400 RGB565 3D frame deflates ≈ 2.0× **[measured]** (255 KB) and inflates in 1.7–1.8 ms; at 20 fps that is 5 MB/s, which the 16 KB/tick token bucket throttles to ≈ 1 fps. The real fallback is A's lossy 4×4 lineage + half-res LOD (09 §3.4, scheduled for M4), which therefore must move *before* the mirror, not after it.
4. **Memory is not a constraint.** Worst case per watched T3 3D display ≈ 8.9 MB heap + 1 MB direct + 1 MB GPU (T2 ≈ 2.4 MB heap); five T3 mirrors ≈ 45 MB, under 1 % of the user's heap (Prism global `MaxMemAlloc=8000`/`MinMemAlloc=6000` MB, applied because the instance has `OverrideMemory=false`; the GTNH wiki recommends 4–6 GB for single player and warns that > 8 GB on Java 8 stutters). Cap resident mirrors (LRU, default 8) and the sum (64 MB) anyway.
5. **The `:jit` child-loader strategy works identically on the client.** Both sides load mods through the same `LaunchClassLoader` (or `RfbSystemClassLoader` under lwjgl3ify); Mixin hooks only `LaunchClassLoader.findClass` via `registerTransformer`; the one `java.lang.instrument` user in `+unimixins-all-1.7.10-0.3.2.jar` is `MixinAgent`, which activates only through `premain`/`agentmain` guarded by `-Dmixin.hotSwap=true`, and no `-javaagent` is in the instance's or lwjgl3ify's JVM arguments; CoreTweaks and Hodgepodge reference `defineClass` nowhere; GTNHLib's `StaticASMEventHandler$ASMClassLoader` is exactly the recommended child-loader pattern and already runs on this client stack. Two client-specific obligations: compile on the mirror worker (never the render thread), and do not let the first 1–2 interpreted-bytecode frames of a new program trip `PREFER_TILES`.
6. **Integrated server: bypass the mirror by policy, not by sharing objects.** `FMLCommonHandler.getEffectiveSide()` is a thread-name check (`"Server thread"` → SERVER, anything else → CLIENT, `FMLCommonHandler.java:152-160`), so `SideTracker.isServer` is *false on every OC worker and OpenGPU pool thread*, on dedicated servers too; OC's own tile entities use `world.isRemote` instead (`traits/TileEntity.scala:30`). OpenGPU must capture the side at construction and never ask on a pool thread. For local viewers the server-side encoder should check `NetworkManager.isLocalChannel()` (`NetworkManager.java:274-277`) and send `TILES` only, undeflated, without a token bucket: the local pipeline has no codec (`NetworkSystem.java:117-125`, `NetworkManager.java:321-333`), so the packet object crosses by reference and the only cost is one 64–512 KB copy. No mirror, no determinism exposure and no second render in single player or for the LAN host.
7. **Cross-ISA determinism is achievable but narrower than 09 states.** `+ − × ÷ √`, conversions and comparisons are IEEE-exact on both x86-64 (SSE2) and aarch64 with or without `strictfp` on Java 17+ (JEP 306) and with `strictfp` on Java 8 (x86-64 HotSpot generates SSE2 code; 06 verification C9); Java forbids implicit FMA contraction and HotSpot keeps floating-point reductions in sequential order even when auto-vectorizing (`requires_strict_order`, JDK-8320725). `Math.*` transcendentals are *not* portable (the aarch64 `Math.cos` stub was wrong in JDK 11/12, JDK-8210461; the aarch64 `Math.log` intrinsic was removed, JDK-8210858). `StrictMath` is portable by specification and fully Java since JDK 21 (JDK-8171407, Fix Version 21); on JDK 8/17 the still-native fdlibm functions are compiled with `-ffp-contract=off` since JDK-8210416 (backported to 8u). aarch64 clients only exist on the lwjgl3ify/Java 17+ leg (LWJGL 2.9.4 ships Windows/Linux/macOS x86 natives only; lwjgl3ify adds `natives-osx-arm64`/`natives-linux-arm64`), so the practical matrix is x86-64 JDK 8/17/21 + aarch64 JDK 17/21, and the conformance CI needs an aarch64 leg (GitHub `ubuntu-24.04-arm` or `macos-14` runners). Residual, un-measurable here: subnormal handling (MXCSR FTZ/DAZ or FPCR.FZ set by a native library on the mirror thread) — mitigated because a CRC mismatch forces `TILES`, so divergence degrades, never corrupts.
8. **CRC32 per packet is free**: 0.002 ms for a 128 KB frame and 0.010 ms for 512 KB **[measured]** on both JRE 8 and JDK 25 (hardware CLMUL intrinsic). The resync *keyframe* is the cost: ≈ 1.8 ms inflate + ≈ 0.3 ms apply per T3 resync on the bench box, plus 200–340 KB of bandwidth.
9. **The captured `Context` needs an explicit lifecycle** (§6): it is the computer's `Machine` (`Machine.scala:393`), it survives chunk unload as a stale object (a *new* `Machine` is built on reload), and `signal` on it returns `false` once the machine is `Stopping/Stopped` (`:335-339`, `close()` clears the queue `:939-953`). Design: an `AtomicReference<Context>` on the card refreshed by every callback, cleared on `onDisconnect(this.node)` and on `computer.stopped`, an epoch counter that invalidates in-flight jobs, and pool jobs that hold the card, never the `Context`.

**Conclusion (§7):** keep the mirror as the design's long-term shape, but **move it out of M2 into M3 (with the JIT it depends on) and pull A's governor (lossy lineage + half-res LOD) from M4 into M2**. v1 commits to T2 3D for remote viewers (mirror on, ≈ 2.3–3.8 ms per display per tick on typical hardware) and to T3 3D only on LAN/single player (`TILES`, local channel) or via M5 GL. The numeric exit criteria the mirror must meet before it is enabled by default are listed in §7.

## 1. Client CPU per tick

**Loop facts.** The 1.7.10 client runs `runTick()` 0–10 times (`Timer.elapsedTicks`, clamped at `Timer.java:95-97`) and then renders, all on one thread (`Minecraft.runGameLoop`, `Minecraft.java:1008-1115`: tick loop `:1037-1040`, `updateCameraAndRender` `:1067`), then `Display.sync(getLimitFramerate())` when a frame cap is set (`:1136-1139`). Packet handlers run on this same thread (03 §6), which is why 09 puts the mirror on a worker. The worker does not block rendering, but it competes for cores with everything else the client runs: Iris's thread pool (`max(2, min(12, cores/2))`, `Angelica-2.2.21/src/main/java/net/coderbot/iris/Iris.java:157`), Sodium's chunk builders (user slider 0..`availableProcessors`, `SodiumGameOptionPages.java:506`, default `chunkBuilderThreads = 0` = automatic, `SodiumGameOptions.java:217`), the GC (`-XX:ParallelGCThreads=2` in `instance.cfg` JvmArgs), Netty and sound; in single player additionally the "Server thread", OC's four `Computer` threads (07 §3) and the OpenGPU server pool (`max(1, cores/2)`, 09 §3.1).

**Per-frame cost model [derived from 06 §3, ±20 %].** Textured, perspective-correct, depth-tested pixels cost 8–9 ns on JDK 8 (06 §3 reading: "≈8–9 ns per textured pixel"; 7.2 Mtri/s ≈ 130–140 ns setup per small triangle). With 09's 2× overdraw assumption:

| Stage | T2 320×200 | T3 640×400 | Basis |
|---|---|---|---|
| Fragments (2× overdraw, textured) | 128 k × 8–9 ns = 1.02–1.15 ms | 512 k × 8–9 ns = 4.1–4.6 ms | 06 §3 |
| Triangle setup, 1–2 k triangles | 0.13–0.28 ms | 0.13–0.28 ms | 06 §3 |
| Colour + depth clear (0.5 / 2 MB) | ≈ 0.03–0.05 ms | ≈ 0.1–0.2 ms | [est.] memset-class |
| Quantize to wire format (index8 / RGB565) | ≈ 0.06 ms | ≈ 0.26 ms | 08-C §6 (~1 ns/px) |
| Dequantize to ARGB `int[]` for `glTexSubImage2D` | ≈ 0.06 ms | ≈ 0.26 ms | [est.] 1 ns/px |
| CRC32 of the quantized frame | 0.002 ms | 0.010 ms | **[measured]**, §5 |
| Command decode + validate (~100 B uniforms) | ≈ 0 | ≈ 0 | 07 §1 B |
| **Total per presented frame, bench CPU** | **≈ 1.3–1.6 ms** | **≈ 4.8–5.6 ms** | |
| **Typical player CPU (× 1.8–2.4)** | **≈ 2.3–3.8 ms** | **≈ 8.6–13.4 ms** | inference, below |

The hardware factor is an inference from PassMark single-thread ratings (synthetic, single-core): Core Ultra 9 285HX ≈ 4,612; Ryzen 5 3600 ≈ 2,559 (0.55×); i5-8250U ≈ 1,910 (0.41×) (cpubenchmark.net, see Sources). 06's own risk note allows 2–5× for older cores. The Steam survey (Sep 2026) puts 8-core at 30 %, 6-core at 27 % and 4-core at ≈ 13 % of surveyed machines, so "a spare core" is usual but not universal, and a 4-core laptop running GTNH under Angelica has none.

**Per tick.** Tier FPS caps are 20 = tick rate (07 §5, 08-C §6), so a watched display produces ≤ 1 presented frame per tick and the mirror replays ≤ 1 frame per display per tick:

| Watched displays | T2, bench | T2, typical | T3, bench | T3, typical |
|---|---|---|---|---|
| 1 | 1.3–1.6 ms | 2.3–3.8 ms | 4.8–5.6 ms | 8.6–13.4 ms |
| 3 | 3.9–4.8 ms | 7–11.5 ms | 14–17 ms | 26–40 ms |
| 5 | 6.5–8 ms | 11.5–19 ms | 24–28 ms | 43–67 ms |
| 5, as a share of one core (tick = 50 ms) | 13–16 % | 23–38 % | 48–56 % | **86–134 %** |

Reading. 09 §5 Q5's "30–55 ms per tick for five T3 displays" sits between the bench and typical columns and is consistent with this model. Five T3 3D displays on typical hardware exceed one core; the renderer thread needs one of its own at 60 fps (16.7 ms per frame including up to a tick's `runTick`), so on 4-core machines the mirror would be stealing from chunk building and the integrated server. Five T2 displays are affordable everywhere.

**The self-limit's unit is wrong.** 09 §3.1 bounds replay at "≤ 4 ms per client frame across displays". Frames arrive once per tick; at 60 fps the worker has 12 client frames per tick, so the bound permits 48 ms of replay per tick — it limits *latency per client frame*, not throughput, and it tightens only as the client's fps falls, i.e. only after the damage is done. Replace it with a **per-tick replay budget** `client.mirrorBudgetMs` (default 8 ms ≈ 16 % of a core; fits 1 T3 or 5 T2 displays on the bench box, ≈ 1 T3 or 2–3 T2 on typical hardware), spent in order of on-screen size (the display the player is actually looking at first), measured as an EWMA of actual replay time per display so a slow client sheds displays before the tick is late; a display outside the budget gets `PREFER_TILES` (09's hint) — which, as the next paragraph shows, means the lossy/LOD lineage, not lossless tiles. Keep the 4 ms figure only as a per-replay *slice* so one T3 display cannot pin the worker.

**Interpreter vs JIT on the client.** 09 §4 ships the mirror in M2 with the interpreter and the `:jit` backend in M3. 07 §1's cost model has `c_frag` = 10–20 ns compiled and 100–500 ns for a tree-walking interpreter; 06 §3 measures a 64 k-element kernel at 0.15–0.65 ms JIT vs 6–30 ms interpreted (10–50×). A user fragment shader executed by the interpreter costs the mirror **13–64 ms per T2 frame and 51–256 ms per T3 frame** [derived] — infeasible at any budget. Two consequences: (a) the M2 criterion "textured 1 k-triangle scene at 20 fps on T2 under 3 ms server CPU" is only achievable with a built-in fixed-function textured/Gouraud path, so M2 must *name* that path as the thing that runs in M2 for both server and mirror; (b) the mirror's shaded-content case needs the client JIT, so the mirror belongs with M3. (The same arithmetic applies to the server, but the server was already planned to carry the interpreter cost under a 10 ms slice; the mirror has no slice of its own on the client's budget.)

**TILES as the fallback for 3D [measured].** Deflating a synthetic RGB565 3D-like frame (gradient + ±1 LSB noise, `scratchpad/gap12/bench/InflateMid.java`): 320×200×2 B → 74,189 B (ratio 1.73), deflate 1.85–1.90 ms, inflate 0.50–0.51 ms; 640×400×2 B → 255,056 B (ratio 2.01), deflate 6.7–6.9 ms, inflate 1.7–1.8 ms; 640×400 index8 → 116,906 B (2.19), deflate 4.1–4.3 ms, inflate 0.94 ms (JRE 1.8.0_492 and JDK 25.0.4.1 agree within 5 %). These confirm 07 §1's **[est.]** 1.5–2.5× ratio and 1.3/5.1 ms deflate figures. At 20 fps a lossless T3 3D stream is ≈ 5 MB/s per viewer; the 16 KB/tick bucket (09 §3.4) admits ≈ 1 frame per second of it. So when the mirror sheds a T3 3D display, the viewer sees a slideshow unless the lossy 4×4 lineage and half-res LOD exist: 09 §3.4 quotes ≈ 26 KB per 320×200 lossy frame (→ 10 fps in 260 KB/s); at 640×400 that is ≈ 100 KB [est.] → ≈ 3 fps within the bucket, and half-res LOD (320×200) brings it back to 10 fps. Hence the governor is the prerequisite of the mirror's fallback and must ship first.

## 2. Client heap per watched display and the available heap

**Per display, client side [derived from 09 §3.1/§3.7, 08-C §6 tier table].** Mirror `Device` colour `int[]` (4 B/px) + depth `float[]` (4 B/px); the quantized wire-format frame that the CRC and `TILES` refer to (1 B/px index8 at T1/T2, 2 B/px RGB565 at T3); the dequantized ARGB `int[]` the TESR uploads, double-buffered per 03 §6 (4 B/px × 2); resident resources up to the tier VRAM cap (256 KB / 1 MB / 4 MB, 08-C §6); decode scratch (one ≤ 256 KB packet copy, an `Inflater` ≈ 40 KB, tile scratch); off-heap: one direct `IntBuffer` for `glTexSubImage2D` (4 B/px) and the GL texture (4 B/px of driver memory).

Against a 4–8 GB heap the mirror's bounded ≈ 45–64 MB is ≈ 1 %: **memory does not decide the question; CPU does.**

## 3. The `:jit` child-`ClassLoader` strategy on the client

05 §1 established for the server that generated classes are defined by a private `ClassLoader` subclass parented to the mod's loader (`OC-Wasm-GTNH/src/main/java/ca/chead/ocwasm/Compiler.java:190-204` pattern) and that `LaunchClassLoader` runs transformers only inside its own `findClass`. The client-side evidence:

- **Same loaders on both sides.** Forge 1.7.10 launches client and server through launchwrapper's `LaunchClassLoader` (Java 8) or RetroFuturaBootstrap's `RfbSystemClassLoader` (`-Djava.system.class.loader=com.gtnewhorizons.retrofuturabootstrap.RfbSystemClassLoader`, lwjgl3ify `README.MD:39`); mod classes, including `opengpu.client.*`, are loaded by the same loader as `opengpu.core.*`, so a child loader parented to `OpenGpuJit.class.getClassLoader()` links identically on both sides.
- **What UniMixins hooks.** Searching every class in `+unimixins-all-1.7.10-0.3.2.jar` (3,621 classes, extracted to `scratchpad/gap12/unimixins-jar`) for `defineClass` finds only `MixinExtras`'s `ClassGenUtils`/`LocalRefClassGenerator` and the `MixinAgent*` classes; for `java/lang/instrument` only `MixinAgent` and `MixinAgent$Transformer`. `javap -p -c MixinAgent`: `premain` checks `mixin.hotSwap` == `"true"` before `init(Instrumentation)`, `agentmain` calls `init` directly; the manifest declares `Premain-Class`/`Agent-Class: org.spongepowered.tools.agent.MixinAgent`, `Can-Redefine-Classes: true`. Neither path runs unless the jar is passed as `-javaagent` or attached: the instance's `JvmArgs` (`instance.cfg`), the `jvm_args` lines in the `hs_err_pid*.log` files and lwjgl3ify's `java9args` (`README.MD:39`) contain no `-javaagent`. Mixin's normal path registers an `IClassTransformer` with `LaunchClassLoader.registerTransformer` (05 §1), which a child loader's `defineClass` never reaches.
- **Other coremods.** `CoreTweaks-1.7.10-0.3.3.2+nomixin.jar` and `hodgepodge-2.7.216.jar` (scratchpad `hodgepodge-classes`) contain no class referencing `defineClass`. `gtnhlib-0.11.52.jar` contains `com/gtnewhorizon/gtnhlib/eventbus/StaticASMEventHandler$ASMClassLoader`, which `extends java.lang.ClassLoader`, is constructed with `StaticASMEventHandler.class.getClassLoader()` as parent and calls `defineClass(String, byte[], int, int)` (javap) — the precise pattern 05 recommends, exercised today on this client stack by every mod using GTNHLib's event bus. MixinExtras instead resolves `sun.misc.Unsafe.defineClass` reflectively on Java 8 and `MethodHandles.Lookup.defineClass` on 9+ (javap of `ClassGenUtils`), the mechanism 05 §1 advises against; it proves runtime class generation under Mixin on both JVM legs is routine, not that OpenGPU should copy it.
- **`--add-opens`** is irrelevant to a child loader; lwjgl3ify opens `java.base/java.lang` anyway (`README.MD:39`).

Two client-only obligations follow. (1) Compile on the mirror worker: ASM emission + `defineClass` + verification is milliseconds and must never run on the render thread; the server ships shader *source* in `RESOURCE` records and the client compiles it itself with the same cache key `hash(source, pipeline state)` — never ship bytecode. (2) HotSpot warm-up: a freshly defined class runs in the bytecode interpreter until C1/C2 compile it (thousands of invocations, i.e. the first frame or two of a new program at 128 k–512 k fragments), so the first replays of a new program are several times slower; the per-display EWMA in §1 must ignore the first N frames after a program change so warm-up cannot trip `PREFER_TILES`.

## 4. The integrated server (client and server in one JVM)

**Side detection.** `SideTracker.isServer()` is `FMLCommonHandler.instance().getEffectiveSide().isServer()` (`OpenComputers-GTNH/src/main/java/li/cil/oc/util/SideTracker.java:7-9`), and in Forge 1.7.10 `getEffectiveSide` is `Thread.currentThread().getName().equals("Server thread") ? Side.SERVER : Side.CLIENT` (`OC-LuaJIT/build/rfg/minecraft-src/java/cpw/mods/fml/common/FMLCommonHandler.java:152-160`). It distinguishes sides by *thread*, not by world: on an OC `Computer` worker thread or an OpenGPU pool thread it returns `CLIENT` even on a dedicated server. OC's tile entities therefore prefer `world.isRemote` and fall back to `SideTracker` only when `world == null` (`common/tileentity/traits/TileEntity.scala:30`). Rule for OpenGPU: the card environment is created server-side only (`createEnvironment` returns `null` on the client, 09 §3.2), the display TE captures `world.isRemote` at `validate()`, and nothing on a pool thread ever consults `SideTracker`/`getEffectiveSide`.

**Two devices, one JVM.** In single player the integrated server (`Minecraft.theIntegratedServer`, `Minecraft.java:2185-2186`) owns the authoritative `Device` in the server-world TE, and the client world holds a *different* TE object for the same block. Sharing the server's frame array with the client TE would couple the pool thread to the render thread, bypass the packet seq/CRC state machine and break on LAN (other players still need packets). Keep one path and make it cheap instead:

- The server→client channel for a local player is Netty's in-memory transport: the server endpoint pipeline is just `packet_handler` (`NetworkSystem.java:117-125`) and the client's local pipeline likewise (`NetworkManager.provideLocalClient`, `NetworkManager.java:321-333`); there is no encoder/decoder, so the `S3F`/`FMLProxyPacket` object crosses by reference and the only byte work is what OpenGPU writes and reads.
- `NetworkManager.isLocalChannel()` (`NetworkManager.java:274-277`: `channel instanceof LocalChannel || LocalServerChannel`) is available on the server as `player.playerNetServerHandler.netManager`. **Policy:** for a local viewer the encoder always picks `TILES`, skips deflate, and exempts the viewer from the token bucket. Cost per T3 frame: one 512 KB copy at write and one at read (≈ 0.05–0.1 ms each [est.]) plus the dequantize/upload the client does anyway. The mirror never starts, no determinism is exposed, and single player never double-renders.
- LAN (`theIntegratedServer.getPublic()`, `Minecraft.java:1117`): the host stays on the local policy; remote players get the normal `TILES`/`CMDS` choice.
- Pools: one OpenGPU `ForkJoinPool` per JVM (shared by server jobs and the mirror in single player), sized `max(1, cores/2)` as 09 says; the mirror's budget (§1) is accounted separately from the server's 10 ms slice.
- Pause: when a GUI pauses single player (`isGamePaused`, `Minecraft.java:1117`) the server thread stops ticking and no packets flow; the client must not treat the silence as desync.

## 5. Determinism across x86-64 and aarch64, and the CRC32 cost

**Who runs aarch64.** LWJGL 2.9.4 in the instance ships only `natives-windows` (`C:\Games\Minecraft\libraries\org\lwjgl\lwjgl\lwjgl-platform\2.9.4-nightly-20150209\`; upstream also linux/osx x86); lwjgl3ify's launcher patch adds `natives-osx-arm64` and `natives-linux-arm64` (`lwjgl3ify/prism-libraries/patches/net.minecraft.json:327-360`). An aarch64 GTNH client is therefore always the Java 17+/lwjgl3ify leg; Java 8/aarch64 is not a target. The matrix that matters: server x86-64 (JDK 8, 17, 21), client x86-64 (JDK 8, 17, 21) and client aarch64 (JDK 17, 21).

**Basic arithmetic.** JEP 306 (delivered in JDK 17) makes every floating-point operation strict and removes the extended-exponent value set, noting that the looser default existed only because of x87 and that SSE2 "could support strict semantics in a straightforward manner without undue overhead" (openjdk.org/jeps/306). On JDK 8 x86-64 HotSpot already generates SSE2 code, so default and `strictfp` results coincide in practice and `strictfp` makes it a guarantee (06 verification C9 marks this as an inference from JEP 306 plus HotSpot codegen). On aarch64 there was never an extended-precision mode. Java forbids contracting `a*b+c` into a fused multiply-add (`Math.fma` is the only FMA), and HotSpot's auto-vectorizer keeps floating-point add/mul reductions in source order: JDK-8320725 ("AArch64: C2: Add `requires_strict_order` flag for floating-point add and mul reduction") states that using NEON's unordered reduction for auto-vectorized code would violate the Java Language Specification's evaluation-order rules, and JDK-8333964 does the same for RISC-V. Hence `+ − × ÷`, `Math.sqrt` (correctly rounded by spec), comparisons, `float↔int` conversions and all integer/fixed-point work in 09 §3.3 (28.4 edge functions, integer blend, RGB555 LUT) are bit-identical across the matrix, in the interpreter, C1 and C2 alike.

**Transcendentals.** `Math.*` is explicitly non-portable: the aarch64 `Math.cos` stub returned −0.2745… for `cos(1647100)` where 0.7833… is correct because `__kernel_rem_pio2` reduced the argument to 1.8489… instead of `[-π/4, π/4]` (JDK-8210461, fix version 12; the JDK 11 line disabled the sin/cos/log stubs meanwhile, JDK-8211105), and the aarch64 `Math.log` intrinsic was removed for returning −710.99 instead of −744.44 at `4.9E-324`, "correct on Intel x86" (JDK-8210858); the x86 stubs are Intel LIBM-derived and differ from fdlibm by up to 1 ulp. `StrictMath` is specified as the fdlibm algorithms "transliterated into Java"; the port finished in JDK 21 (JDK-8171407 "Port fdlibm to Java, part 2", Fix Version 21, resolved 2023-04-05: sin, cos, tan, asin, acos, atan, atan2, sinh, cosh, tanh, log, log10, expm1, log1p). On JDK 8 and 17 those functions are still native fdlibm C; since JDK-8210416 (and its 8u backport) the JDK builds fdlibm with `-O2`/`-O3 -ffp-contract=off` (or `-mno-fused-madd -fno-strict-aliasing` where unavailable), precisely to keep its results IEEE-exact across compilers. So 09 §3.3's rule "transcendentals through `StrictMath` or own polynomials, never `Math`" is correct and necessary; the safest form for the shader runtime is **own polynomials in `float`** (no dependency on fdlibm's build flags at all, and faster than `StrictMath`'s `double` path), which 09 already permits.

**Residual risks that cannot be verified from here.** (a) Flush-to-zero: a native library (audio, GL driver, LuaJIT's natives) that sets MXCSR FTZ/DAZ or FPCR.FZ on a thread changes subnormal results for Java code on that thread; HotSpot does not reset it. The rasterizer's depth/attribute ranges never produce subnormals, but a user shader can (`exp(-200.0)`); mitigation is structural: a CRC mismatch forces a keyframe and two consecutive mismatches force `TILES` for that display, so divergence degrades the viewer, never corrupts it. (b) Interpreter vs JIT: both executors evaluate the same scalarised IR in the same order with the same `float` ops, and the fuzzer oracle (09 §3.3) is the check. (c) No aarch64 machine was available for this report; the conformance suite must run on an aarch64 CI runner (GitHub-hosted `ubuntu-24.04-arm`/`macos-14`) before the mirror is enabled by default.

**CRC32 per packet [measured]** (`scratchpad/gap12/bench/CrcInflateBench.java`, `java.util.zip.CRC32` over a random buffer, 2,000 iterations after warm-up): 64 KB 0.001 ms, 128 KB 0.002 ms, 512 KB 0.010 ms, 1 MB 0.019 ms (≈ 53 GB/s) on **both** JRE 1.8.0_492 and JDK 25.0.4.1 — the CLMUL intrinsic exists on JDK 8. Even at a tenth of that speed on an old CPU the hash is < 0.2 ms per T3 frame; the per-packet CRC is not a cost. Inflating a stored (incompressible) 512 KB block is 0.11 ms, a realistic 2× deflated T3 frame 1.7–1.8 ms (§1), so a **resync** costs the client ≈ 1.8 ms inflate + ≈ 0.3 ms apply (bench; ≈ 3–5 ms typical) and 200–340 KB of bucket, and the server one keyframe encode (≈ 7 ms deflate at T3 [measured], on the pool).

## 6. Lifecycle of the captured `Context`

**Facts.** A callback's `Context` is the invoking computer's `Machine` (`Machine.invoke` → `component.invoke(method, this, args)`, `Machine.scala:393`; `api/machine/Context.java` exposes `node()`, `isRunning()`, `signal()`, `pause()`, `stop()`, `consumeCallBudget()`). `Machine.signal` takes `state.synchronized` then `signals.synchronized`, returns `false` when the state is `Stopped`/`Stopping` or the queue is full (`maxSignalQueueSize`, 256 in the installed config, 07 §3), and otherwise enqueues and calls `architecture.onSignal()` (`Machine.scala:335-369`), which is a no-op for native Lua (`NativeLuaArchitecture.scala:302`), LuaJ (`LuaJLuaArchitecture.scala:215`) and OC-LuaJIT (`LuaJITArchitecture extends NativeLuaArchitecture`, `OC-LuaJIT/src/main/java/io/github/astronfo/ocluajit/arch/LuaJITArchitecture.java:83`, no override) — so calling it from the OpenGPU pool is safe and never takes the machine monitor, confirming 09 §3.2. Lifecycle events:

- *Computer stops* (user, crash, CPU removed — `Case.scala:112-114`): `stop()` pushes `Stopping` and schedules `close` (`:277-284`); `tryClose` → `close()` clears `state` to `Stopped`, closes the architecture and **clears the signal queue** (`:939-953`), then `node.sendToReachable("computer.stopped")` (`:927-936`). `GraphicsCard.onMessage` resets its buffers on `computer.stopped`/`started` from a neighbour (`GraphicsCard.scala:538-545`).
- *Chunk unload / TE invalidate*: `traits/TileEntity.onChunkUnload`/`invalidate` → `dispose()` (`traits/TileEntity.scala:46-54`) → `traits/Computer.dispose` → `machine.stop()` (`traits/Computer.scala:137-141`); the node network removes the computer node → `Machine.onDisconnect(this.node)` → `close()` (`Machine.scala:684-688`). On reload Forge constructs a **new** TE and OC a **new** `Machine`; the old one is garbage once nothing references it.
- *Card removed or moved*: the driver's `ManagedEnvironment` gets `onDisconnect(node)` with `node == this.node` (precedent `GraphicsCard.scala:600-605`, which drops its screen binding); any later `onConnect` is a new computer.

**Consequences for 09's design.** A `Context` captured by "the last callback" and held by a pool job (a) is simply a `Machine` reference: after `close()` every `signal` returns `false`, harmlessly; (b) is a **strong reference to a dead `Machine`, its host TE and its `World`** if the chunk unloaded — a leak for as long as the job (or a stale field) lives; (c) can be the *wrong* computer if the card was moved between `submit` and completion, unless the move invalidates the job.

**Design (replaces 09 §3.2's "captured by the last callback").**

```
final class OpenGpuCard extends ManagedEnvironment {
  private final AtomicReference<Context> ctx = new AtomicReference<>();  // read on pool threads only inside signalFrame()
  private final AtomicInteger epoch = new AtomicInteger();                 // a bump invalidates every in-flight job
  private final Device device;                                            // owns the ordered pool queue for this card

  // every @Callback (OC worker thread): a reference store, no cost
  ctx.set(context);  int e = epoch.get();  device.enqueue(new FrameJob(this, e, ...));

  // pool thread, on job completion
  void signalFrame(FrameJob job, long frameId, String status) {
    if (job.epoch != epoch.get()) return;                 // card moved / computer stopped / unloaded: drop silently
    Context c = ctx.get();
    if (c == null || !c.isRunning()) return;              // Stopping/Stopped: Machine.signal would return false anyway
    if (!c.signal("opengpu_frame", cachedAddress, frameId, status))   // false: queue full or raced with stop
      device.markNeedsResync();                           // Lua's waitFrame treats a missing signal as a timeout (09 risk 10)
  }

  @Override public void onDisconnect(Node n) { super.onDisconnect(n);
    if (n == node()) invalidate("disconnect"); }           // card removed, computer TE disposed, chunk unloaded
  @Override public void onMessage(Message m) { super.onMessage(m);
    if (node().isNeighborOf(m.source()) && (m.name().equals("computer.stopped") || m.name().equals("computer.started")))
      invalidate(m.name()); }                              // same trigger GraphicsCard uses (GraphicsCard.scala:538-545)

  private void invalidate(String why) { epoch.incrementAndGet(); ctx.set(null); device.cancelPending(); /* handles reset per 09 §3.6 */ }
}
```

Rules: jobs reference the card (bounded by the item's environment lifetime), never the `Context`; `ctx` is cleared on every disconnect/stop so no dead `Machine` is retained beyond the next tick; the epoch makes a job from the previous computer unable to signal the next one; signals are coalesced to one pending per card (09 §3.2) *before* `signal` so a `false` return loses nothing but a timestamp; `node()`/world are never touched from the pool (the address is cached at `onConnect`). Save/load: `invalidate("save")` is not needed — in-flight jobs are already dropped at save (09 §3.6) and the epoch bump at `computer.started`/`onConnect` after load covers the rest. The display TE's own unload only unbinds (`onDisconnect(displayNode)`): resources and the device belong to the card, the display is a sink.

## 7. Decision: mirror in M2, or deferred?

| | Mirror in M2 (09 as written) | Mirror deferred to M3; M2 = `TILES` + A's governor |
|---|---|---|
| Remote 3D at T2 in M2 | lossless, 4–40 KB/s, but only fixed-function content (interpreter too slow for shaders, §1) | lossy/LOD 10–20 fps at ≤ 260 KB/s, any content, zero client CPU |
| Remote 3D at T3 | mirror on: 8.6–13.4 ms per display per tick on typical CPUs; mirror shed: ≈ 1 fps lossless or ≈ 3 fps lossy without LOD | lossy + half-res LOD ≈ 10 fps; lossless only on LAN/SP |
| Risk exposure in v1's first 3D release | determinism load-bearing (09 risk 1), two encodings, residency, resync | none of those; `TILES` codec already exists from M0 |
| M2 size | 6–8 w incl. ≈ 3 w of mirror/transport (09 Q1) | ≈ 4–6 w (+1 w for lossy lineage/LOD pulled from M4) |
| What M3 gains | JIT only | JIT + mirror (which needs the JIT) + CRC conformance incl. aarch64 |

**Recommendation.** Defer the mirror to M3 and ship M2's 3D as `TILES` with A's governor (lossy 4×4 lineage, half-res LOD with hysteresis, server aggregate budget), keeping the mirror's *contracts* in M2 so nothing is thrown away: the `CMDS` encoding and `RESOURCE` residency records are produced and **recorded** (the `:viewer` virtual client, 09 §3.8) even though no client consumes them yet, the determinism rules stay in `:core` from day one, and the single-player bypass (§4) is implemented in M2 because it is needed regardless. The user's Q1 default ("public internet") does not change this: on the internet the mirror only pays off for T2 at modest client cost and for T3 at a cost most clients cannot afford; the governor is what every remote viewer needs first. The mirror then arrives in M3 with the JIT, enabled per display by the client budget, and T3 lossless 3D for remote viewers is honestly an M5 (GL) feature.

**Numeric exit criteria for the mirror (gate to "enabled by default", end of M3).**

1. Replay cost, fixed-function textured scene, 1–2 k triangles, 2× overdraw, JIT path: ≤ 1.6 ms per T2 frame and ≤ 5.5 ms per T3 frame on the bench box (JDK 8), and ≤ 4 ms / ≤ 13 ms on a reference ≈ 2,500 PassMark-ST machine (or scaled by measured single-thread ratio); the same scene with a 30-op user fragment shader ≤ 2× those numbers.
2. Budget enforcement: with `mirrorBudgetMs = 8` and five T3 displays in view, worker time ≤ 10 ms per tick and the render thread's per-frame cost from OpenGPU (upload + swap, MC profiler section) ≤ 1 ms; shedding order follows on-screen size; no `PREFER_TILES` flip during the first 60 frames after a program change (warm-up).
3. Determinism: byte-identical quantized frames server vs mirror over ≥ 10^4 fuzzed frames (interpreter and JIT, 1 vs 8 pool threads) on x86-64 JDK 8/17/21 **and** aarch64 JDK 17/21; CRC-triggered resyncs < 1 per display per 10 minutes in a 1-hour LAN soak with four clients.
4. Resync: a client joining mid-stream is in sync within 2 keyframe intervals; a T3 resync costs the client ≤ 3 ms (bench) and ≤ 340 KB.
5. Memory: ≤ 9 MB heap per T3 mirror, `maxMirrors` LRU respected, total mirror heap ≤ 64 MB with 20 displays subscribed, no growth over a 1-hour soak (heap histogram).
6. Single player / LAN host: zero mirror replays (counter) and zero `CMDS` packets to local-channel viewers.
7. Lifecycle: a test that unloads the computer's chunk, moves the card to another computer and stops/starts the computer while 2 frames are in flight produces no signal to the wrong machine, no exception, and no retained `Machine` (weak-reference check after GC).
