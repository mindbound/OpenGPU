## 1. Summary

**The question is closed: OpenGPU can call the LWJGL2 API `org.lwjgl.opengl.GLContext.getCapabilities()` (plus vanilla `OpenGlHelper` flags) on both legs with one code path. No `GlCaps` interface with one implementation per LWJGL major, and no `glGetString`-based probing, is needed.**

- lwjgl3ify's RFB transformer rewrites every `org/lwjgl/` type reference in mod bytecode to `org/lwjglx/` [V], where a **hand-written shim** `org.lwjglx.opengl.GLContext` / `ContextCapabilities` lives [V]. Its 364 `public boolean` fields (`OpenGL11`…`OpenGL45`, `GL_ARB_*`, `GL_EXT_*`, `GL_KHR_*`, vendor flags) are **populated by reflection from LWJGL3's `GLCapabilities`** for every name both classes share [V].
- Every flag OpenGPU can plausibly gate on exists in LWJGL 2.9.4, in the shim and in LWJGL 3.3.6/3.4.3 (§2.3 table) [V]. What is missing is harmless or avoidable: 14 LWJGL2 fields the shim lacks (GL 4.5-era `GL_ARB_clip_control`, `GL_KHR_robustness`, … — never reference them, see §2.7), 65 legacy vendor/EXT fields that are always `false` under lwjgl3ify (all are GL 1.2–1.4 core functionality; gate on `OpenGL1x` instead), and `OpenGL46`, which LWJGL2 never had.
- The shim object is a **process-wide static snapshot**, not per-thread and not per-context [V]: rebuilt at the end of `Display.create()` on 3.0.25+ [V]; on 2.1.16/3.0.24 it is a one-shot snapshot taken when the class is first used [V]. Vanilla first uses it at `OpenGlHelper.initializeTextures()` (`MC/net/minecraft/client/Minecraft.java:497`), right after `createDisplay()` (`:474`) and before any mod code runs (`:522`), so mod code at construction/pre-init/init/render sees a populated object on every lwjgl3ify version [V].
- Angelica does not special-case `GLContext.getCapabilities` in its redirector and **uses it itself**: `GLStateManager.preInit` stores `GLContext.getCapabilities()` (`ANG@2.2.21/glsm/.../GLStateManager.java:587`) and `RenderSystem`/`Lwjgl2GLRenderBackend` read `OpenGL33`…`OpenGL45` and ten ARB/EXT/KHR flags from it [V]. The Angelica jar carries no `Lwjgl3ify-Aware` manifest attribute and `GLStateManager` is not `@Lwjgl3Aware` [V], so on the Java 21 pack those reads go through the very shim OpenGPU would use. Angelica's SDL-GPU backend feeds the shim through lwjgl3ify's `GLCapabilitiesOverride` [V] — `GLContext.getCapabilities()` is the *designed* probe there.
- OC-GTNH probes `OpenGL13/14/15` and `GL_ARB_multitexture` through the same call (`OC/.../ScreenRenderer.scala:34`, `OC/.../RenderState.scala:11`, `OC/.../client/Proxy.scala:61`; identical in 1.12.64) [V] and ships unchanged on the Java 21 pack (GTNH 2.9.0-RC-2: lwjgl3ify 3.0.37, Angelica 2.2.28, OC 1.12.64-GTNH) [V].
- Replacement for the M0 exit criterion: a one-line log of the probed flags on `runClient` and `runClient21` (a smoke check), not a research gate. Four real pitfalls remain and are design rules, not unknowns (§2.7, §3).

## 2. Findings

### 2.1 How an `org.lwjgl.opengl.GLContext` reference reaches the shim [V]

- `LwjglRedirectTransformer` maps the prefixes `org/lwjgl/` → `org/lwjglx/` (plus JAXB/Pack200/Nashorn/LiteLoader prefixes) in every class whose bytes contain one of the prefixes (`L3IFY/src/main/java/me/eigenraven/lwjgl3ify/rfb/transformers/LwjglRedirectTransformer.java:35-40`, `:42-44`, `:84-85`, `map()` at `:117-130`). It runs after everything else including Mixin (`sortAfter` `:46-49`) and skips a class only when the jar manifest has `Lwjgl3ify-Aware: true` (`:31-32`, `:78-82`) or the class carries `@Lwjgl3Aware`, which aborts the remap of that class (`:139-151`; annotation `L3IFY/src/main/java/me/eigenraven/lwjgl3ify/api/Lwjgl3Aware.java:8-13`). `org.lwjgl.` and `org.lwjglx.` are transformer-excluded in the launch class loader (`L3IFY/src/main/java/me/eigenraven/lwjgl3ify/rfb/Lwjgl3ifyRfbPlugin.java:47-48`).
- Where the renamed reference lands: `org.lwjglx.opengl.{GLContext, ContextCapabilities, Display, Drawable, PixelFormat, ContextAttribs, GLSync, …}` are hand-written (`L3IFY/src/main/java/org/lwjglx/opengl/`, 26 files), while `org.lwjglx.opengl.GL11…GL45`, `ARB*`, `EXT*` etc. are **generated delegating wrappers** with LWJGL2 signatures (254 files in `L3IFY/src/generated/java/org/lwjglx/opengl/`, part of the `main` source set, `L3IFY/build.gradle.kts:112-116`; e.g. `GL11.glEnable` → `org.lwjgl.opengl.GL11.glEnable` at `L3IFY/src/generated/java/org/lwjglx/opengl/GL11.java:808-810`). RetroFuturaBootstrap contains no `lwjglx` logic at all (grep of the 78b6871 clone) — the whole mechanism is the remap plus these wrappers.
- The *un-remapped* names also exist, as **throwing stubs**: `L3IFY/src/generated/java/org/lwjgl/opengl/GLContext.java:5-7` is `getCapabilities() { throw new UnsupportedOperationException(); }` and `L3IFY/src/generated/java/org/lwjgl/opengl/ContextCapabilities.java` is an all-`false` copy of the LWJGL 2.9.4 field list (98 such stub classes). They are what a `@Lwjgl3Aware` class, a `Lwjgl3ify-Aware: true` jar, or a `Class.forName("org.lwjgl.opengl.GLContext")` string lookup gets [V for the first two; the string case is [I]: the transformer overrides no `visitLdcInsn`/`mapValue`, and ASM's `ClassRemapper` rewrites `Type` constants but not plain `String` constants].

### 2.2 What `GLContext.getCapabilities()` returns under lwjgl3ify [V]

`L3IFY/src/main/java/org/lwjglx/opengl/GLContext.java:3-18` (3.0.37):

```java
private static ContextCapabilities contextCapabilities = new ContextCapabilities();
public static ContextCapabilities getCapabilities() { return contextCapabilities; }
/** Rebuild the capabilities from the current GL context or GLCapabilitiesOverride. */
public static void refreshCapabilities() { contextCapabilities = new ContextCapabilities(); }
```

`L3IFY/src/main/java/org/lwjglx/opengl/ContextCapabilities.java:14-36`: if `Display.isCreated() && Display.hasGLContext()`, it takes `GL.getCapabilities()` (LWJGL3, the calling thread's capabilities), iterates `GLCapabilities.class.getFields()`, collects the names starting with `GL_` or `OpenGL` whose value is `true`, and sets the shim field of the same name to `true` by reflection, silently skipping names the shim does not declare (`getField` → `ReflectiveOperationException` ignored). Without a GL context it uses `GLCapabilitiesOverride.get()` (`:26-28`; `L3IFY/src/main/java/me/eigenraven/lwjgl3ify/api/GLCapabilitiesOverride.java:13-28`, default empty set).

Population timing and object model:

- **Static snapshot, process-wide.** One object for the whole process; the same reference is returned on every thread. It is **not** per-thread (LWJGL2 and LWJGL3 both keep capabilities in a `ThreadLocal` and throw off-thread: LWJGL 2.9.4 `GLContext.getCapabilities()` throws `RuntimeException("No OpenGL context found in the current thread.")` when `current_capabilities` is unset, `javap -c org.lwjgl.opengl.GLContext`; LWJGL 3.3.6 and 3.4.3 `GL.getCapabilities()` read `capabilitiesTLS` and `checkCapabilities` throws `IllegalStateException` when `Checks.CHECKS` and null, `javap -c org.lwjgl.opengl.GL`). It is **not** per-context: Minecraft has one GL context; lwjgl3ify builds the snapshot from the main thread's LWJGL3 capabilities.
- **3.0.25 and later** (commit 48547f9 "SDL-GPU and ES support (#324)", 2026-06-13, first tag 3.0.25): `Display.create()` sets `displayCreated = true` inside the main-thread block (`L3IFY/src/main/java/org/lwjglx/opengl/Display.java:327`; `MainThreadExec.runOnMainThread` runs the block inline on the main thread, otherwise blocks on a future, `L3IFY/src/main/java/me/eigenraven/lwjgl3ify/client/MainThreadExec.java:102-109`), then `GL.create(...)`, makes the drawable current (`:341-345`) and calls `GLContext.refreshCapabilities()` (`:352`). Before that point the snapshot is the empty override → all fields `false`; it is never rebuilt again unless `refreshCapabilities()` or `GLCapabilitiesOverride.set()` (`GLCapabilitiesOverride.java:18-23`) is called. `Display.destroy()` clears LWJGL3's TLS capabilities (`Display.java:453-465`) but leaves the shim snapshot in place.
- **2.1.16 and 3.0.24** (`git show 2.1.16:…`, `git show 48547f9^:…`): same reflection loop, but the object is built **once when `GLContext` is first class-initialised**, and the constructor's field initialiser `cap = GL.getCapabilities()` runs outside the try/catch, so a first touch on a thread without a current LWJGL3 context would throw into an `ExceptionInInitializerError` [I from the shown source]. That never happens in practice because vanilla touches it first, on the main thread, after the display exists (next bullet). No `refreshCapabilities()` exists in these versions.
- **Vanilla start-up order** (`MC/net/minecraft/client/Minecraft.java`): `ForgeHooksClient.createDisplay()` `:474` (bare `Display.create()` only in the `catch` fallback `:494`) → `OpenGlHelper.initializeTextures()` `:497`, whose first statement is `GLContext.getCapabilities()` (`MC/net/minecraft/client/renderer/OpenGlHelper.java:74`) → `FMLClientHandler.beginMinecraftLoading` `:522` (mod construction and pre-init, `MC/cpw/mods/fml/client/FMLClientHandler.java:190-243`) → `finishMinecraftLoading` `:597` (init, `:302-311`). Hence on every lwjgl3ify version the snapshot is populated before any mod lifecycle event. Angelica's `MixinForgeHooksClient_CoreProfile.createDisplay` (03 §5) still goes through `Display.create(...)`, so this holds with Angelica too [I].
- `OpenGlHelper`'s own flags (`openGL14`, `framebufferSupported`, `shadersSupported`, …; 03 §5) are computed from the same shim on the Java 21 leg because `OpenGlHelper` is ordinary transformed bytecode; every field it reads (`OpenGL13/14/21/30`, `GL_ARB_multitexture`, `GL_EXT_blend_func_separate`, `GL_ARB_framebuffer_object`, `GL_EXT_framebuffer_object`, `GL_ARB_shader_objects`, `GL_ARB_vertex_shader`, `GL_ARB_fragment_shader`) is in the shim's field list (`ContextCapabilities.java:99-114`, `:133`, `:156`, `:214`, `:241`, `:255`, `:303-309`).

### 2.5 How Angelica treats `GLContext.getCapabilities()` [V]

- **Redirector**: `GLSMRedirector` only rewrites LWJGL method calls whose *name* starts with `gl`/`ngl` (`isUnmappedGlCall`, `ANG@2.2.21/glsm/src/main/java/com/gtnewhorizons/angelica/glsm/redirect/GLSMRedirector.java:74-79`) or that are in its explicit maps (`glMethodRedirects` for `org/lwjgl/opengl/GL*` owners, `:949`; `methodRedirects`, `typeRedirects` `:976`). `getCapabilities` is in none of them; the `AWARE_NON_DISPATCHING` set (`:85-95`) lists only the **LWJGL3** entry points `org/lwjgl/opengl/GL getCapabilities/setCapabilities/getFunctionProvider/create`, `GLCapabilities getAddressBuffer/initialize` and `GLDebugMessageCallback`, and it matters only for `@Lwjgl3Aware` classes (`:967`). So a mod's `GLContext.getCapabilities()` call passes Angelica's transformer untouched (both in the 2.2.8 checkout, `ANG/glsm/.../GLSMRedirector.java:86`, and in 2.2.21), then lwjgl3ify renames it to the shim. The same holds for `org/lwjgl/opengl/ContextCapabilities` field reads.
- **GLSM uses the LWJGL2 API itself**: `public static ContextCapabilities capabilities` (`ANG@2.2.21/glsm/.../GLStateManager.java:86`, `:276`) is assigned `GLContext.getCapabilities()` in `preInit` (`:587`); `RenderSystem` reads `OpenGL40/42/43/44/45`, `GL_ARB_direct_state_access`, `GL_EXT_direct_state_access`, `GL_ARB_tessellation_shader`, `GL_ARB_shader_image_load_store`, `GL_EXT_shader_image_load_store`, `GL_ARB_shader_storage_buffer_object`, `GL_ARB_multi_draw_indirect`, `GL_ARB_buffer_storage`, `GL_ARB_clear_texture` from it (`ANG@2.2.21/glsm/.../RenderSystem.java:91-134`); `Lwjgl2GLRenderBackend` reads `GL_EXT_texture_filter_anisotropic`, `OpenGL33`, `GL_ARB_timer_query`, `OpenGL43/44`, `GL_KHR_debug`, `GL_ARB_debug_output`, `GL_AMD_debug_output` (`ANG@2.2.21/glsm/.../backend/Lwjgl2GLRenderBackend.java:49`, `:77`, `:99`, `:134`, `:1446-1545`). GLSM is compiled against LWJGL2 and Java-8-downgraded (02 §4); the installed `angelica-2.2.21.jar` manifest has no `Lwjgl3ify-Aware` attribute (only `FMLCorePlugin`/`TweakClass`), and `@Lwjgl3Aware` appears only on `lwjgl3-backend` (`Lwjgl3GLRenderBackend`, `MissingDependencySdl`), `tracy-client` (3 classes) and `glsm/shader/{SpirvShaderTranslator,SpirvCompiler}`. Therefore on the Java 21 pack Angelica's own capability reads already go through the lwjglx shim — the strongest available evidence that it works, short of running the pack.
- **SDL-GPU backend** (lwjgl3ify-only, opt-in; 02 §4): with `DisplayEvents.isCreateGLContextEnabled() == false` there is no GL context, `Display.hasGLContext()` is false (`Display.java:109-114`, `:152`) and the shim reads `GLCapabilitiesOverride` (§2.2). `SDLGPURenderBackend.populateGLCapabilities()` sets it to `OpenGL11`…`OpenGL46` plus ~50 extension names (`ANG@2.2.21/sdl-gpu/src/main/java/com/gtnewhorizons/angelica/sdlgpu/SDLGPURenderBackend.java:380-417`; `OpenGL46` is dropped by the shim because it has no such field) and answers `glGetString(GL_VERSION/GL_EXTENSIONS)` from the same advertised set (`:3866-3872`; routed there because GLSM maps `glGetString` → `RENDER_BACKEND.getString`, `GLSMRedirector.java:284`, `GLStateManager.java:5812-5820`). A fabricated LWJGL3 `GLCapabilities` is installed on the thread for `@Lwjgl3Aware` mods (`ANG@2.2.21/sdl-gpu/.../compat/Lwjgl3GLCapabilitiesShim.java:15-44`). So on that leg the LWJGL2-style probe and the string probe agree by construction, and `GLContext.getCapabilities()` is the path Angelica designed for LWJGL2-style mods. (The `org.lwjgl.opengl.GLContext` under `ANG@2.2.21/sdl-gpu/src/glsmSdlStubs/` is a unit-test-only stub, `sdl-gpu/build.gradle.kts:98-100`, `:133-141`.)

### 2.6 OC-GTNH cross-check and production evidence [V]

- OC probes through the LWJGL2 API in three places, unchanged between the 1.12.55 checkout and the 1.12.64 tag: `private val canUseBlendColor = GLContext.getCapabilities.OpenGL14` (`OC/src/main/scala/li/cil/oc/client/renderer/tileentity/ScreenRenderer.scala:34`, import `:18`), `val arb = GLContext.getCapabilities.GL_ARB_multitexture && !GLContext.getCapabilities.OpenGL13` (`OC/src/main/scala/li/cil/oc/util/RenderState.scala:11`), and `if (GLContext.getCapabilities.OpenGL15)` to choose `HologramRenderer` vs its fallback (`OC/src/main/scala/li/cil/oc/client/Proxy.scala:61-64`). The first two are Scala `object` initialisers evaluated on first use (TESR registration in `Proxy.init`, first render), the third runs in `FMLInitializationEvent` — all after `Minecraft.java:497`.
- OC's only lwjgl3ify-specific code is file-upload support (`OC@1.12.64/src/lwjgl3/java/li/cil/oc/integration/lwjgl3ify/FileUploadSupport.java:15-17`, `@Lwjgl3Aware`, compiled against lwjgl3ify 3.0.3 `OC@1.12.64/build.gradle:8-16`, gated on lwjgl3ify `@[3.0.0,)` in `OC/src/main/scala/li/cil/oc/integration/Mods.scala:54`). The installed `OpenComputers-1.12.64-GTNH.jar` manifest has no `Lwjgl3ify-Aware` attribute, so the three probes above are remapped to the shim on the Java 21 pack, where OC 1.12.64-GTNH ships as a `BOTH`-side mod (`manifest-2.9.0-RC-2.json:367-369`). lwjgl3ify itself compiles against OC 1.12.64 for its `InputBuffer` mixin (`L3IFY/dependencies.gradle:67`, `L3IFY/src/main/java/me/eigenraven/lwjgl3ify/mixins/early/oc/OcInputBuffer.java:11`), i.e. OC on lwjgl3ify is a supported, tested combination.
- Not verified: a live run of the Java 21 pack on this machine (no lwjgl3ify instance is installed; the user's instance is Java 8 + LWJGL 2.9.4). The claim "OC's and Angelica's probes work on the Java 21 pack" rests on (a) the source paths above, (b) the pack shipping both mods with these exact code paths, and (c) the absence of any lwjgl3ify-specific capability code in OC. That is the evidence the assignment asked for; a `runClient21` log line (§3) turns it into a measurement at zero cost.

### 2.7 Pitfalls that remain (design rules, not unknowns)

1. **Never opt OpenGPU out of the lwjgl3ify remap.** No `@Lwjgl3Aware` on any class that touches `org.lwjgl.*`, no `Lwjgl3ify-Aware: true` in the jar manifest, no reflective lookups by the string `"org.lwjgl.opengl.…"`: all three resolve `GLContext.getCapabilities()` to the generated stub that throws `UnsupportedOperationException` (§2.1) [V/I]. 02 §5 rule 1 ("never exclude `opengpu.client.*` from transformation") already covers Angelica; this extends it to lwjgl3ify.
2. **Only read fields in the all-three set** (§2.3). The 14 LWJGL2-only names compile and run on Java 8 but throw `NoSuchFieldError` under lwjgl3ify. Add a unit test that lists every `ContextCapabilities` field name OpenGPU references (e.g. by scanning `GlCaps` with ASM in `:core` tests) and asserts membership in a checked-in copy of the shim's field list (`L3IFY/src/main/java/org/lwjglx/opengl/ContextCapabilities.java:38-401`).
3. **Thread semantics differ, so adopt the stricter one.** The shim can be read from any thread; LWJGL 2.9.4 throws off the render thread. `GlCaps` therefore fills itself on the render thread only (first `TileEntitySpecialRenderer` call, or `FMLInitializationEvent` on the client — both after `Minecraft.java:497`) and stores primitives; it never stores the `ContextCapabilities` object (on 3.0.25+ a reference captured before `Display.create()` would stay all-`false`; on 2.1.16/3.0.24 a first touch from a coremod/tweaker thread would break the class, §2.2).
4. **Legacy flags are always `false` on lwjgl3ify** (§2.3). Gate on `OpenGL12`/`OpenGL14` for packed pixels, 3-D textures, fog-coord, LOD bias, mipmap generation; use `GL_EXT_texture_filter_anisotropic`, not the ARB name; treat `OpenGL45` as the ceiling (`OpenGL46` is invisible on both legs).

### 2.8 Is `glGetString`-based probing still needed?

No. `glGetString(GL_VERSION)`/`GL_EXTENSIONS` would go through the same remap (`org.lwjglx.opengl.GL11.glGetString`, which additionally guards against a missing context, `L3IFY/src/generated/java/org/lwjglx/opengl/GL11.java:1004-1018`) and, under Angelica, through GLSM to the backend's cached strings (§2.5), so it carries no information the shim lacks and adds string parsing. Keep `glGetString(GL_VERSION/GL_RENDERER/GL_VENDOR)` as **log output only** (bug reports; it is also what `Minecraft.java:2613` does for the snooper). The `GL_CONTEXT_PROFILE_MASK` read for core-profile detection (03 §5 rule 8) is orthogonal and stays.

## 3. Recommended `GlCaps` (replaces 03 §5 rule 8 and 08-B §5.6's interface)

```java
// opengpu.client.render.GlCaps — one class, no interface, no per-LWJGL implementations
public final class GlCaps {
    public final boolean gl14, gl15, gl20, gl21, gl30, gl33;          // OpenGL1x/2x/3x flags

    public final boolean angelica, sdlGpu;   // Loader.isModLoaded("angelica"); BackendManager/system property (02 §4)
    public final String version, renderer, vendor;  // glGetString, logged once, never branched on
    private static volatile GlCaps instance;
    /** Render thread only; first call after Minecraft.startGame has run OpenGlHelper.initializeTextures(). */
    public static GlCaps get() { ... lazily build from GLContext.getCapabilities() + OpenGlHelper ... }
}
```
