# 10 — Gap: the GTNH pack's shipped `OpenComputers.cfg` versus the user's instance, and what OpenGPU's runtime targets really are

Research date: 2026-10-08. Sources: the GTNH modpack repository (`config/OpenComputers.cfg` at `master`, `2.8.4`, `2.9.0-beta-3`, `2.9.0-RC-2`, fetched 2026-10-08 into the session scratchpad), the GitHub API for the pack's and the OC fork's commit history, the user's live config `C:\Games\Minecraft\instances\Main\minecraft\config\OpenComputers.cfg` (80 062 bytes, modified 2026-10-06 18:56; cited as `CFG:line`), the local OC-GTNH checkout `C:\Users\astro\Downloads\OpenComputers-GTNH` (single-commit clone of f83bd95 = tag 1.12.55-GTNH; cited as `OC/path:line`), the scratchpad clone at tag 1.12.64-GTNH (commit 1e4559ff), the installed `OpenComputers-1.12.64-GTNH.jar` (its `application.conf` extracted to the scratchpad), ocelot-brain and OC-LuaJIT. "Verified" = read in source or in the fetched file; "inference" = derived, confidence stated. Nothing was run in-game; the one conclusion that rests on code reading alone (F4) says so and gives a two-minute verification recipe.

## Summary

1. **The pack ships OC's own defaults, not the user's numbers.** On `master`, `2.8.4` (latest numbered stable, 2025-12-23), `2.9.0-beta-3` (2026-09-06) and `2.9.0-RC-2` (2026-10-04, byte-identical to `master`): `callBudgets=[0.5, 1, 1.5]`, `vramSizes=[1, 2, 3]`, `ramSizes=[192, 256, 384, 512, 768, 1024]`, `maxTotalRam=67108864`, `ramScaleFor64Bit=1.8`, `threads=4`, `timeout=5`, `defaultLua53=false`, `enableLua53=true`, `enableLua54=false`, `allowBytecode=false`, `allowGC=false`, `disableUserdata=false`, `disableMemoryLimit=false`, `registerLuaJArchitecture=false`, `forceLuaJ=false`, `maxNetworkClientPacketDistance=0`, `maxWirelessRange=[16, 400]`, `maxScreenTextRenderDistance=20`; `maxSignalQueueSize` is `1024` on `master`/`2.9.0-RC-2` (commit 9ad74cedbe, 2026-09-30, PR #27079) and `256` on `2.8.4` and `2.9.0-beta-3`. Every one of these except `defaultLua53` and `maxSignalQueueSize` equals the jar default in `application.conf` (F1, F2). [verified]
2. **The user's instance is hand-tuned on eleven keys that matter to OpenGPU**: `callBudgets=[1,2,4]`, `vramSizes=[1,2,4]`, `ramSizes=[256..8192]`, `maxTotalRam=134217728`, `defaultLua53=true`, `enableLua54=true`, `allowBytecode=true`, `allowGC=true`, `registerLuaJArchitecture=true`, `maxWirelessRange=[16,512]`, `maxHandles=64` (plus `maxSignalQueueSize=256`, which matches `2.8.4` but not `2.9.0`). Reports 00/04/07 and the synthesis 09 quote these as the environment; they are the user's environment only (F3). [verified]
3. **`defaultLua53=false` does not make a crafted CPU run Lua 5.2 on any GTNH OC build the pack has shipped.** Upstream commit 7bd148367c (payonel, 2020-05-14, "put 5.3 above 5.2 so it is the first selected architecture") registers `NativeLua53Architecture` before `NativeLua52Architecture`; an unstamped CPU resolves to `api.Machine.architectures.head` (`OC/.../DriverCPU.scala:59`), which is 5.3 whenever `enableLua53=true`; `defaultLua53` only controls whether crafting *stamps* the stack with 5.3, which is now redundant (`OC/.../LuaStateFactory.scala:45-55`). That commit is an ancestor of every GTNH tag checked (1.7.5.11-GTNH through 1.12.64-GTNH) and the pack's "make 5.2 the default lua version" commit (1045b5f3bf, 2022-05-10, PR #10252) changed only that one flag. So on the pack a fresh CPU runs **Lua 5.3**, 5.2 is one sneak-right-click (or one `computer.setArchitecture("Lua 5.2")`) away, and 5.4 is not registered at all (F4, F5). [verified at source; not observed in-game — see F4 for the recipe]
4. **Therefore the primary runtime stays Lua 5.3, with Lua 5.2 a co-equal, mandatory target** — not because the pack makes it the default, but because the pack maintainers *intend* it to be (PR #10252, motivated by issue #8048: the debug card's number handling breaks on 5.3, so GTNH players are told to switch to 5.2), because OC-LuaJIT presents itself as 5.2, and because a one-line fork fix could make the pack's intent effective at any time. Lua 5.4 drops to a user-instance-only leg; LuaJ is a user-instance/no-natives fallback (F4, F5, F9).
5. **05's "wrong" verdict on OC-LuaJIT's `ocelot-brain.md:40` must be rewritten, not withdrawn.** OC-LuaJIT's "GTNH's is 5.2" correctly describes the pack's *configured* default and the maintainers' intent; 05's "5.3 is the GTNH in-game default" correctly describes what a fresh CPU *runs* — but 05 proved it with the wrong evidence (the jar default `defaultLua53: true` and the user's `CFG:213`, neither of which is the pack), and the pack flag it never looked at is `false`. The accurate statement is in §"Implications" below (F4, F9).
6. **T1 Lua RAM on the pack is 192 KB apparent per stick, 192–512 KB per T1 case** (two `Memory(Tier.One)` slots, `OC/common/InventorySlots.scala:8,11`; T1 items are RAM levels 1–2 = 192/256 KB). The real allocator cap is `kernelMemory + ceil(apparentBytes × 1.8)` (`OC/.../NativeLuaArchitecture.scala:152-166, :317`), i.e. 353 894 B of user headroom above the kernel for one 192 KB stick, and Lua sees the apparent figure. What OpenOS itself leaves free at 192 KB was **not measured** here (F6). 09 §3.2's "T1 programs use resident resources and ≤ 16 KB readback chunks" survives arithmetically (a 16 KB result is ~8.9 KB apparent, 4.6 % of 192 KB) but 09 Q9's premise "your `ramSizes` start at 256 KB" and "3D assumes ≥ 1 MB" need restating in pack terms: 1 MB apparent is a T2 case with two 512 KB sticks or any T3 case (F6).
7. **Budget tables: tune against `[0.5, 1, 1.5]` first**; it is both the pack's and OC's default, and `[1,2,4]` is a local override. Under 09 §3.2's proposed charges, T1 affords 4 `present`/tick (80/s), 32 simple-2D ops/tick (640/s) and 2 readback chunks/tick — half of what every report computed from the user's table (F7).
8. **`allowBytecode=false` on the pack** forces `load(...,"t")` (`OC/.../machine.lua:755-756`), so `load(string.dump(f))` fails; 04's suggested LuaJIT behavioural probe ("whether `load` accepts a `string.dump` chunk") is unusable on the pack, and `opengpu.lua` must never ship or cache bytecode (F8).
9. **Ocelot test matrix**: pin 5.3 and 5.2 as the two must-pass legs (both explicit via `setArchitecture`, as 05 §3 already requires), OC-LuaJIT third, 5.4 as a user-instance-only leg; `maxSignalQueueSize` must be tested at 256 (the floor, `OC/Settings.scala:486`, the user's and 2.8.4's value) even though 2.9.0 ships 1024; `vramSizes[2]=3`, not 4 (F9).

### F4. How a crafted CPU's architecture is chosen, and why `defaultLua53=false` is inert

Code path (1.12.55 checkout; the 1.12.64 scratchpad clone's `Proxy.scala:74-91` is byte-identical, and the GitHub compare `1.12.55-GTNH...1.12.64-GTNH` lists none of these files; the compare `1.11.20-GTNH...1.12.55-GTNH` (56 commits, 300 files) touches `application.conf` and `machine.lua` but not `Proxy.scala`, `DriverCPU.scala`, `LuaStateFactory.scala`, `Machine.scala`, `CPULike.scala` or `ExtendedRecipe.scala`, so the finding holds for both OC versions the pack ships):

1. Registration order, `OC/common/Proxy.scala:74-91`: `if (LuaStateFactory.include53) add(NativeLua53Architecture)`; `if (include54) add(NativeLua54Architecture)`; `if (include52) add(NativeLua52Architecture)`; `if (includeLuaJ) add(LuaJLuaArchitecture)`; then `api.Machine.LuaArchitecture = if (forceLuaJ) LuaJ else api.Machine.architectures.head`. The gates (`OC/server/machine/luac/LuaStateFactory.scala:33-43`): `includeLuaJ = !isAvailable || forceLuaJ || registerLuaJArchitecture`; `include52 = Lua52.isAvailable && !forceLuaJ`; `include53 = Lua53.isAvailable && enableLua53 && !forceLuaJ`; `include54 = Lua54.isAvailable && enableLua54 && !forceLuaJ`; `default53 = include53 && defaultLua53`.
2. The registry keeps insertion order: `object Machine … // Keep registration order, to allow deterministic iteration of the architectures. val checked = mutable.LinkedHashSet…; override def architectures = checked.toSeq` (`OC/server/machine/Machine.scala:1072-1088`).
3. Resolution for a CPU stack, `OC/integration/opencomputers/DriverCPU.scala:43-60`: if the stack has an `oc:archClass` tag, that class (with the old abstract `NativeLuaArchitecture` name migrated to `api.Machine.LuaArchitecture`, :46-49); otherwise `api.Machine.architectures.headOption.orNull` (:59). `setArchitecture` writes `oc:archClass`/`oc:archName` (:62-67). The machine reads it in `onHostChanged` through `driver.architecture(stack)` (`OC/server/machine/Machine.scala:130-131`), and the item tooltip shows the same value (`OC/common/item/traits/CPULike.scala:25-26`).
4. The only effect of `defaultLua53`: `LuaStateFactory.setDefaultArch(stack)` stamps the stack with 5.3 *if* `default53`, else leaves it untouched (`LuaStateFactory.scala:45-55`). Callers: `ExtendedRecipe.scala:83-85` (OC's own crafting recipes for CPUs/APUs), `Items.scala:196,216,253,290` (creative-tab kits), `SpawnComputerCommand.scala:79-80` (`/oc_sc`).

Put together, with the pack's values (`enableLua53=true`, `enableLua54=false`, `forceLuaJ=false`, `registerLuaJArchitecture=false`, natives present): `architectures = [Lua 5.3, Lua 5.2]`, `LuaArchitecture = Lua 5.3`, and a freshly crafted CPU — unstamped because `defaultLua53=false` — resolves to the head, **Lua 5.3**. With `defaultLua53=true` (user instance, jar default) the stack is stamped 5.3 and resolves to the same thing. The flag changes nothing observable. (Inference, medium confidence: GTNH crafts OC CPUs in GregTech machines whose recipe outputs are plain stacks, so they never pass through `ExtendedRecipe` at all and are unstamped under either setting; GT5-Unofficial's recipe sources were not checked.)

History that explains the mismatch between the config comment and the behaviour (upstream MightyPirates/OpenComputers, `master-MC1.7.10`; the GTNH fork's history of `Proxy.scala` is the same list of commits, so the fork never modified this block):
- aba2225fa5 (payonel, 2018-03-02, "add config option to craft lua 5.3 cpu by default … only affects cpus and apus when crafted"): introduced `defaultLua53` and registered **5.2 first, then 5.3**, with `LuaArchitecture = architectures.head`. Under that order `defaultLua53=false` genuinely meant "5.2 unless stamped". The config comment ("If enabled, a crafted CPU will first be the Lua 5.3 architecture") dates from here and was never updated.
- dd63789b81 (2019-11-15): `includeLuaJ`/`luajRequested` gates; `_VERSION` sandbox mapping.
- 7bd148367c (payonel, 2020-05-14, "put 5.3 above 5.2 so it is the first selected architecture"): swapped the two `add` blocks. 66bcd3f46a (same day, "fix cpu to use default lua arch (5.3)"): evaluates `include52` first to work around a JNLua static-initialiser bug but keeps 5.3 registered first.
- ac4d93589a (2022-09-04, "Add Lua 5.4 support…"): inserted 5.4 between them.
- Neither 2020 commit is in upstream `v1.7.5` (tag commit 2019-11-16; compare `7bd148367c...v1.7.5` = behind by 32), but both are ancestors of every GTNH tag checked: `1.7.5.11-GTNH` (ahead by 101), `1.7.5.20-GTNH`, `1.7.5.30-GTNH`, `1.7.5.32-GTNH`, `1.11.20-GTNH` (ahead by 673), `1.12.64-GTNH` (ahead by 736).
- Pack side: issue #8048 (2021-06-13, "debug card impacted by the lua version": `setNBT`-style number arguments fail on 5.3, workaround "putting back lua 5.2"; links upstream #2448), then commit 1045b5f3bf / PR #10252 (boubou19, merged 2022-05-10): "finally adress #8048: lua will by default be 5.2 but users will still be able to use 5.3 and newly crafted cpus will need to be changed to 5.3 manually, the same way it needs to be changed to 5.2 currently." The diff is the single line `defaultLua53=true` → `false`. No later pack or fork issue mentions the default (GitHub issue search over both repositories for "Lua 5.3", "Lua 5.2", `defaultLua53`: only #8048 and #10252).

Confidence: the code reading is unambiguous and was cross-checked against ocelot-brain, which carries the same logic (`totoro/ocelot/brain/Ocelot.scala:51-57` registers 5.3, 5.4, 5.2 in that order; `MachineAPI.scala:49` falls back to `architectures.headOption`). It has **not** been observed in-game. Verification recipe (two minutes, in a throwaway copy of the user's instance, since this research may not modify the live one): set `defaultLua53=false`, start the game, craft or `/give` a CPU with no NBT, read the tooltip's "Architecture" line or run `computer.getArchitecture()` — the prediction is `Lua 5.3`.

### F5. Switching in-game

- Sneak-right-click with the CPU/APU in hand cycles through `driver.allArchitectures` (`OC/common/item/traits/CPULike.scala:29-46`; `allArchitectures = api.Machine.architectures.toList`, `DriverCPU.scala:41`; `APU` mixes in `CPULike`, `OC/common/item/APU.scala:10`). On the pack the cycle is `Lua 5.3 → Lua 5.2 → Lua 5.3…`; on the user's instance `Lua 5.3 → Lua 5.4 → Lua 5.2 → LuaJ → …`.
- From Lua: `computer.getArchitectures()`, `computer.getArchitecture()`, `computer.setArchitecture(name)` (`OC/server/machine/luac/ComputerAPI.scala:116-159`; sandbox wrappers `machine.lua:1435-1447`). `setArchitecture` writes the tag and returns `true`; the new architecture is instantiated on the next `onHostChanged` (`Machine.scala:130-156`), i.e. it is a restart-time change, not a live one.
- Lua 5.4 cannot be selected on the pack by either route (`include54` is false, so it is never registered). LuaJ cannot be selected on the pack unless the natives fail to load (`includeLuaJ = !isAvailable || …`) — the silent-fallback hazard OC-LuaJIT's `ocelot-brain.md:40-42` documents. [verified]

### F6. T1 RAM on the pack and what it means for command buffers and readback

- Slots: a T1 case has two `Memory(Tier.One)` slots (`OC/common/InventorySlots.scala:8,11`), T2 two `Memory(Tier.Two)` (:18-19), T3 two `Memory(Tier.Three)` (:30-31). T1 RAM items are levels 1–2, T2 levels 3–4, T3 levels 5–6 (`application.conf:239-241` comment; `DriverMemory.scala:14-18` indexes `ramSizes` by level). On the pack: T1 case 192–512 KB, T2 384–1024 KB, T3 768–2048 KB apparent. On the user's instance: 256 KB–1 MB, 1–4 MB, 4–16 MB.
- Cap: `setTotalMemory(kernelMemory + ceil(memoryBytes × ramScale))` with `memoryBytes = Σ amount(stack) × 1024` and `ramScale = 1.8` on a 64-bit JVM (`OC/server/machine/luac/NativeLuaArchitecture.scala:152-166, :317`; `ramScaleFor64Bit=1.8` on both configs). One 192 KB stick therefore gives 353 894 bytes of real allocator headroom above the kernel, and `computer.totalMemory()`/`freeMemory()` report the apparent (÷1.8) figures (`application.conf:252-264` comment). `kernelMemory` is whatever `machine.lua` holds after boot and is *added* to the cap, not charged against it (`:207-222`). OC-LuaJIT measured, on ocelot-brain with a 1024 KB stick, `kernelMemory=322521 totalMemory=2209958 freeMemory=1856649` (`OC-LuaJIT/docs/research/memory-accounting.md:293`; 322 521 + 1 024 × 1 024 × 1.8 = 2 209 958, confirming the formula).
- **Not measured**: what OpenOS leaves free at 192 KB and 256 KB. No authoritative figure was found (ocdoc's memory/CPU pages give no sizes; OC-LuaJIT's harness always uses a 1024 KB stick, `OcljSmoke.scala:3690-3990`). This blocks a numeric T1 cap; it is an M0 measurement (boot OpenOS in `:ocelot-harness` with `Memory(Tier.One)` and read `computer.freeMemory()` at the shell).
- Arithmetic that does hold (inference, high confidence): a 16 KB `readPixels` result is a 16 KB real allocation = ~8.9 KB apparent = 4.6 % of a 192 KB stick, so 09 §3.2's T1 cap of 16 KB per call is affordable; a 1 000-triangle fixed-point command buffer (3 000 vertices × 12 B ≈ 36 KB) built with `table.concat` transiently needs roughly 2–3× that in Lua (pieces plus result), i.e. ~70–110 KB real ≈ 40–60 KB apparent — not viable on a single 192 KB stick once OpenOS is resident, which is why 09's "3D assumes ≥ 1 MB" should be kept but restated: on the pack that means a T2 case with two 512 KB sticks or any T3 case. The 2D product (resident resources, ≤ 16 KB readback, sub-KB command buffers) is the only tier that can promise to run on one T1 stick, and even that promise is conditional on the unmeasured OpenOS baseline.

### F7. Budget arithmetic under the pack's table

`maxCallBudget` is the mean of `getCallBudget` over the CPU and every RAM stick, each returning `callBudgets(tier)` (`OC/server/machine/Machine.scala:123-126`; `DriverCPU.scala:69`; `DriverMemory.scala:40`), reset once per tick (`:532`). With the pack's `[0.5, 1, 1.5]` and 09 §3.2's proposed charges: `present` at 1/8, 1/16, 1/32 → 4, 16, 48 presents per tick (80/320/960 per second; the 10/20/20 fps tier targets need 0.5–1 per tick, so this is slack, not a wall); simple-2D at 1/64..1/256 → 32, 128, 384 ops per tick at T1..T3 (OC's own `gpu.set` numbers, `GraphicsCard.scala:66`, which is where 04 §2's "640…20,480 set/s" came from — those figures already assumed 0.5/1.0/1.5); readback at 1/4 per 64 KB → 2 chunks per tick at T1. Every figure is exactly half of what the same charges give on the user's `[1,2,4]` at T1 and 0.5–0.375× at T2/T3. A mixed machine (T1 CPU, two T2 sticks) runs on the mean, 0.83. The raw direct-call cost is `1/limit` with `limit() default Integer.MAX_VALUE` (`OC/api/machine/Callback.java:88`), so unbudgeted direct calls remain effectively free on both tables; only `consumeCallBudget` charges matter. [verified mechanics; the per-tick counts are arithmetic on 09's proposed costs]

### F8. `allowBytecode`, `allowGC`, LuaJ

- `allowBytecode=false` (pack) → `machine.lua:755-756` forces `mode = "t"` for every `load`, so `load(string.dump(f))` raises on the pack; it works only on the user's instance (`CFG:203 true`). 04 §5/§6's LuaJIT probe idea "whether `load` accepts a `string.dump` chunk" and 04 §7 item 8's "bytecode is … `allowBytecode`-gated, not refused outright" must be read as: refused on the pack. `opengpu.lua` must be shipped and cached as source only; `string.pack` detection via `load()` of a *source* chunk (09 §3.2) is unaffected.
- `allowGC=false` (pack) → user `__gc` metamethods are stripped; 09's integer-handle design already assumes no `__gc` (04 §6), so no change.
- `registerLuaJArchitecture=false` (pack) → LuaJ is not a selectable architecture; it appears only if the natives fail to load. 09 §3.6's "LuaJ (no persistence) gets `opengpu_reset` on every reboot" remains correct but is a fallback path, not a pack target; the LuaJ correctness pass in M3 stays, at lower priority. [verified]

### F9. Restated runtime targets and test-matrix priority

| Runtime | Pack 2.8.4 / 2.9.0 | User instance | Role for OpenGPU |
|---|---|---|---|
| Lua 5.3 | what a fresh CPU runs (F4); selectable | fresh-CPU default (stamped) | **Primary** (performance targets set here) |
| Lua 5.2 | selectable, one click; the maintainers' declared default (PR #10252) | selectable | **Co-primary, mandatory**: no integer subtype, numbers arrive as `Double` (04 §1), no `string.pack`, `bit32` present; the slower encoder path, so it also needs an M0 encode figure |
| OC-LuaJIT | not shipped by the pack; user addon | installed (ocluajit-a4994e6) | Third leg; presents `_VERSION "Lua 5.2"`; detection must not rely on `string.dump` (F8) |
| Lua 5.4 | **unavailable** (`enableLua54=false`) | selectable | User-instance-only leg; never a pack target |
| LuaJ | only if natives fail | selectable | Fallback correctness pass |

The ocelot matrix should therefore pin 5.3 *and* 5.2 explicitly as must-pass (ocelot's own default config has `defaultLua53: true`, `enableLua54: true`, `ocelot-brain/src/main/resources/application.conf:228-236`, and the same head-first fallback, so an unpinned ocelot run is 5.3 — fine as long as it is asserted, which is 05 §3's rule and OC-LuaJIT's `guard()` practice). Pinning 5.2 *first* is not needed; pinning it *at all* is, and it is what 05 §3 already specifies ("5.3 … 5.2 (LuaJIT-compat profile) and 5.4, each pinned explicitly").

On 05's "wrong" verdict (05 §Verification "Additional finding: Lua default", and design implication 4 at 05:136): OC-LuaJIT's `docs/research/ocelot-brain.md:44` ("ocelot-brain's default is Lua 5.3; GTNH's is 5.2") and `docs/roadmap.md:64` ("ocelot defaults to 5.3, GTNH ships 5.2") are accurate about the pack's *configured* default and about what a GTNH player is told to use; they are inaccurate, by the code in F4, about what an unmodified fresh CPU *runs*. 05's "5.3 is the GTNH in-game default" is accurate about the latter but cited the jar default and the user's config as evidence, neither of which is the pack. Replace both with the F4 statement. OC-LuaJIT's choice to pin `NativeLua52Architecture` for its own comparisons remains sound for its purpose (its target is a 5.2-compatible surface).
