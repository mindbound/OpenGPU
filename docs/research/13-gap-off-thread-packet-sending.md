## Summary

1. **`FMLEventChannel.send*` and `SimpleNetworkWrapper.send*` are not safe to call from two threads on the same channel [V].** Each `sendX` is three separate operations on one shared `FMLEmbeddedChannel`: set the `FML_MESSAGETARGET` attribute, set the `FML_MESSAGETARGETARGS` attribute, `writeAndFlush` (`MC/cpw/mods/fml/common/network/FMLEventChannel.java:135-140`). The embedded channel's event loop reports `inEventLoop() == true` for every thread (`EmbeddedEventLoop.java:102-110`), so Netty runs the outbound pipeline synchronously on the calling thread (`DefaultChannelHandlerContext.java:693-701`); `FMLOutboundHandler.write` then reads the two attributes back (`FMLOutboundHandler.java:257-262`). Two concurrent callers therefore interleave at attribute granularity: a packet can be routed with the other caller's target (both `PLAYER` → silently misdelivered), or with a mismatched target/argument pair (`validateArgs` throws `RuntimeException`, `:98-104`). The targets `ALL`, `DIMENSION` and `ALLAROUNDPOINT` additionally iterate the server-thread-owned `playerEntityList` (`:129`, `:158`, `:193`). The underlying Netty pipeline state (`ChannelOutboundBuffer`, `inFlush0`) is also unsynchronised, but for every real target the message never reaches it, so that race is unobservable in practice (§1.3).
2. **`NetworkManager.scheduleOutboundPacket(Packet)` is safe from any thread [V].** It is the path vanilla uses for every packet the server thread sends, and the server thread is never the Netty event loop, so the "foreign thread" branch (`MC/net/minecraft/network/NetworkManager.java:185-200`, `eventLoop().execute(...)`) is the normal one. The only state it touches is a `ConcurrentLinkedQueue`, atomic channel attributes, a once-written `channel` field and the event loop's `LinkedBlockingQueue` (§1.5). The actual `writeAndFlush`, the `FMLProxyPacket → S3FPacketCustomPayload` conversion in `NetworkDispatcher.write` (`NetworkDispatcher.java:428-442`) and the serializers all run on the event loop thread. `FMLOutboundHandler` itself ends in exactly this call (`sendProxy`, `NetworkDispatcher.java:363-366`), so the FML channel adds nothing but the recipient selection and the race.
3. **The `Machine.beep` precedent in 07 §1 is false, but OC does send on its FML channel from worker threads [V].** `Machine.beep` is `@Callback(doc = ...)` with no `direct` element (`Machine.scala:456-457`; bytecode of the installed jar shows `Callback(` with no `direct=` element), so it runs in `Machine.update()` on the server thread. The real precedent is disk activity: `FileSystem.exists/size/isDirectory/lastModified/open/read/write` and `Drive.readSector/writeSector/readByte/writeByte` are `direct = true` (`FileSystem.scala:92-112, 157-237`; `Drive.scala:93-133`; installed-jar bytecode: `read` `direct=true limit=15`, `write` `direct=true`, `open` `direct=true limit=4`, `exists` `direct=true`, `readSector` `direct=true`) and call `diskActivity()` → `ServerPacketSender.sendFileSystemActivity` → `PacketBuilder.sendToPlayersNearHost` → `OpenComputers.channel.sendTo(packet, player)` (`FileSystem.scala:362-367`, `Drive.scala:215-220`, `server/PacketSender.scala:132-169`, `common/PacketBuilder.scala:72-123`). OC knows these run concurrently — the rate-limit cache is built with `concurrencyLevel(Settings.get.threads)` (`PacketSender.scala:137`) — and tolerates the resulting misrouting because the packets are rate-limited to one per 500 ms per disk (installed `OpenComputers.cfg:754`) and declared non-essential (`application.conf:1448-1449`). Every other `PacketSender` call in `server/component/*.scala` and `Machine.scala` is on the server thread (§2.1 table). OC's own screen path is the opposite pattern: mutate under a lock from the worker, send once per tick from the server thread (`TextBuffer.scala:68-79, 158-161`; `Hologram.scala:116-120, 396-415`).
4. **Hodgepodge 2.7.216 and lwjgl3ify (commit `c87172b`, 2026-10-04) do not change outbound packet threading [V].** Hodgepodge's network mixins touch `processReceivedPackets` (inbound drain), `FMLProxyPacket.processPacket` exception handling, `NetworkDispatcher` fallback lookup, `Bootstrap.checkAddress`, TCP_NODELAY, and the `S3FPacketCustomPayload` constructor (size cap → `packetSizeLimit=268435456`, channel-name ≤ 20 chars). None touches `scheduleOutboundPacket`, `dispatchPacket`, `FMLOutboundHandler`, `FMLEmbeddedChannel` or `EmbeddedChannel`. lwjgl3ify has no network mixin at all.
5. **Verdict for OpenGPU: send frame packets from the OpenGPU pool thread through `NetworkManager.scheduleOutboundPacket`, with the recipient list chosen on the server thread; never call `FMLEventChannel.send*` off the server thread.** Exact path in §4.2. This removes the 0–50 ms (avg 25 ms) wait for the display's next `update()` that 07 §1 counted — **[derived]** Lua-call→pixels on LAN drops from ≈ 35–60 ms to ≈ 10–30 ms average — at the cost of tick-atomic ordering only: per-connection order is still the order of `execute()` calls, so the stream must be self-sequenced (display id, generation, frame id), which 09 §3.4 already requires. 09 §3.5 should promote this from "later measured optimisation" to the M0 design with a config fallback; the runtime test 03 asked for (integrated and dedicated server) stays in M0 but is now a confirmation, not an open question.

## 1. The Forge 1.7.10 server→client send path, line by line

### 1.1 `FMLEventChannel.send*` and `SimpleNetworkWrapper.send*` are three non-atomic steps [V]

`FMLEventChannel` holds one `FMLEmbeddedChannel` per logical side (`FMLEventChannel.java:28`, created by `NetworkRegistry.newChannel` at `:75`; `NetworkRegistry.java:141-157` builds one per `Side`). Every server-side send is the same shape:

```java
// FMLEventChannel.java:135-140
public void sendTo(FMLProxyPacket pkt, EntityPlayerMP player) {
    channels.get(Side.SERVER).attr(FMLOutboundHandler.FML_MESSAGETARGET).set(FMLOutboundHandler.OutboundTarget.PLAYER);
    channels.get(Side.SERVER).attr(FMLOutboundHandler.FML_MESSAGETARGETARGS).set(player);
    channels.get(Side.SERVER).writeAndFlush(pkt).addListener(ChannelFutureListener.FIRE_EXCEPTION_ON_FAILURE);
}
```

`sendToAll` (`:123-127`, target `ALL`, no args), `sendToAllAround` (`:147-152`, `ALLAROUNDPOINT` + `TargetPoint`), `sendToDimension` (`:159-164`, `DIMENSION` + `Integer`) and `sendToServer` (`:170-174`) are identical in structure; `SimpleNetworkWrapper` does the same on its own pair of channels (`simpleimpl/SimpleNetworkWrapper.java:179-182, 192-196, 206-210, 220-224, 233-236`) with the `FMLIndexedMessageToMessageCodec` encoder in front of the outbound handler. `fireRead`'s reply path sets `REPLY` on the *connection's* channel context instead (`FMLEventChannel.java:104-108`) and is not relevant here.

### 1.2 The embedded pipeline runs on whichever thread calls it [V]

`FMLEmbeddedChannel extends EmbeddedChannel` (`FMLEmbeddedChannel.java:20`); its constructor sets the `FML_CHANNEL`, `CHANNEL_SOURCE` and `MOD_CONTAINER` attributes and inserts `FMLOutboundHandler` as the first (outermost) handler (`:25-32`). `EmbeddedChannel` owns a private `EmbeddedEventLoop` (`EmbeddedChannel.java:51`) whose `inEventLoop()` and `inEventLoop(Thread)` return `true` unconditionally (`EmbeddedEventLoop.java:102-110`) and whose task queue is a plain `ArrayDeque` (`:32-40`). `channel.writeAndFlush(msg)` goes `DefaultChannelPipeline.writeAndFlush` → `tail.writeAndFlush` (`DefaultChannelPipeline.java:892-894`) → `DefaultChannelHandlerContext.write(msg, true, promise)`, which checks `executor.inEventLoop()` and, since that is always true here, calls `next.invokeWrite(msg, promise)` and `next.invokeFlush()` inline on the calling thread (`DefaultChannelHandlerContext.java:693-701`). So an OC worker thread calling `sendTo` executes `FMLOutboundHandler.write` itself, right then, with no serialisation against any other thread doing the same.

Scope of the race: the attributes live on the `FMLEmbeddedChannel`, i.e. per registered channel name. Senders on different channels (OC's `"OpenComputers"`, Hodgepodge's `SimpleNetworkWrapper`, a future `"OpenGPU"`) never interfere with each other; only two threads using the *same* channel can.

### 1.4 Where every path ends: `NetworkDispatcher.sendProxy` → `NetworkManager.scheduleOutboundPacket` [V]

`FMLOutboundHandler.write` resolves the target to a list of `NetworkDispatcher`s (`:273`; `PLAYER` via `player.playerNetServerHandler.netManager.channel().attr(FML_DISPATCHER)`, `:109`) and calls `targetDispatcher.sendProxy(msg)` for each (`:282-285`), which is nothing but `manager.scheduleOutboundPacket(msg)` (`NetworkDispatcher.java:363-366`). `NetHandlerPlayServer.sendPacket` is the same call with a chat-visibility check in front (`NetHandlerPlayServer.java:682-718`, `:702`). So the FML channel API only adds recipient selection and the attribute hand-off in front of the vanilla queue.

### 1.5 `scheduleOutboundPacket` off-thread: the vanilla path, state by state [V]

```java
// NetworkManager.java:148-159
public void scheduleOutboundPacket(Packet inPacket, GenericFutureListener ... futureListeners) {
    if (this.channel != null && this.channel.isOpen()) { this.flushOutboundQueue(); this.dispatchPacket(inPacket, futureListeners); }
    else { this.outboundPacketsQueue.add(new InboundHandlerTuplePacketListener(inPacket, futureListeners)); }
}
```

- `channel` (`:60`) is a plain field written once in `channelActive` on the event loop (`:77-83`) before any packet of that connection is queued to `receivedPacketsQueue` (a `ConcurrentLinkedQueue`, `:56, :128`); a pool thread that obtains the `NetworkManager` from a server-thread snapshot sees the field through that chain **[I]**.
- `outboundPacketsQueue` is a `ConcurrentLinkedQueue` (`:58`); `flushOutboundQueue` (`:206-216`) only polls it, and it is non-empty only before the channel is active, so concurrent calls are harmless.
- `dispatchPacket` (`:165-201`) reads `channel.attr(attrKeyConnectionState)` (atomic attribute) and `EnumConnectionState.func_150752_a(inPacket)`, a static map lookup by class (`EnumConnectionState.java:322-325`) that returns `null` for `FMLProxyPacket`; the `setAutoRead(false)` and `setConnectionState` branches are explicitly skipped for `FMLProxyPacket` (`:170, :178, :192`). Then: `if (channel.eventLoop().inEventLoop()) writeAndFlush(...) else channel.eventLoop().execute(runnable)` (`:176-200`). The server thread is not the event loop (the server's event loops are the `NioEventLoopGroup`/local group used by `NetworkSystem`, `NetworkSystem.java:73-102`; the server tick calls `networkTick` → `processReceivedPackets` from `MinecraftServer.java:730`), so vanilla itself always takes the `execute` branch. `SingleThreadEventExecutor.execute` adds to a `LinkedBlockingQueue` and wakes the selector (`SingleThreadEventExecutor.java:155-157, 291-298, 681-700`) — a many-producer-safe hand-off.
- Inside the event loop the runnable does `channel.writeAndFlush(inPacket).addListeners(futureListeners).addListener(FIRE_EXCEPTION_ON_FAILURE)` (`:197`): tail → `packet_handler` is skipped (`NetworkManager extends SimpleChannelInboundHandler`, `:42`, inbound only) → `fml:packet_handler` (`NetworkDispatcher`, inserted `addBefore("packet_handler", ...)`, `NetworkDispatcher.java:120-125`) converts `FMLProxyPacket` to `S3FPacketCustomPayload` via `payload.array()` (`:428-437`, `FMLProxyPacket.java:132-135`) → `encoder`/`prepender` (`NetworkSystem.java:96`) → socket.

Hence a pool thread calling `nm.scheduleOutboundPacket(fmlProxyPacket)` is indistinguishable, at the Netty level, from the server thread doing it. Ordering: all writes to one connection are serialised through that event loop's single task queue in `execute()` order, so a pool-thread frame and a server-thread packet for the same player arrive in the order their `execute()` calls happened — real-time order, not tick order.

### 1.6 What happens on the event loop, and what kicks the viewer [V]

- The `S3FPacketCustomPayload(String, byte[])` constructor throws `IllegalArgumentException("Payload may not be larger than 2097050 bytes")` above `0x1FFF9A` bytes (`MC/net/minecraft/network/play/server/S3FPacketCustomPayload.java:25-35`). Hodgepodge replaces that constant with `FixesConfig.packetSizeLimit` (`MixinS3FPacketCustomPayload_LengthLimit`, `@ModifyConstant` on `<init>(String,byte[])`, body `getstatic FixesConfig.packetSizeLimit`), set to `268435456` with `increasePacketSizeLimit=true` in the installed `hodgepodge.cfg:638, 697`, and widens the length prefix on both read and write; the stock cap still applies to any peer without Hodgepodge, which is why 09 §3.4 keeps packets ≤ 256 KB. `MixinS3FPacketCustomPayload_Validation` adds `validateLimitedString(channelName, 20)` at the constructor tail.
- Because the conversion happens in `NetworkDispatcher.write` on the event loop, a throw there is caught by `invokeWrite`, fails the promise, and `FIRE_EXCEPTION_ON_FAILURE` fires `exceptionCaught` through the connection pipeline: `NetworkDispatcher.exceptionCaught` logs "NetworkDispatcher exception" and propagates (`NetworkDispatcher.java:479-488`), and `NetworkManager.exceptionCaught` closes the channel with "Internal Exception: …" (`NetworkManager.java:102-116`). **An over-cap or badly named packet disconnects the viewer**, whichever thread queued it. The size check belongs on the sending thread, before `scheduleOutboundPacket`.
- `payload.array()` requires a heap buffer whose backing array *is* the payload: `Unpooled.wrappedBuffer(byte[])` as OC does (`PacketBuilder.scala:149, 161`), not a slice or a pooled/direct buffer.
- `channel.isWritable()` is a volatile read of the outbound buffer's `writable` flag (`AbstractChannel.java:82-85`, `ChannelOutboundBuffer.java:89, 415-417`), flipped when queued-but-unsent bytes exceed the high-water mark; it is a thread-safe back-pressure signal a pool thread may consult before queuing a frame **[I]** (vanilla never checks it).

### 2.2 The two OC patterns, and the race OC lives with [V]

**Pattern A — mutate under a lock, flush from the tick (screens, holograms).** GPU callbacks append to a per-buffer `CompressedPacketBuilder` under the buffer's monitor (`common/component/TextBuffer.scala:68-79`), and `update()` sends it once per tick on the server thread (`:158-161`); hologram `set` is direct (`Hologram.scala:159`) and only marks dirty columns (`:116-120`), which `updateEntity` flushes (`:396-415`). This is the pattern 09 §3.5 adopted.

**Pattern B — send immediately from the worker (disk and network activity).** `sendFileSystemActivity` posts a Forge event, builds a `SimplePacketBuilder` and calls `sendToPlayersNearHost` right there (`PacketSender.scala:141-165`); the per-disk timeout cache is a Guava `Cache` built with `concurrencyLevel(Settings.get.threads)` inside a `synchronized` `WeakHashMap` (`:130, :136-138`) — OC's authors explicitly expected the worker threads here. The recipient scan then iterates `w.playerEntities` and calls `isPlayerWatchingChunk` (`PacketBuilder.scala:93-96`) or `playerEntityList` (`:116`) off-thread.

Consequence (OC's existing, live race): a worker-thread `sendTo` from pattern B and a server-thread `sendTo` from pattern A (`TextBuffer.update` → `sendToPlayersNearHost` → per-player `sendTo`) both use `OpenComputers.channel` with target `PLAYER`. Interleaved as in §1.3 they cannot throw (same target type) but can deliver one player's `TextBufferMulti` delta to another player; the affected screen then desyncs until its periodic resync (`TextBuffer.scala:70-72, 163-169`, see 03 §3). The disk-activity packet itself is "non-essential — losing them should not cause glitches" (`application.conf:1448-1449`). So OC's precedent is: it works in the sense that the vanilla queue underneath is thread-safe, and OC accepts a rare misrouted packet because everything it sends this way is either throttled, cosmetic, or self-healing. It is not a precedent for sending per-frame payloads through `FMLEventChannel` off-thread.

### 2.3 Correction to 07 §1 (line 58) [V]

The sentence "OC itself sends packets from the worker thread (`Machine.beep` → `PacketSender.sendSound`, `Machine.scala:295-297`)" must become: "OC itself sends packets from its worker threads, but not from `beep` (a non-direct callback that runs in `Machine.update()` on the server thread, `Machine.scala:456-471, 597-604`): the direct callbacks `FileSystem.read/write/open/exists/size/isDirectory/lastModified` and `Drive.readSector/writeSector/readByte/writeByte` call `diskActivity()` → `ServerPacketSender.sendFileSystemActivity` → `OpenComputers.channel.sendTo` (`FileSystem.scala:172-195, 362-367`; `Drive.scala:93-133, 215-220`; `PacketSender.scala:132-169`), rate-limited to one packet per 500 ms per disk and tolerant of the `FMLEventChannel` attribute race (13 §1.3, §2.2). OpenGPU should not copy that path; it should hand finished `FMLProxyPacket`s to `NetworkManager.scheduleOutboundPacket`, which is the thread-safe queue every FML send ends in (13 §1.4-1.5)." The latency conclusion that follows in 07 (removing the ≈ 25 ms average tick wait) stands; its clause "at the cost of ordering guarantees vs. other tick packets" should read "at the cost of tick-atomic ordering only; per-connection order follows `execute()` order (13 §1.5)".

## 3. Hodgepodge 2.7.216 and lwjgl3ify [V]

## 4. Verdict for OpenGPU

### 4.1 Decision

Send encoded frame packets **from the OpenGPU pool thread via `NetworkManager.scheduleOutboundPacket(FMLProxyPacket)`**, with the **recipient list computed on the server thread** and published as an immutable snapshot. Never call `FMLEventChannel.send*` / `SimpleNetworkWrapper.send*` from any thread but the server thread (or, equivalently, never from two threads). Keep a config switch (`net.sendFromPool=true`) that routes frames through the tick-thread hand-off instead, for diagnosis. Confidence: **high** on safety (it is the vanilla path; §1.5), **medium** on the latency figure (derived, unmeasured until M0).

### 4.2 Exact code path

```java
// Server thread, in the display TE's update() (or whenever the watcher set changes):
//   OC's recipient rule (PacketBuilder.scala:79-102): WorldServer.playerEntities,
//   PlayerManager.isPlayerWatchingChunk, distance² ≤ displayRange², optional misc.maxNetworkClientPacketDistance
List<NetworkManager> nms = ...;                      // EntityPlayerMP.playerNetServerHandler.netManager
display.viewers = Collections.unmodifiableList(nms); // volatile field or AtomicReference; never EntityPlayerMP refs

// OpenGPU pool thread, when a frame job finishes encoding:
byte[] bytes = frame.bytes();                        // exactly the payload; own array
if (bytes.length > cap) { report opengpu_error; return; }   // §1.6: an over-cap S3F kicks the viewer
FMLProxyPacket pkt = new FMLProxyPacket(Unpooled.wrappedBuffer(bytes), "OpenGPU"); // channel name ≤ 20 chars
for (NetworkManager nm : display.viewers) {
    if (!nm.isChannelOpen()) continue;               // NetworkManager.java:348-351
    if (!nm.channel().isWritable()) { skip or defer per the per-viewer token bucket; continue; } // [I]
    nm.scheduleOutboundPacket(pkt);                  // NetworkManager.java:148-159 → eventLoop().execute → NetworkDispatcher.write → S3F
}
```

One `FMLProxyPacket` may be shared across viewers (its outbound path is read-only, §1.3); `TILES` lineages shared across viewers (09 §3.4) therefore cost one allocation. Control packets originating on the server thread (resets, resource uploads, keyframes on subscribe) may go through the same `scheduleOutboundPacket` calls or through the `"OpenGPU"` `FMLEventChannel` *from the server thread only*; the former keeps a single ordering domain per connection and is simpler to reason about. Client→server input stays on the FML channel from the client main thread.

### 4.3 Latency difference [derived]

07 §1 (line 58) budgets Lua-call→pixels on LAN as render 2–10 ms + encode 1–5 ms + **wait for the server-thread send 0–50 ms (avg 25)** + decode/upload 0.5 ms + wait for the client frame 0–16 ms ≈ 35–60 ms average. The tick wait is the time from frame completion to the display's next `update()`; on an overloaded server it is the whole (longer) tick. With the pool sending directly, that term becomes one `LinkedBlockingQueue.add` plus a selector wake-up and the write on the event loop — **[est.]** well under 1 ms, unmeasured. Result: ≈ 3.5–31.5 ms, **≈ 10–30 ms average on LAN**, i.e. the ≈ 25 ms average saving 07 counted, plus whatever a slow tick would have added. The only cost is that recipients are up to one tick stale (a player who just left range gets ≤ 1 extra frame; one who just disconnected has `isChannelOpen()` false and is skipped, or the packet lands in a dead `outboundPacketsQueue` until that `NetworkManager` is dropped by `networkTick`, `NetworkSystem.java:165-177` — a bounded, harmless leak).

### 4.4 Ordering, failure modes and rules

- **Ordering.** Per connection, packets are written in `execute()` order (§1.5), so a frame and a server-thread packet for the same player may arrive in either order relative to the tick boundary but never reordered relative to each other's queueing time. Required stream property (already in 09 §3.4, now load-bearing): every packet carries `(displayId, generation, frameId)`; the client drops frames whose generation is stale and frames for displays it does not have yet — the chunk/TE data for a freshly watched display is sent from the server thread and may arrive *after* the first pool-sent frame (`isPlayerWatchingChunk` turns true before the chunk packet goes out; OC's client handles the same situation by requesting a full sync, 03 §3). A generation bump (reset, resolution/palette change) must be sent before the first frame of the new generation: simplest is to emit it from the pool job that first renders under the new generation.
- **Never iterate world or player lists off the server thread.** The recipient snapshot is the only world-derived input the pool reads.
- **Size and name.** Check `bytes.length` against the configured cap (≤ 256 KB per 09 §3.4; stock FML cap 2,097,050; installed Hodgepodge cap 268,435,456) before queuing; a throw in `NetworkDispatcher.write` disconnects the viewer (§1.6). Channel name ≤ 20 characters.
- **Buffers.** `Unpooled.wrappedBuffer(byte[])` only; `toS3FPacket` uses `payload.array()`.
- **Integrated server.** Same path: the `LocalChannel`'s event loop is still a separate thread from the server thread (`NetworkManager.java:270-277`, `isLocalChannel`), so `dispatchPacket` takes the `execute` branch there too.
- **Back-pressure.** `nm.channel().isWritable()` (volatile) is a free signal that a viewer's socket is backed up; combine with the per-viewer token bucket from 09 §3.4 so the pool skips rather than queues.

### 4.5 What remains to be tested in M0

Static analysis cannot show the absence of a mixin or coremod in the other 180 installed mods that wraps `NetworkManager`; nothing in Hodgepodge, lwjgl3ify, GTNHLib or UniMixins does (§3), and no such thing is known to the researcher, but the M0 vertical slice should still run the two-thread stress (server-thread `TextBuffer`-style sends plus pool sends on the same connection, dedicated and integrated server, Java 8 and 21) and record Lua-call→pixel latency with `sendFromPool` on and off. The expected outcome is now "confirms", not "decides".
