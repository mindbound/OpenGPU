## Summary

1. **A direct `@Callback` with no arguments costs 4.2–4.5 µs on OC's Lua 5.2, 5.3 and 5.4 (≈ 225 000–240 000 calls/s) and 1.5–1.6 µs on OC-LuaJIT (≈ 620 000–670 000 calls/s)**, identical on JDK 8 and JDK 17, identical under `callBudgets=[0.5,1,1.5]` and `[1,2,4]`, identical for `component.invoke(addr, m)` and the `proxy.m()` path. Two integer arguments and one integer result add 1–4 µs on PUC (5–9 µs total, run-to-run) and ~0.3–0.8 µs on LuaJIT (1.8–2.4 µs). **Report 04 §2's 4–8 µs was right; 07 §2's 5–20 µs contained the truth but its top end is 2–4× too pessimistic; 09 §1's 4–20 µs inherits that; 06 §1's "sub-µs hop" is the bare JNI upcall (measured 0.17–0.19 µs for `computer.uptime()`), which is 25× smaller than a component call and must not be quoted as one.**
2. **Payloads.** A 100 KB string argument costs 22–28 µs in (≈ 36 000–45 000 calls/s), 34–51 µs for a round trip (string in, same string out) on PUC; 19–22 µs / 26–28 µs on LuaJIT. 07 §2's "20–40 µs plus ~1 µs" for 100 KB marshalling was right. A 1000-entry table argument costs 84–118 µs on PUC (16 µs on LuaJIT with the JIT on, 40–44 µs with it off); **returning a 1000-entry table costs 0.9–1.6 ms** (≈ 1.2 µs per entry of JNI traffic), 25–40× a 100 KB string.
3. **Budget stall, measured directly per tick.** With `limit=256` a tight loop lands exactly `maxCallBudget × 256 + 1` calls in every full tick: 385 (T3, `[0.5,1,1.5]`), 1025 (T3, `[1,2,4]`), 129 (T1 default), 257 (T1 installed); the `+1` is the over-budget call re-issued as a synchronized call on the tick thread. A non-direct call is exactly 1 per tick (21/s). `computer.pullSignal(0)` resumes 3.2 times per tick (≈ 63/s). 07 §2's "≈ budget/cost + 1 calls per tick" and 04 §2's "60–80 iterations/s" were both right.
4. **New finding: table arguments drain sandbox RAM until the JVM collects.** Every table argument becomes a lazy JNLua `AbstractTableMap` proxy over a `luaL_ref` registry slot that is released only when `LuaState.check()` drains a `PhantomReference` queue, i.e. after a JVM GC. 100 000 table calls with an idle 1 GB heap drained a 2048 KB machine from ~1.9 MB free to 58–61 KB (5.2), 285 KB (5.3), 236 KB (5.4) and ~1.24 MB (LuaJIT); with a 48 MB heap (frequent young GCs) free memory stayed at 1.87 MB. The earlier harness attempt in this scratchpad died with `machine:1085: not enough memory` from exactly this. Strings do not have the problem (copied to `byte[]`). The same code and the same shaded OC-JNLua 20230530.0 are in the installed 1.12.64-GTNH jar.
5. **Machines resolved.** All numbers here, 06's raster bench and the game instance are on this box: Intel Core Ultra 9 285HX (8 P + 16 E cores, 24 logical), 256 GB RAM, Windows 11 Pro 10.0.26300. 07's "the user's bench box is a Ryzen 7 7840U" is OC-LuaJIT's September laptop (`bench/results-2026-09-01.md:7`; `results-ladder-2026-09-29.md:57-62` records the move to the 285HX on 09-29, and that the 7840U "was not idle: 56–62 % load and a Minecraft client JVM throughout"). The 7840U figures are standalone VM ratios, not call costs, and were never the game host.
6. **Design consequence for 09:** the per-call constant is settled 5–10× below the "not worth it" threshold (≥ 50 µs); 2 direct calls + a 60–100 KB string per frame cost ≈ 30–40 µs of executor time on PUC (≈ 0.1 % of a tick at 20 fps). Per-primitive 2D at 1000 calls/frame costs 4.3 ms/frame on PUC and fits one tick only at T3 with the installed `[1,2,4]` budget (1025/tick); at the default budget it stalls two extra ticks per frame. Tables must stay out of the per-frame path in both directions.

## 1. Method

**What was built.** A 160-line Scala entity `callbench.Bench` modelled on `ocelot-brain/src/main/scala/totoro/ocelot/brain/entity/ColorfulLamp.scala` (`Entity with Environment`, `Network.newNode(...).withComponent("bench", Visibility.Network)`), with direct callbacks `noop()`, `add(a,b)`, `sink(s)` (string in, length out), `echo(s)` (string in, same `byte[]` out), `sinkTable(t)` (table in, size out), `echoTable(t)` (table in, same `Map` out), the same four with `@Callback(direct = true, limit = 256)`, one non-direct `sync()`, and instrumentation callbacks (`begin`, `finish`, `report`, `budget`, `fingerprint`, `jit`). An EEPROM program (`bench.lua`, run as the BIOS by OC's real `machine.lua`, no OpenOS) times 100 000 calls of each workload with scalar arguments, a 100 KB string (`string.rep("x", 100000)`) and a 1000-entry array table.

**How time is measured.** Two independent clocks per batch: (a) Java-side, `System.nanoTime()` stamped inside every measured callback; `finish()` returns the interval between the first and the last stamp, divided by n−1 round trips — this covers the whole path Lua loop → `machine.lua` `invoke` wrapper (`:1080-1103`) → `component.invoke` (JNI, `ComponentAPI.scala:79-82`) → `Machine.invoke` (`Machine.scala:344-361`) → `Component.invoke` → `CallbackWrapper` → the method → result push → back in the loop; (b) Lua-side, `os.clock()` (`Machine.cpuTime`, nanoTime-based, `OSAPI.scala:13-19`). The two agree to 0.001 µs in every row (see `work/summary-all.md`), which also shows the stamping itself is not the cost. Unlimited workloads run 10 batches of 10 000 (scalars) or 50 batches of 2 000 (payloads), each batch after a `computer.pullSignal(0)` yield so every batch is a fresh resume under the 5 s deadline; min / median / max over batches are reported. Limited workloads record the server tick of every call; a ticker calls `Workspace.update()` every 50 ms (measured gap: mean 50.0–52.4 ms, max 61–64 ms), which is what resets `callBudget` (`Machine.scala:498`) and runs synchronized calls, so "calls per full tick" is read directly.

**Isolation.** One freshly booted machine per workload (Case T3, CPU T3, 2 × `Memory(ExtendedTier.ThreeHalf)` = 2048 KB apparent, `ramScaleFor64Bit` 1.8, the EEPROM, the bench entity; T1 arm: CPU T1 + 1 × `Memory(One)` = 192 KB). The earlier attempt that shared one machine across workloads is why it died (§4.4). Each (budget × runtime) pair is its own JVM because `Settings` is loaded once (`Settings.scala:34-40`). Config = ocelot-brain's `application.conf` plus `callBudgets`, `forceNativeLibPathFirst`, `allowBytecode=false`, `ramScaleFor64Bit=1.8`; `executionDelay` 12 ms and `timeout` 5 s are the defaults (`application.conf:207,132`), the same values as the instance's `OpenComputers.cfg:191,302`.

**Runtimes.** `NativeLua52Architecture`, `NativeLua53Architecture`, `NativeLua54Architecture` (ocelot-brain's bundled OC natives from OC-JNLua-Natives-20220928.1, driven through OC-JNLua-20230530.0 — the same two artifacts GTNH OC shades, `OpenComputers-GTNH/dependencies.gradle:5-6`), and OC-LuaJIT in its shipped *additive* configuration: `ocljit.arch.OCLuaJITArchitecture` (`OC-LuaJIT/test/native/OcljArch.scala`) backed by `libjnluajit52-windows-x86_64.dll` whose SHA-256 `bac49645…7a06a` is byte-identical to the DLL inside the installed `mods/ocluajit-a4994e6.jar`, with the watchdog kernel produced by `native/kernel/patch-machine-lua.lua` from ocelot-brain's `machine.lua` (13 sites patched). ### 2.3 Table arguments drain sandbox RAM until the JVM collects (new)

Free sandbox memory at the end of the `sinkTable_1000` workload (100 000 calls, fresh 2048 KB machine, ≈ 1.9 MB free at start), by Java heap:

| Runtime | JVM `-Xmx1g` (main matrix) | JVM `-Xmx48m -Xmn16m` (`logs/leak48-*.log`) |
|---|---|---|
| Lua 5.2 | **58–61 KB** left | — |
| Lua 5.3 | 285–286 KB left (from 1 270) | **1 871 KB** left |
| Lua 5.4 | 236–238 KB left | — |

`echo_100KB` and the scalar workloads end with 1.7–1.9 MB free on every runtime (5.3 reports ~1.27 MB because its baseline is lower). The drain is per call, not per table: `T` is the same table every time. Mechanism, verified by `javap` on OC-JNLua-20230530.0 and on the classes shaded into the installed `OpenComputers-1.12.64-GTNH.jar`: `ComponentAPI` converts every argument with `toSimpleJavaObjects` (`ExtendedLuaState.scala:99-110`; GTNH `util/ExtendedLuaState.scala:106-116`), which turns a table into `lua.toJavaObject(index, classOf[java.util.Map])`; `DefaultConverter.convertLuaValue` answers a `Map` request with `new DefaultConverter$1(luaState.getProxy(index))`, a lazy `AbstractTableMap` over a `LuaValueProxyImpl` holding a `luaL_ref` registry slot; the slot is released by `lua_unref` only when `LuaState.check()` (run on every API entry) polls `proxyQueue`, a `ReferenceQueue` of `PhantomReference`s (`LuaState$LuaValueProxyRef`) — i.e. only after the JVM garbage collector has found the proxy unreachable. With nothing else allocating, a 1 GB JDK 8 heap never collected during the run, so every call left one live registry entry (≈ 16 B per slot in PUC's TValue array, less on LuaJIT) charged against the OC RAM cap; with a 16 MB young generation the proxies were collected every few hundred calls and the registry stayed small. The kernel's own `collectgarbage("collect")` every tenth resume (`machine.lua:1524-1530`) cannot free a registry reference held by Java. In a running server the JVM collects every few seconds, so the drain is bounded, but a T1 machine (192 KB) passing tables at the measured 9 000–12 000 calls/s can exhaust itself within one GC interval; the first harness attempt in this scratchpad (`logs/trial-53-default.log`, 14:52) hit `machine:1085: not enough memory` after `echo_100KB` + `sinkTable` in one 1024 KB machine. **Design rule: tables cross the boundary only for rare configuration calls; per-frame data is byte strings.** Returning tables is separately expensive: `pushTable` (`ExtendedLuaState.scala:79-97`) walks the proxy through JNI per entry (`AbstractTableMap$EntryIterator`: `pushJavaObject`, `next`, `toJavaObject`×2, `pop`) and pushes each key/value again — 0.9–1.6 ms per 1000 entries, ≈ 1.2 µs per entry.

*[inference]* Why a table *in* costs 84–118 µs on PUC but 16 µs on LuaJIT with the JIT on and 40–44 µs with it off: the Java side does one `getProxy` and one `size()`; the Lua side runs `unwrapUserdata` (`machine.lua:1205-1221`), a recursive `pairs` walk that calls a closure and writes `value[k]` back for each of the 1000 entries, and `processResult` → `wrapUserdata` (`:1187-1203`) walks the result. The JIT compiles that walk; the PUC interpreter spends ≈ 80–100 ns per entry on it. The dominant cost of a table argument is therefore OC's kernel, not JNI, and it scales with entry count on every runtime.

## 5. Open questions

1. The in-game path differs from ocelot-brain only in `recomputeMemory`, `SaveHandler` and the thread pool's host (`OC-LuaJIT/docs/research/ocelot-brain.md`, "Residual risk" 3); the `Machine.invoke`/`consumeCallBudget`/kernel code is byte-identical (`OpenComputers-GTNH/src/main/scala/li/cil/oc/server/machine/Machine.scala:286-294,385-409,532`). A one-boot in-game confirmation on the instance (JRE 1.8.0_492, with 188 mods loaded and the server tick busy) would turn "same code" into "same number"; expect the same per-call cost and a noisier tick.
2. Older/slower server cores: no measurement exists; the 285HX P-core figures should be scaled by 1.5–3× for a 2018-era server part *[inference]*, which still leaves the 2-calls-per-frame design two orders of magnitude under a tick.
3. `add`'s bimodal 5 vs 9 µs on PUC was not root-caused (E-core placement vs C2 state); pinning the JVM to P-cores (`start /affinity`) would separate the two.
4. Whether OC-LuaJIT could release table proxies eagerly (e.g. `lua_unref` at the end of `Machine.invoke` for proxies created for that call) is a question for the OC-LuaJIT author; stock OC cannot change it without touching `ExtendedLuaState`.
