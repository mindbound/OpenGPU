# 06 — Graphics-engine architecture best practices for a JVM-hosted pixel GPU

Research date: 2026-10-08. Scope: API shape, 2D layer, software rasterizer design, shader language/compiler, compute pipeline, determinism/sandboxing and module decomposition for OpenGPU (server-side CPU rendering, Java 8 bytecode, results readable by Lua, frames streamed to viewers). Local checkouts cited as `path:line`; web sources listed at the end. Measured numbers come from two throw-away microbenchmarks I wrote for this report (scratchpad `bench/RasterBench.java`, `bench/ShaderBench.java`; see §3.6) — they are indicative, not a product benchmark.

## Summary

1. **Command buffers are the right design, but OC does not force them.** OC charges a `direct` callback `1/limit` against a per-tick `callBudget` (defaults 0.5/1.0/1.5 per tier, the mean over CPU *and* memory components; the installed config overrides the tiers to 1/2/4) and defers over-budget calls to one synchronized call per tick — but `@Callback.limit` defaults to `Integer.MAX_VALUE`, so an uncharged direct call costs ~0 budget. OC's own text GPU is the one that *chooses* to charge 1/64–1/256 per `set` (and only when the target is the screen, not VRAM buffers), which caps it at ~1 k screen `set`s per tick on this install. The real per-call floor for a per-primitive Lua API is JNI + argument marshalling + GC — measured by 11 §2: the bare JNI hop is 0.17–0.19 µs, but a whole direct component call is 4.2–4.5 µs (≈ 225 000–240 000 calls/s) on OC's PUC Lua and 1.5 µs on OC-LuaJIT — plus tick coupling and persistence. OpenGPU should still take one packed byte-string command buffer per frame via `Arguments.checkByteArray`, and charge the budget itself in OpenGPU units.
2. **API shape:** WebGPU/sokol_gfx-style *immutable pipeline objects + integer generation handles + recorded command buffers*, not a GL ES 2 state machine. Handles are 32-bit `slot | generation`, zero = invalid; fixed-size pools give VRAM accounting for free.
3. **Rasterizer:** Pineda edge functions, 28.4 fixed point, top-left rule, incremental stepping, guard-band ±1024 px with near-plane clipping only, float barycentrics, perspective-correct via 1/w, early depth test, 32×32 or 64×64 tile bins rendered by a `ForkJoinPool`. Measured on this machine (JDK 8, one core, 320×200; run-to-run spread ≈ ±20%): ~340–420 Mpix/s flat, ~200–250 Mpix/s Gouraud, ~110–130 Mpix/s perspective-textured; ~7 M 8-px triangles/s; 16 threads give ~5.5× (320×200) to ~8.6× (640×400).
4. **Shader language:** a GLSL ES 1.00 subset (Appendix-A style restrictions: constant-bound `for` loops, no recursion, no dynamic indexing) compiled by a hand-written lexer/Pratt parser to JVM bytecode with the ASM 5.0.3 Forge already ships; emit one class per (program × pipeline-state) containing the *whole inner loop* (llvmpipe/SwiftShader-Reactor specialization) — the measured requirement is that the per-pixel call site stays monomorphic (a megamorphic shader interface halves a flat pixel and deoptimizes the shared loop on JDK 25); whole-loop generation satisfies that and additionally removes per-pixel state branches, but the benchmark does not show it is *necessary* over a per-program class calling a monomorphic shader method — keep generated methods < 8000 bytecode bytes, and keep a tree-walking interpreter as the reference implementation.
5. **Compute:** OpenCL/WebGPU work-item model (1D–3D dispatch, `global_id`), typed buffers, no barriers in v1, deterministic by design (each work-item writes only its own outputs; reductions via fixed-order two-pass). Results read back as packed strings.
6. **Determinism:** Java 8 on x86-64 is, by inference from JEP 306 (HotSpot x86-64 uses SSE2, and only x87's extended exponent range ever made results non-strict), already IEEE-strict for `+ - * / sqrt`, and Java 17+ makes it mandatory; use `StrictMath` (fdlibm) or own polynomials for transcendental built-ins (`Math` allows 1 ulp for most functions, 2 for `atan2`, 2.5 for `sinh/cosh/tanh`); never `Math.sin` in a shader; never rely on thread scheduling order.
7. Precedent **OCLights2** (1.7.10, OC addon) already did "draw-command deque replayed on the client with java.awt" and documents its own network inefficiency — useful as a cautionary design.

## Findings

### 1. API shape and resource model

**Why batching is the right design (and what OC does and does not impose).** `Machine.invoke` charges `1.0 / annotation.limit` budget for every `direct` callback (`OpenComputers-GTNH/src/main/scala/li/cil/oc/server/machine/Machine.scala:385-402`); `consumeCallBudget` throws `LimitReachedException` once the per-tick budget is exceeded (`:286-294`), after which the kernel re-issues the call as a synchronized call executed on the server tick (one per tick, `:597-604`; `machine.lua:1080-1103`). The budget is reset to `maxCallBudget` once per tick (`:532`), and `maxCallBudget` is the *arithmetic mean* of `getCallBudget` over every `CallBudget`-providing component — CPU (`DriverCPU.scala:69`) *and* memory (`DriverMemory.scala:40`) — so a T3 CPU with T1 RAM does not get the T3 figure (`:123-126`). Default tier budgets are `[0.5, 1.0, 1.5]` (`src/main/resources/application.conf:162-166`, also in the installed 1.12.64 jar), but `Settings.scala:71-76` takes the configured list and the installed config overrides it to **`callBudgets=[1, 2, 4]`** (`C:\Games\Minecraft\instances\Main\minecraft\config\OpenComputers.cfg:143-147`; likewise `vramSizes=[1,2,4]` at `:521-525` vs the jar default `[1,2,3]`). `@Callback.limit` defaults to `Integer.MAX_VALUE` (`src/main/java/li/cil/oc/api/machine/Callback.java:88`), so a direct callback that does not call `consumeCallBudget` costs ≈0 budget and is limited only by per-call cost and the "too long without yielding" timeout — the budget is a throttle each component *opts into*. OC's text GPU does opt in: `setCosts = 1/64, 1/128, 1/256` per `set`, `copyCosts = 1/16..1/64`, `fillCosts = 1/32..1/128` by tier (`server/component/GraphicsCard.scala:63-69`, applied at `:489,:505,:523`), but `resolveInvokeCosts` (`:100-107`) charges them *only when the target buffer is the screen* (`case RESERVED_SCREEN_INDEX => consumeCallBudget`, `case _ => true`) — `set/copy/fill` into VRAM pages are budget-free — and bitblt cost grows with the dirty source area, with a `pause()` once the budget is exhausted twice (`:196-209, :233-249`). On this install a T3 CPU + T3 GPU (T3 RAM) therefore allows 4×256 = 1024 screen `set` calls per tick (≈20 k/s; with the jar defaults 1.5×256 = 384, ≈7.7 k/s). **Implication (high confidence):** the "few thousand calls/s" ceiling is a policy OpenGPU would choose, not one OC imposes; the real floor for a per-primitive API is JNI + argument marshalling + GC per call — `report-compat-and-perf.md:82`'s "sub-µs hop" is the bare JNI upcall, measured at 0.17–0.19 µs by 11 §2, whereas a whole direct component call measures 4.2–4.5 µs (≈ 225 000–240 000 calls/s) on OC's Lua 5.2/5.3/5.4 and 1.5 µs on OC-LuaJIT, so "hundreds of thousands of calls/s" holds only for empty calls — plus the tick coupling of synchronized calls and NBT persistence of partially built frames. Those are still decisive: OpenGPU should accept whole frames as one call, and charge OC's budget itself (via `context.consumeCallBudget`, letting OC compute `maxCallBudget` from the installed config) in OpenGPU units. OC already marshals Lua strings as `byte[]` without copying through Java `String` (`util/ExtendedLuaState.scala:109`, `api/machine/Arguments.java:120 checkByteArray`), so a packed binary command buffer is the cheapest Lua→Java path. Note that `string.pack` exists on OC's Lua 5.3/5.4 but is `nil` on LuaJIT (`OC-LuaJIT/docs/research/report-compat-and-perf.md:21`) *and* on OC's still-shipped Lua 5.2 architecture (`NativeLua52Architecture` and `libjnlua52-*` natives are in the installed `OpenComputers-1.12.64-GTNH.jar`; `machine.lua`'s `string.pack/unpack/packsize` sandbox entries are plain references that are "nil on 5.2 already", `report-compat-and-perf.md:27`, `OC-LuaJIT/docs/feasibility.md:69`), and OC-LuaJIT deliberately does not expose `ffi` (`OC-LuaJIT/docs/ffi-decision.md`), so the encoder must have a pure-Lua fallback (`string.char`/`table.concat`) for a built-in OC architecture as well as for LuaJIT, or OpenGPU should also accept a flat Lua table of numbers and encode it on the Java side.

**Which API style.** The four families compared:

- *GL ES 2.0 state machine*: global mutable state makes command streams order-dependent and persistence messy. Keep the GLSL ES 1.00 *language* (§4), not the GL object/state model.
- *WebGPU*: immutable `GPURenderPipeline`/`GPUComputePipeline`, `GPUBindGroup` resource sets, `GPUCommandEncoder` → `GPUCommandBuffer` → `GPUQueue.submit()`; invalid calls become no-ops and objects are tagged invalid, reported via error scopes (spec §"Object model"; explainer §3.2–3.7). The explainer's rationale for record-then-submit — encoding is independent of other state and bigger batches let the backend schedule — maps exactly onto "Lua encodes, server thread pool renders".
- *sokol_gfx*: `sg_buffer/sg_image/sg_sampler/sg_shader/sg_pipeline/sg_view`; frame = `sg_begin_pass → sg_apply_pipeline → sg_apply_bindings → sg_apply_uniforms → sg_draw → sg_end_pass → sg_commit`; resource states `INITIAL/ALLOC/VALID/FAILED/INVALID`; pools sized up front by `sg_desc`; the header's "DOES NOT" list (no window, swapchain or shader language) is a good template for OpenGPU's core/adapter split.
- *bgfx*: "Bring Your Own Engine", ordered views, 16-bit handles, render thread fed by `bgfx::frame()`.

**Handles.** floooh's "Handles are the better pointers": handle = slot index bits + per-slot generation counter; zero reserved as invalid; a stale handle is detected because the slot's counter no longer matches; with 32-bit handles "you can always create 4 billion items", at most 2^(32−counter bits) alive at once; slots whose counter overflows are retired. Fixed pools "make leaks easier to find early" and give a hard per-GPU cap. For OpenGPU: 16-bit slot + 16-bit generation per resource type (buffers, textures, programs, pipelines, render targets), per-GPU pools sized by tier, VRAM accounting = Σ(bytes of VALID resources) checked at `create*` against a tier cap (OC precedent: `gpu.vramSizes [1,2,3]` and `totalMemory/freeMemory` callbacks, `application.conf:1667`, `GraphicsCard.scala:180-188`). Persistence: resources must be saved in NBT (OC's `Value` objects must be `Persistable` with a default constructor, `api/machine/Value.java:16-23`), so integer handles plus a serializable pool are far easier than exposing Java objects to Lua.

### 2. The 2D layer

**What fantasy consoles get right** (PICO-8 manual; TIC-80 wiki; Picotron manual): a tiny fixed palette (PICO-8: 128×128, 16 colours; TIC-80: 240×136, 16 colours; Picotron: 480×270, 64 colours), `pal()`/`palt()` remaps and transparency, `clip()`, `camera()` offset, `fillp()` 4×4 patterns, sprite sheet + `spr/sspr/map`, and a hard CPU budget surfaced to the program (PICO-8 `stat(1)`, ~4 M VM ops/s; Picotron costs vector ops at "1 cycle per 24 operations"). TIC-80's `ttri(x1..y3, u1..v3, texsrc, chromakey, z1, z2, z3)` is the one fantasy-console primitive that already is a textured, depth-buffered triangle (depth buffer active when z is given, cleared by `cls()`; texture source = sprite RAM, map RAM or the other vbank's screen). Picotron's `userdata` (`u8/i16/i32/i64/f64`, `:add/:mul/:matmul3d/:copy/:take/:lerp`, `blit`, `set_draw_target`, `get_display`) is the closest existing answer to "how does a sandboxed Lua program do bulk math fast": typed arrays with vectorised ops instead of per-element Lua — exactly the compute-pipeline shape recommended in §5.

**What 2D libraries converge on** (raylib.h; LÖVE `Graphics.h`; SDL_BlendMode): `Color{r,g,b,a}` as 4×u8; float `Rectangle`; `Camera2D{offset,target,rotation,zoom}`; `DrawTexturePro(src rect, dst rect, origin, rotation, tint)`; scissor (`BeginScissorMode`, LÖVE `setScissor/intersectScissor`); a transform stack (`push/pop/translate/rotate/scale/shear`); fill vs line modes; nearest/bilinear filters and repeat/clamp/mirror wraps. Blend modes with SDL's exact formulas: NONE, BLEND (`dstRGB = srcRGB·srcA + dstRGB·(1−srcA)`), ADD (`dstRGB = srcRGB·srcA + dstRGB`), MOD (`dstRGB = srcRGB·dstRGB`), MUL; raylib adds `BLEND_ALPHA_PREMULTIPLY`. Premultiplied alpha should be the internal convention (one formula, correct filtering).

**Thin layer over the 3D rasterizer vs a blitter.** Dear ImGui proves the "everything is textured triangles" route: `ImDrawVert = {pos, uv, col}` (20 bytes), `ImDrawIdx` (16-bit by default), `ImDrawCmd{ClipRect, TexRef, VtxOffset, IdxOffset, ElemCount}`, all shapes (`AddRectFilled`, `AddCircle`, `AddText`, `AddImage`, `AddPolyline`, `AddConvexPolyFilled`) emitted as triangles over a font atlas that contains a white pixel (`GetFontTexUvWhitePixel`) for solid fills, commands merged while clip rect and texture are unchanged, anti-aliasing by feathered edge geometry (`ImDrawFlags_AAFill/AALines`). This gives one code path, one pipeline, trivial Z-ordering and lets 2D run through any future hardware backend. The cost is per-pixel: an axis-aligned opaque blit through the triangle path costs ~2.4–3 ns/px (flat, measured §3.6, ±20%) versus ~0.3 ns/px for `System.arraycopy` of int rows. **Recommendation:** implement 2D as ImGui-style draw lists executed by the 3D rasterizer (so clipping, transforms, blending and render targets are shared), and add *fast paths* detected at decode time for the two hot cases: axis-aligned, unrotated, unscaled, NONE/BLEND sprite blits (row copy / per-row blend) and rectangle fills. Picotron's `blit` being "much faster than an equivalent `sspr`" is the same optimisation.

**Fonts.** OC ships its screen font as `src/main/resources/assets/opencomputers/font.hex` (4,914,163 bytes; 12,953 lines with 32 hex digits = 8×16 glyphs and 62,890 with 64 digits = 16×16), parsed by `client/renderer/font/FontParserHex.java:55-75` (glyph height 16, `:122`) with `FontUtils.wcwidth` deciding double-width (`util/FontUtils.scala:13-14`). The *format* is GNU Unifont's `.hex`, but the font is **not** Unifont: OC's `README.md:131-134` states "The font used for screens and for monospace text in manual is unscii, made by viznut, and was further expanded by asie" (github.com/asiekierka/unscii-asie), and nothing in the GTNH checkout mentions Unifont. Licensing therefore cannot be taken from unifoundry.com: viznut's unscii variants are public domain except `unscii-16-full`, which packagers (NetBSD pkgsrc `fonts/unscii`) mark GPL because it merges GNU Unifont glyphs — and any Unifont glyphs merged there predate Unifont 13.0.04 (2021), so the SIL OFL 1.1 dual-licence does not cover them. **Before embedding OC's `font.hex`, OpenGPU must check unscii-asie's actual licence**; the alternative is to ship a current GNU Unifont build directly (GPLv2+ with font-embedding exception, dual-licensed OFL 1.1 since 13.0.04, unifoundry.com), which the same `.hex` parser reads. A bitmap font API (`drawText(font, x, y, str)` with per-glyph 8×16 cells, plus user-uploaded bitmap fonts as textures with a glyph table) covers OpenOS-style UIs and matches OC's CP437-centred `basicChars` set (`TextureFontRenderer.scala:15`). Text should be emitted as textured quads from the atlas, so it needs no special rasterizer path.

**Coordinates.** Pixel centres at (x+0.5, y+0.5), y down, origin top-left for 2D (raylib/LÖVE/PICO-8 all agree); 3D NDC y-up with a viewport transform that flips — document which convention `gl_FragCoord` uses (GL: lower-left) and pick one (recommend top-left, D3D-style, matching 2D).

### 3. Software rasterizer design for the JVM

**Algorithm (high confidence; ryg 2013, Abrash 2009, Pineda 1988).** Triangle setup from three edge functions `orient2d(a,b,p) = (b.x−a.x)(p.y−a.y) − (b.y−a.y)(p.x−a.x)`, evaluated at pixel centres; a pixel is inside when all three are ≥ 0 (sign-bit test `(w0|w1|w2) >= 0`); the function is affine so stepping one pixel adds a constant (`three additions per pixel`). Top-left fill rule: compute `bias = isTopLeft ? 0 : −1` once per edge and keep the `>= 0` test; remember to remove the bias before using the weights as barycentrics (ryg notes "the bias slightly changes the barycentric values passed to the pixel shader"). Larrabee used 15.8 fixed point with a `[-16K, +16K)` range, subtracts 1 for left and flat-top edges, and says worst-case edge evaluation needs 48 bits — 64-bit in software — but "90+% of triangles fit in a 128×128" box and use narrower math (Abrash, pp. 108–111, 719–720). ryg's overflow bound: with p-bit coordinates the determinant needs 2p+2 bits, so 32-bit math allows coordinates in `[-16384, 16383]` sub-pixel units; with 4 sub-pixel bits that is a ±1024-pixel guard band, enough for any OpenGPU resolution if triangles crossing the near plane are clipped in clip space and everything else is handled by the guard band + scissor. His trick for more sub-pixel bits: do setup in 64-bit, step in whole pixels (low bits constant), then shift. **Recommendation:** 28.4 fixed point (`int`) for edges, `long` only in setup, near-plane (w > ε) clipping only, guard band ±1024 px, 8 sub-pixel bits only if "wobble" is visible at OpenGPU's small resolutions.

**Hierarchy and tiles.** Larrabee: 64×64 tiles, bins per tile, trivial-reject/trivial-accept corner tests descending 64×64 → 16×16 → 4×4 blocks, 16-wide vector tests; small triangles (≤ one tile, "90% of all triangles") are binned by bounding box only. ryg's measurements: his hierarchical variant was "somewhat faster" than the simple bounding-box loop but "not really enough of a win to justify the effort", because "if a triangle touches less than 10 pixels to begin with, it's just not worth the effort" and most triangles in his scene are that small; the Intel demo binned into 320×90 tiles so each tile's depth buffer "fits comfortably within the L2 cache of a core". llvmpipe: `TILE_ORDER 6` (64×64 tiles), `LP_MAX_THREADS 32`, shader/setup variant caches (`LP_MAX_VARIANTS_PER_FS 16`, `LP_MAX_SETUP_VARIANTS 64`, also `LP_MAX_VARIANTS_PER_CS 16`) (`lp_limits.h`). SwiftShader processes 4 lanes — `SIMD::Width` is an `extern const int` runtime constant in `src/Reactor/SIMD.hpp`, with `assert(SIMD::Width == 4)` in `SIMD::Pointer::Store` and repeated `ASSERT(SIMD::Width == 4)` in `SIMD.cpp`, so 4 is the only width the code actually supports rather than a compile-time guarantee — i.e. 2×2 quads, and ryg's depth rasterizer also uses 2×2 quads with a 2×2-tiled depth layout. **For OpenGPU:** bin triangles per 32×32 tile after transform (one `int[]` list per tile, bounding-box test), then render tiles in parallel; inside a tile use the plain bounding-box loop (triangles are small at 320×200–640×480), add a 4×4 block reject only if profiling shows large-triangle cost. Hierarchical Z and MSAA: skip (Abrash notes MSAA "falls out" of the block-corner scheme, but it quadruples depth memory for little benefit at these resolutions).

**Interpolation, textures, blending.** Perspective-correct attributes: interpolate `attr/w` and `1/w` linearly and divide per pixel (that divide dominates: flat ≈2.4–3 ns/px vs textured ≈8–9 ns/px on JDK 8, measured below, ±20%). ryg's form `z = z0 + l1·(z1−z0) + l2·(z2−z0)` saves a multiply and a conversion per pixel. Depth: `float[]` z-buffer tested *before* the fragment shader (early-Z, legal because the shader cannot write depth in the recommended subset). Textures: power-of-two only in v1 (wrap = `& (size−1)`), nearest and bilinear, optional box-filtered mipmaps chosen per triangle (per-pixel LOD needs quad derivatives; defer). Blending as in §2, premultiplied 8-bit, integer `(x + (x>>8)) >> 8` approximation.

**Java-specific** (high confidence unless stated):
- *Arrays, not `ByteBuffer`* (on Java 8; medium confidence as a general rule). Plain `int[]`/`float[]` loops get range-check elimination (counted int loops, `a[i*scale+off]`, loop-invariant arrays hoisted into locals; HotSpot wiki *RangeCheckElimination*) and the best SuperWord treatment. JDK-8257531 ("Super word not applied to a loop of simple Buffer operations", filed by Paul Sandoz after Daniel Lemire's 2020 blog observation that arrays were "more than 4 times faster" than `IntBuffer`) confirms the `IntBuffer` loop "is getting unrolled but not auto-vectorized" while the `int[]` loop used 256-bit vector adds — but it was **fixed in JDK 16 b28**, so this particular gap exists on Java 8–15 only and is closed on the Java 17–21 + lwjgl3ify path. The panama-dev thread's 8.35 M vs 2.2 M ops/s (array vs buffer; Antoine Chambille's numbers, not Lemire's) was explained in that thread by C2 memory barriers around opaque `bufferBase/bufferAddress` calls and missing unrolling ("Membars are the culprit"), not by vectorization, and after Vladimir Ivanov's fix the buffer variant was at parity or ahead (8.60 M vs 7.96 M ops/s) — so it is not evidence for a permanent array advantage. Use one `int[]` ARGB colour plane and one `float[]` depth plane per render target, row-major, tile-friendly 32-aligned widths; the decision rests on Java 8 behaviour, RCE and the simpler codegen, and can be revisited if OpenGPU ever targets 17+ only. Keep `DirectByteBuffer` only at the edge where the *client* uploads into GL (`GLStateManager.glTexSubImage2D(..., IntBuffer)` exists in Angelica — `Angelica/glsm/src/main/java/com/gtnewhorizons/angelica/glsm/GLStateManager.java:5300` in the 2.2.8 checkout, `:5890` in installed 2.2.21 (`ByteBuffer` overload `:5874`), delegating on the LWJGL2 path to `glsm/backend/Lwjgl2GLRenderBackend.java:451-456` `GL11.glTexSubImage2D` — so the Java 8 + LWJGL 2.9.4 and lwjgl3ify paths both go through the same GLSM entry point).
- *No allocation in the inner loop.* C2's scalar replacement removes a temporary only when it provably does not escape; a control-flow merge of two allocations already defeats it (Shipilev, quark #18: 1.9 ns/op with EA vs 3.8 ns/op and 16 B/op without). So vector types must be scalarized in generated code (`float x,y,z,w` locals), never `Vec4` objects per pixel.
- *Auto-vectorization is weak on JDK 8* (medium confidence): SuperWord on 8u only vectorizes straight-line counted loops; `CMov` vectorization of conditionals arrived in JDK 9 (JDK-8139340), reductions were partly disabled (JDK-8078563), and `c[i]=a[i]*5+b[i]*10` was judged "Unprofitable" (JDK-8181633). The inner loop (coverage branch + depth branch) runs scalar on JDK 8; the JDK 25 column below shows what later JITs recover for free under Java 17–21 + lwjgl3ify. Design for scalar code.
- *Threads.* `ForkJoinPool(parallelism)` with work-stealing; tasks must not block (javadoc). Do not use OC's own `Computer` pool (`Settings.threads` = 4, `Settings.scala:59`; installed `OpenComputers.cfg:295`) — the renderer owns a separate pool sized `min(tiles, cores−1)` with a server-wide cap.
- *Determinism across threads* is free as long as each tile's pixels are written only by that tile's task and triangle order within a tile is the submission order (bins are built serially).

**Throughput measured for this report.** Code: scratchpad `bench/RasterBench.java` (edge-function rasterizer as above, `int[]` colour, `float[]` depth, nearest 256×256 texture) and `bench/ShaderBench.java`; CPU Intel Core Ultra 9 285HX (24 logical), Windows 11; `-Xmx256m`, 2 s warm-up, 3 s measure. The table shows single runs; two independent re-runs on the same JDK 1.8.0_504 (scratchpad `verify-bench/run.log`, `verify6/run.log`) gave flat 338/422, Gouraud 202/207, textured 127/124 Mpix/s, 7.38/6.79 Mtri/s small triangles, ×16 tiles 635/677 Mpix/s, JDK 25 flat 607 — i.e. **treat every figure as ±20% and quote ranges** (flat ~340–420, Gouraud ~200–250, textured ~110–130 Mpix/s single-threaded on JDK 8), not three significant digits.

Reading: ≈2.4–3 ns per flat pixel, ≈4–5 ns per Gouraud pixel, ≈8–9 ns per textured pixel on JDK 8 (±20%); ≈130–140 ns per small triangle (setup dominates below ~30 px); tile parallelism scales ~8.6× at 16 threads once a frame is big enough (640×400), ~5.5× at 320×200 where the ~100 µs frame is dominated by fork/join and the serial depth clear. Older public Java numbers agree in shape: jPCT's software renderer did 40/77/94/110 Mpix/s on 1/2/3/4 cores of a 3.2 GHz Core 2 Quad in 2009 (jpct.net forum); thebennybox's tutorial renderer is a scanline/gradient design with `byte[]` components and clip-space polygon clipping (`RenderContext.java:38-46, 142-206`), no numbers; JavaFX's Prism SW pipeline is 2D-only (`com/sun/prism/sw`, no mesh classes); Marlin (JEP 265, pure Java, default since JDK 9; standalone 0.9.4.7 for JDK 8, GPL2) was within 10% of Oracle's native Ductus single-threaded and ahead multi-threaded in 2014 mapbench runs — a pure-Java rasterizer is competitive when it avoids allocation and uses thread-local contexts.

**Budget arithmetic** (carry ±20–30% error bars from the run-to-run spread above). A 320×200 frame at 20 fps (OC's tick rate) with 3× overdraw of textured pixels is 3.8 Mpix/s ≈ 3–4% of one core here, perhaps 10% on an older server core; a 640×480 frame at 20 fps with 3× overdraw is 18 Mpix/s ≈ 15–40% of a core. Suggested per-GPU per-frame caps by tier (to be tuned): T1 320×200, 0.5 M fragment invocations, 20 k triangles; T2 640×400, 2 M, 100 k; T3 800×600 or 1024×768, 6 M, 300 k; frames clamped to one present per tick; server-wide render pool with `cores−1` threads and a per-tick time slice.

### 4. Shader language and compiler

**Language choice.** Options: (a) GLSL ES 1.00 subset, (b) WGSL subset, (c) custom, (d) Lua. (d) is ruled out by cost: even a megamorphic Java interface call costs on the order of ~1–3 ns/pixel (§3.6, cross-program comparison), while a Lua→Java callback per pixel crosses JNI, the OC budget and the sandbox (OC-LuaJIT's own numbers put a JNI hop at sub-µs, `report-compat-and-perf.md:82`, i.e. ≥100× a shaded pixel); a restricted-Lua-compiled-to-bytecode variant inherits Lua's dynamic typing and gains nothing over a typed DSL. (b) WGSL has the right modern feature set (`@workgroup_size`, `global_invocation_id`, 16 KiB workgroup limit, `i32/u32/f32/f16`, atomics) but its syntax is less familiar to the OC audience and its spec is large. **(a) is recommended:** GLSL ES 1.00 is small, extremely well documented, directly passable to a future client GL backend (Angelica's GL 2.1/3.x context), and its *Appendix A* already codifies the sandbox-friendly restrictions OpenGPU wants: control flow "limited to forward branching and to loops where the maximum number of iterations can easily be determined at compile time"; `for` loops with one loop index of type `int`/`float`, `init = constant-expression`, `index relop constant-expression`, `index++/--/+=/-= constant`, index not assigned in the body; "support for `while` and `do-while` is not mandated"; array/vector/matrix indexing only by constant-index expressions in fragment shaders (spec rev 17, Appendix A §4–5); "Static and dynamic recursion is not allowed" (§6.1). Types (§4.1): `void bool int float vec2..4 bvec2..4 ivec2..4 mat2..4 sampler2D samplerCube`; storage qualifiers `attribute uniform varying const`; precision qualifiers (§4.5.2: `highp` ≥ 2^-16 relative, `mediump` ≥ 2^-10, `lowp` absolute 2^-8) can be parsed and ignored (everything is `float`). Built-ins to support: `gl_Position`, `gl_PointSize`, `gl_FragCoord`, `gl_FrontFacing`, `gl_FragColor`; `gl_FragData`/MRT later. Add two OpenGPU extensions: an explicit `#version 100` check and `discard`.

**Compiler pipeline.** Hand-written lexer + Pratt parser + type checker is the right size (GLSL ES has ~15 precedence levels and no ambiguities worth a generator); ANTLR 4.13.2's Java runtime is 326 KB, BSD-3 and Java 8-compatible since 4.10, acceptable if preferred, but it adds a jar to shade and generated parsers are slower to warm up; Janino (BSD-3, Java 7 target, needs `commons-compiler`) would compile *Java source* at runtime — simplest to prototype but slow to compile (~tens of ms per program) and harder to constrain. ASM 5.0.3 is already on every 1.7.10 Forge classpath (`C:\Games\Minecraft\libraries\org\ow2\asm\asm-all\5.0.3\asm-all-5.0.3.jar`), supports `V1_8` class files, and is what Forge/Mixin use — use it directly (`ClassWriter.COMPUTE_FRAMES` needs a `getCommonSuperClass` override that does not load classes; define generated classes in a per-GPU child `ClassLoader` so they can be unloaded with the GPU).

**Codegen shape (the important part).** Follow llvmpipe/Reactor: "specialization beats generic code when state varies" — branch on pipeline state at *generation* time (blend mode, depth func, texture format/filter/wrap, vertex layout, which varyings exist) so no per-pixel state checks remain; keep a variant cache keyed by `hash(program source, pipeline state)` (llvmpipe caps variants per shader at 16 and setup variants at 64). Concretely, generate one class per (program, pipeline-state) with: `static` fields for uniforms (set via a generated `setUniforms(float[])`), a `vertex(float[] in, int base, float[] out)` method, and a `rasterizeTile(int[] fb, float[] zb, int[] triIds, …)` method that contains the full edge loop with the fragment body *inlined* and all `vecN` scalarized into locals. Why specialize rather than call a per-pixel `PixelShader` interface from a shared rasterizer — what the benchmark actually shows (`ShaderBench.java`, JDK 8, re-run twice): a *monomorphic* interface call is free for an 8 ns textured pixel (110 vs 113 Mpix/s; re-runs 126 vs 133 and 125 vs 124), and in the warm-up pass of the megamorphic run — while the site is still monomorphic — the flat shader via interface ran at 326 Mpix/s on JDK 8 and 590–615 on JDK 25, i.e. no penalty either. Once the same site has seen three receiver classes, the flat shader drops to ~190–215 Mpix/s and, on JDK 25, the polluted profile also deoptimizes the *inlined* baseline in the shared rasterizer method (295 → 174–197 Mpix/s warm; the report's original run: 247 → 166). The original "207 vs 413" (megamorphic flat in `ShaderBench` vs inlined flat in `RasterBench`) compared across two programs and conflated megamorphic dispatch with call overhead; `ShaderBench` has no inlined-flat or monomorphic-flat case. The supportable conclusion is therefore **keep every per-pixel call site monomorphic** — one generated class per (program × state) achieves this, and HotSpot then inlines the shader — and never route several programs through one shared rasterizer method. Generating the whole loop (rather than a per-program class that calls a monomorphic shader method) is sufficient and also removes per-pixel state branches, but the benchmark does not show it is *necessary*; a per-program class with a monomorphic `shade()` call is an acceptable first implementation. HotSpot inlines only monomorphic/bimorphic sites (`UseBimorphicInlining`) or a >90% dominant receiver (`TypeProfileMajorReceiverPercent = 90`), bytecode-size thresholds `MaxInlineSize 35` / `FreqInlineSize 325` (platform-dependent), and **never JIT-compiles a method above `HugeMethodLimit` = 8000 bytecode bytes** (`DontCompileHugeMethods` is on by default and the limit is not tunable in product builds; JDK-8079661, Spark PR 19083). So: unroll nothing, keep each generated method < ~6 KB of bytecode, split the fragment body into a separate `private static` method only if it exceeds that, and reject programs whose generated size exceeds the cap at compile time. Instruction budget: loop bounds are compile-time constants, so the static instruction count per invocation is known; enforce a hard cap (e.g. 4 k scalar ops per fragment, 16 k per vertex) at compile time, which makes a runtime counter unnecessary and keeps the inner loop clean.

**Execution strategies to keep.** (1) A tree-walking interpreter over the typed AST — reference semantics, tests, fallback when codegen fails or ASM is unavailable. (2) ASM whole-loop specialization as above. (3) Future: pass the same GLSL ES source to a client GL backend. Other precedents are not applicable here: Aparapi/Rootbeer go the other way (bytecode → GPU), TornadoVM needs JDK 21, Truffle/Graal needs the Graal compiler and is impractical under LaunchWrapper on Java 8 (medium confidence).

### 5. Compute pipeline

Model it on OpenCL/WebGPU, which agree: a *kernel* is "a function … executed on an OpenCL device", a *work-item* "one of a collection of parallel executions of a kernel", identified by a global ID or work-group ID + local ID; memory regions global/constant/local/private; a barrier synchronizes "all the work-items of a work-group" only (OpenCL 3.0 glossary). WebGPU defaults: `maxComputeWorkgroupSizeX/Y/Z = 256/256/64`, `maxComputeInvocationsPerWorkgroup = 256`, `maxComputeWorkgroupsPerDimension = 65535`, `maxComputeWorkgroupStorageSize = 16384` (MDN `GPUSupportedLimits`); WGSL inputs `local_invocation_id`, `local_invocation_index`, `global_invocation_id`, `workgroup_id`, `num_workgroups`. ISPC's SPMD view is the right *mental* model for the CPU implementation: a gang of program instances in lock-step on one thread (`uniform` vs `varying`, masked control flow) plus `launch/sync` tasking across cores — on the JVM without SIMD the gang is a `for` loop over work-items inside one task, and tasks are workgroups distributed over the `ForkJoinPool`. Futhark's pure `map/reduce/scan` design (no ids, no barriers) is attractive but a second language; Halide's schedule separation is overkill here.

**Recommended v1:** same GLSL-ES-subset frontend with a `kernel` entry point, 1D/2D/3D dispatch, read-only typed input buffers (`float[]`, `int[]`, textures via `texture2D`) and exactly one write-only output buffer indexed by the global id (OpenCL "private" + "global" only, no `local`, no barriers, no atomics). This is embarrassingly parallel and *deterministic regardless of scheduling* because no two work-items write the same location; reductions are expressed as two dispatches (per-group partial sums written to distinct slots, then a second pass), which is also how deterministic GPU reductions are written. Workgroup size is then only a task granularity (e.g. 4096 work-items per ForkJoin task). Readback: `gpu.readBuffer(handle, offset, count)` returning a packed byte string (one Java→Lua copy via `pushByteArray`, `ExtendedLuaState.scala:50`) with a per-call size cap and budget cost proportional to bytes, plus a convenience that returns a Lua table for small counts. Lua-side decoding uses `string.unpack` on 5.3/5.4 and a shipped pure-Lua fallback on LuaJIT and on OC's Lua 5.2 architecture (where `string.unpack` is also `nil`, §1).

### 6. Determinism and sandboxing

- *Floating point.* JEP 306 attributes Java's non-strict default-mode semantics to x87 "peculiarities" (its extended exponent range), says SSE2 "could support strict JVM floating-point operations … without undue overhead", and states that HotSpot will "never run in a floating-point mode which allowed the extended exponent value set"; it does not literally say Java 8 on x86-64 is already strict, but that is a sound inference (HotSpot x86-64 uses SSE2 for `float`/`double`), and Java 17 made strictness mandatory. `strictfp` costs nothing on x86-64 Java 8 and documents intent — use it on the math core. `Math` methods "are not defined to return the bit-for-bit same results" and "code generators are encouraged to use platform-specific native libraries or microprocessor instructions" (`java.lang.Math` javadoc); the permitted error is 1 ulp for most functions (`sin cos tan exp log pow …`), 2 ulps for `atan2` and 2.5 ulps for `sinh cosh tanh`, whereas `StrictMath` must match fdlibm 5.3 for `sin cos tan asin acos atan exp log log10 cbrt atan2 pow sinh cosh tanh hypot expm1 log1p`. Shader built-ins should therefore call `StrictMath` or own fixed polynomial approximations (faster and still deterministic). `Math.fma` does not exist on Java 8. `float` everywhere in shaders; `int` for edge functions; never `double` for anything that is persisted.
- *Why determinism matters here:* the server renders, so clients need no cross-machine agreement, but golden-image tests (JUnit on the standalone core, identical output on Ocelot vs in-game) and reproducible bug reports require that the same command stream + resources produce identical pixels on every JVM and thread count. The tile design in §3 gives thread-order independence; the rules above give JIT/intrinsic independence.
- *Bounding work:* per-frame caps on triangles, fragment invocations (count after early-Z), compute work-items, upload bytes and readback bytes, each tier-scaled and charged to OC's `callBudget` à la `GraphicsCard.resolveInvokeCosts` (`:100-107`) so that an abusive program slows itself rather than the server; a per-GPU render time slice per tick and a server-wide pool; hard caps on resource counts/VRAM via the pools; compile-time instruction and loop bounds (§4), generated-class size cap, compile-rate limiting (a program hash cache prevents recompile storms). Reject NaN/Inf vertex positions at decode time (they break edge-function setup). Frames are presented at most once per tick, which also bounds network traffic (OC's own screen packets are op deltas through `CompressedPacketBuilder` with `Deflater.BEST_SPEED`, `common/PacketBuilder.scala:153`).
- *OCLights2 precedent* (BlueAmulet/OCLights2, branch `opencomputers-1.7`, Forge 1.7.10-10.13.2.1291, Minecraft Mod Public License 1.0.1): a `Deque<DrawCMD>` of ~40 command kinds (`Fill, Plot, CreateTexture, DrawTexture, DrawText, … Push, Pop, Blur, StartFrame, EndFrame`; `CommandEnum.java`), server-side `java.awt` `AffineTransform` stack and `BufferedImage` textures (`gpu/GPU.java:34,69,287`), the command list GZIP'ed and chunked into 32 KB packets that clients replay (`network/PacketChunker.java:31-64`), and a per-call Lua API (`fill, plot, line, filledTriangle, drawTexture, drawText, translate, push, pop, startFrame, endFrame …`). Its README's TODO admits the network code "needs to be more efficient". Lessons: ship dirty tiles or compact commands, never AWT objects; do not tie the renderer to AWT (headless servers, no determinism, GC churn).

## Design implications for OpenGPU

1. API = *resources + pipelines + command buffer*: `createBuffer/Texture/Program/Pipeline/RenderTarget → handle`, `upload(handle, bytes)`, `submit(bytes)`, `present()`, `read*(handle, …) → bytes`; the Lua-facing 2D "immediate" functions are a pure-Lua library that appends to a local string builder and calls `submit` once per frame.
2. One rasterizer path for 2D and 3D (ImGui-style draw lists), plus decode-time fast paths for axis-aligned blits/fills.
3. Software renderer core as a dependency-free Java library with golden-image tests; renderer threads separate from OC's executor; tile-parallel, deterministic.
4. GLSL ES 1.00 subset; interpreter first, ASM whole-loop specialization second; compile-time instruction/loop caps; generated methods < 8000 bytes; variant cache by hash.
5. Compute = same frontend, OpenCL-style ids, single write-only output per dispatch, no barriers in v1; two-pass reductions.
6. Budgets expressed in OpenGPU units (fragments, triangles, work-items, bytes) and charged to OC's existing per-tick `callBudget` via `context.consumeCallBudget` — a policy OpenGPU opts into, as OC's text GPU does, not a cap OC applies by itself; size the costs against the machine's real `maxCallBudget` (mean over CPU and memory tiers, installed config `callBudgets=[1,2,4]` here, jar default 0.5/1.0/1.5) and test against the installed values; per-tier resolution and VRAM pools; present ≤ 1/tick.
7. Expect ~110–130 M textured or ~340–420 M flat pixels per second per core on a modern desktop JVM 8 (±20–30% run to run), ~2–3× less on older server cores, and plan tier caps so a T3 GPU at 640×480 uses well under one core.

## Open questions

1. Target resolutions per tier and whether the display is a new block (pixel screen) or a mode of OC's screen (affects the stream module and the OC adapter, not the core).
2. Colour model for the frame: palettized 8-bit (fantasy-console feel, 4× cheaper to stream) versus 32-bit ARGB internally with palettized *presentation* as an option.
3. Whether Lua programs should see OC's existing `gpu` component API at all (bitblt into the text screen) or only the new component.
4. Is a tree-walking interpreter acceptable as the *only* shader executor for the first release (simplifies Ocelot/tests), with ASM codegen as the second milestone?
5. How much determinism to promise publicly (golden images across JVM versions implies forbidding `Math` intrinsics and documenting the exact blend/rounding formulas).
6. Should the microbenchmark sources (scratchpad `bench/RasterBench.java`, `bench/ShaderBench.java`) be moved into the repo as the seed of `opengpu-core`'s benchmark suite?
