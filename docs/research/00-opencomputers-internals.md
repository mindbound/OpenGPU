## Summary

1. A component is a `ManagedEnvironment` with a `Node` built by `Network.newNode(host, reachability).withComponent(name).withConnector()`; Lua-callable methods are `public Object[] m(Context, Arguments)` annotated `@Callback(direct, limit, doc, getter, setter)`, found by reflection once per class and invoked through an ASM-generated wrapper. [V]
2. `direct=true` callbacks run on one of `computer.threads` (=4) worker threads inside the Lua resume; non-direct callbacks make Lua yield a closure that `Machine.update` runs on the server thread at the next tick (0-50 ms wait), after which the executor is rescheduled with `executionDelay` = 12 ms — a round trip of ~12 ms to ~62 ms plus pool scheduling, i.e. the floor is 12 ms, not "one tick + 12 ms". [V]
3. `limit` is a cost: each direct call subtracts `1/limit` from a per-computer budget reset every tick to `callBudgets[tier]` (defaults 0.5/1.0/1.5; the user's config has 1/2/4). When the cost exceeds the remaining budget a `LimitReachedException` is thrown, the Lua wrapper sees zero results and **re-issues the same call as a synchronized call on the next tick**, so budgeted callbacks must consume budget before mutating anything. [V]
4. Top-level Lua string arguments cross into Java as `byte[]` with no decoding, and `byte[]` results become Lua strings; tables become lazy `java.util.Map` views, but strings *nested inside tables* are converted to `java.lang.String` whenever they round-trip UTF-8 losslessly and stay `byte[]` only otherwise. There is no Java-side size accounting; the only memory limit is the JNLua allocator cap (RAM tier, x1.8 on 64-bit, default 192 KB..1 MB, user config 256 KB..8 MB), and even that is disabled when `debug.disableMemoryLimit = true` (false in the user's config). [V]
5. Screens are server-authoritative `util.TextBuffer` cell grids; every mutation is appended to one compressed `TextBufferMulti` command packet flushed once per tick to every player watching the chunk; clients request the full state with `TextBufferInit`; VRAM pages ride the same channel (`TextBufferRamInit` full NBT once, then `TextBufferBitBlt`). [V]
6. The hologram is the only non-text display: 48x32x48 2-bit voxels in two `Int` bit-planes, per-column dirty tracking, per-tick choice between a delta-list and an area packet, and a TESR that rebuilds a per-hologram VBO lazily; it is the template for a framebuffer display. [V]
7. Large state is persisted outside chunk NBT via `SaveHandler.scheduleSave` (external files under `<world>/opencomputers/state/`), GPU VRAM pages however go into the card's item NBT; screen saves pause connected computers 0.1 s to avoid direct-call races. `SaveHandler.savingForClients` is honoured only by `Machine.save` and `FileSystem.save`: `TextBuffer.save` is not guarded, so every screen description packet also schedules an external buffer write and pauses connected computers. [V]
8. Angelica touch points in the fork: `@ThreadSafeISBRH` on `BlockRenderer` and removal of the per-screen display-list cache in `TextBufferRenderCache` ("display lists do not replay Tessellator vertex state reliably under Angelica"). [V]
9. Packet size envelope on this Forge build: FML does **not** split custom payloads. The vanilla 1,048,576-byte server->client cap is never operative: Forge 10.13.4.1614 binpatches `S3FPacketCustomPayload` to a 2,097,050-byte (0x1FFF9A) limit with a var-short length prefix, and the installed Hodgepodge 2.7.216 replaces that constant with its configurable `packetSizeLimit` (256 MiB in this instance) and lifts the netty frame limit. Client->server stays at the vanilla 32,767 bytes (no binpatch, no Hodgepodge mixin). [V]
10. GTNH releases 1.12.55 -> 1.12.64 leave the screen sync, rendering, GPU budget and VRAM code untouched, but 1.12.58 (#216) changed the public `api.internal.TextBuffer` interface (`dropFile` now takes `byte[]`), so OpenGPU must compile against OC >= 1.12.58-GTNH if it implements that interface; other relevant items are drop-file limits/chunking (#216), AFK-timer bypass for `TextBufferInit` (#220), default `maxSignalQueueSize` 256 -> 1024 (#226). [W for the release list; V for the interface diff]

## Findings

### 1. Component model

**Environment / ManagedEnvironment.** `API/network/Environment.java:50-113` defines `node()`, `onConnect(Node)`, `onDisconnect(Node)`, `onMessage(Message)`; `ManagedEnvironment` (`API/network/ManagedEnvironment.java:19-33`) adds `Persistable` (`load/save(NBTTagCompound)`) plus `canUpdate()/update()` (ticked by the host). The prefab `API/prefab/ManagedEnvironment.java:11-69` stores the node under NBT key `"node"` and, if the node has no address yet at save time, temporarily joins a fresh network to mint one so the address reaches clients (lines 55-62) — this is how client and server component instances get correlated (used by `ComponentTracker`). A node is created with the builder `API/Network.java:183` -> `API/detail/Builder.java:42-79` (`withComponent(name[, visibility])`, `withConnector([bufferSize])` for energy). Reachability/visibility enum: `None | Neighbors | Network` (`API/network/Visibility.java:13-42`). OC's own GPU uses `Visibility.Neighbors` with component name `"gpu"` (`OC/server/component/GraphicsCard.scala:32-36`); screens use `Visibility.Network`, name `"screen"` (`OC/common/component/TextBuffer.scala:43-47`). [V]

**@Callback.** `API/machine/Callback.java:33-147`: `value` (Lua name, default = method name), `direct` (44-59: "may be called directly from the computer's executor thread"; the node network is not thread safe, `Connector.changeBuffer` is), `limit` (61-88: since OC 1.4 a cost — `1/limit` is subtracted from the computer's call budget per direct call; per computer; not applied to host-side `Component.invoke`), `doc` (90-108, format `function(arg:type):result -- Description`), `getter`/`setter` (110-146; work for components only, not for `Value` userdata which use `apply/unapply`). Discovery: `OC/server/machine/Callbacks.scala:82-112` walks the class hierarchy, requires exactly `(Context, Arguments)` params, return type `Array[AnyRef]`, and `public`, logging an error otherwise; results are cached per class (lines 20-27). Each callback gets an ASM-generated `CallbackCall` wrapper class (`OC/server/machine/CallbackWrapper.scala:25-65`), so there is no reflection on the hot path. [V]

**Context / Arguments / Value.** `Context` (`API/machine/Context.java`) exposes `node()`, `canInteract(player)`, `isRunning/isPaused/start/pause(seconds)/stop`, `consumeCallBudget(cost)` (156, dynamic cost for direct calls) and `signal(name, args...)` (184). `Arguments` (`API/machine/Arguments.java:20-375`) has `count`, `checkX/optX/isX` for Any, Boolean, Integer, Long, Double, String, ByteArray, Table (`Map`), ItemStack, and `toArray`. Implementation `OC/server/machine/ArgumentsImpl.scala`: `checkString` accepts `String` or `byte[]` (UTF-8 decode, 165-172), `checkByteArray` returns raw bytes (179-186), `checkTable` accepts `java.util.Map`/Scala `Map`/`mutable.Map` (193-201), `checkInteger` clamps Doubles/Longs to int range instead of erroring (84-111; the strict behaviour is commented out "breaks existing OC1 code"). `Value` (`API/machine/Value.java:23-77`) is the only non-primitive object pushable to Lua: `apply/unapply/call/dispose`, must have a default constructor and implement `Persistable`; `@Callback` methods on a `Value` work like component methods (`OC/server/machine/luac/UserdataAPI.scala:100-106` -> `machine.invoke(value, method, args)`; `OC/server/machine/Machine.scala:404-413`). Prefab: `API/prefab/AbstractValue.java`. `dispose` is called from Lua `__gc` (`UserdataAPI.scala:81-88`). [V]

**Invocation path and threads.** Lua `component.invoke(addr, name, ...)` -> `OC/server/machine/luac/ComponentAPI.scala:74-80` -> `Machine.invoke` (`Machine.scala:385-402`): checks `component.canBeSeenFrom(node)`, then **if `annotation.direct`, `consumeCallBudget(1.0 / annotation.limit)`** (391), then `component.invoke(method, this, args)` -> `OC/server/network/Component.scala:110-118` -> `Registry.convert(callback(env, context, new ArgumentsImpl(args)))`. This runs on whichever worker thread is executing `Machine.run` (`Machine.scala:983-1000`, `architecture.runThreaded` -> `lua.resume`, `OC/server/machine/luac/NativeLuaArchitecture.scala:194-236`). The pool is `ThreadPoolFactory.create("Computer", Settings.get.threads)` (`Machine.scala:1136`), `computer.threads = 4` (`RES/application.conf:119-125`, `CFG:295`). Non-direct calls: `machine.lua` yields a closure (`RES/assets/opencomputers/lua/machine.lua:1093-1101`), `runThreaded` returns `ExecutionResult.SynchronizedCall` (`NativeLuaArchitecture.scala:245-246`), and `Machine.update` on the **server thread** runs `architecture.runSynchronized()` with `inSynchronizedCall = true` (`Machine.scala:597-603`), after which `switchTo(SynchronizedReturn)` (`Machine.scala:606-608`) reschedules the executor on the pool after `executionDelay` (12 ms, `Machine.scala:960-968`; `RES/application.conf:201-207`, `CFG:191`). So a non-direct call costs the wait until the next server tick (anywhere from ~0 to 50 ms) plus 12 ms plus pool scheduling: the floor is ~12 ms, the typical bound ~62 ms. [V]

**Budget accounting.** `callBudget` is `@volatile` (`Machine.scala:80`) and reset to `maxCallBudget` at the top of every `Machine.update` (532). `maxCallBudget` is the average of `CallBudget.getCallBudget(stack)` over installed items implementing `API/driver/item/CallBudget.java` (CPU/APU/RAM) (`Machine.scala:120-126`); values come from `Settings.callBudgets` (`OC/Settings.scala:71-77`; defaults `[0.5, 1.0, 1.5]` at `RES/application.conf:162-166`; the user's config has `[1, 2, 4]`, `CFG:143-147`). `consumeCallBudget` (`Machine.scala:286-294`): if `architecture.isInitialized && !inSynchronizedCall`, throw `LimitReachedException` when `cost > callBudget`, else subtract. With limit = 256 at budget 4 that is 1024 calls per tick; `GraphicsCard.set` costs `setCosts(tier) = 1/64, 1/128, 1/256` (`GraphicsCard.scala:67`) via `resolveInvokeCosts` (100-107). [V]

**What happens when the budget is exhausted.** `NativeLuaArchitecture.invoke` catches `LimitReachedException` and returns **0 results** (`NativeLuaArchitecture.scala:59-77`). In `machine.lua:1080-1103` the wrapper treats `result.n == 0` as "limit reached", sets `result = nil`, and falls into the synchronized path: `coroutine.yield(function() ... target.invoke(...) end)` — i.e. the very same call is executed a second time on the server thread next tick, now with `inSynchronizedCall = true` so budget is ignored. Consequences: (a) the Lua coroutine stalls until the next tick (natural frame-rate limiter); (b) a callback **must call `consumeCallBudget` before any side effect**, otherwise the effect happens twice. `GraphicsCard.bitblt` even uses a `budgetExhausted` flag to detect its own retry and converts the overrun into `context.pause(seconds)` (`GraphicsCard.scala:221-253`). [V] The per-call execution timeout (`computer.timeout = 5.0 s`, `RES/application.conf:131-136`) is a Lua debug hook (`machine.lua:44-54, 1519-1532`) and therefore cannot interrupt a long-running Java callback. [V for the hook mechanism; I for the consequence]

### 2. Drivers and registration

### 3. GPU / Screen / TextBuffer architecture

**Data model.** `OC/util/TextBuffer.scala:18-30`: `buffer: Array[Array[Int]]` (code points) and `color: Array[Array[Short]]` (packed fg/bg via `PackedColor`), plus format (1/4/8-bit palette modes, `OC/util/PackedColor.scala`). NBT: lines as strings in `"buffer"`, colours as a short array `"colors"`, `"depth"`, palette (`TextBuffer.scala:290-308`); load clamps to the max tier resolution (263-266). Tier resolutions 50x16 / 80x25 / 160x50 and depths 1/4/8 bit are hard-coded (`OC/Settings.scala:525-526`); a T3 screen is 8000 cells = ~48 KB in RAM. [V]

**GPU side.** `GraphicsCard.scala:20-30` header comment explains why drawing calls are direct despite side effects and the save-time hack this forces. `bind` is non-direct, resolves `node.network.node(address)` and only requires `node.host.isInstanceOf[api.internal.TextBuffer]` (270-275) — any node host implementing `API/internal/TextBuffer.java` (56-58 declared methods over lines 23-668, of which **five** are `@SideOnly(CLIENT)`: `renderText`, `renderWidth`, `renderHeight`, `setRenderingEnabled`, `isRenderingEnabled` at lines 498-542) can be bound by a stock GPU. Note that this interface changed in 1.12.58-GTNH (#216): `dropFile(String, String, EntityPlayer)` at line 593 of the checkout became `dropFile(String, byte[], EntityPlayer)`, so an implementation compiled against the 1.12.55 checkout would throw `AbstractMethodError` on the installed 1.12.64 jar; compile against OC >= 1.12.58-GTNH (as OC-LuaJIT already does). All drawing callbacks are direct with tier costs (67-72); energy is drawn per unit via `node.tryChangeBuffer` (`consumePower`, 534). Video RAM (OC >= 1.7.6, present here): `allocateBuffer` (135-165) creates a `util.TextBuffer` wrapped in `GpuTextBuffer` (no node: `OC/common/component/GpuTextBuffer.scala:17-19`); capacity `totalVRAM = maxW*maxH * vramSizes[tier]` (74; defaults `[1,2,3]` `RES/application.conf:1667`, user config `[1,2,4]` `CFG:521-525`); `bitblt` (221-268) has a dynamic budget: dirty page -> `bitbltCost * 2^tier * area/maxArea` (196-212; `gpu.bitbltCost = 0.5`), clean page 0.001, VRAM->VRAM free; the first overrun throws `LimitReachedException`, the retry converts remaining cost into `context.pause` (241-253). Pages are persisted inline in the card's NBT under `"videoRam"/"pages"` (646-673). `GpuTextBuffer.bitblt` -> `write_vram_to_screen` does `rawcopy` and then **hands the page object to the screen** (`dstScreen.addBuffer(srcRam)`) and fires `onBufferBitBlt` (`GpuTextBuffer.scala:166-173`); the screen's `VideoRamRasterizer` keeps per-GPU page copies (`OC/common/component/traits/VideoRamRasterizer.scala:78-150`). [V]

**Server -> client sync.** `common.component.TextBuffer` picks a `ClientProxy` or `ServerProxy` at construction via `SideTracker.isClient` (`TextBuffer.scala:94-97`). Every server-side mutation hook (`onBufferSet/Fill/Copy/ColorChange/...`, `ServerProxy` at 739-830) calls `host.markChanged()` and appends a sub-command to a single `CompressedPacketBuilder(PacketType.TextBufferMulti)` (74-78) — the packet types are in `OC/common/PacketType.scala:52-70`. The builder is flushed **once per tick** in `update()` (159-162) with `sendToPlayersNearHost(host, Option(maxWirelessRange(T2)^2))`; because `PacketBuilder.sendToPlayersNearTileEntity` squares the range again (`OC/common/PacketBuilder.scala:86-98`) the distance test is effectively void (`maxWirelessRange` tier 2 is 512 in `CFG:879-882`, giving a 262144-block "range" that is squared again) and the real filter is `isPlayerWatchingChunk` (95), unless `misc.maxNetworkClientPacketDistance > 0` (it is 0 in `CFG:830`). Caution when tuning that key: the config comment (`CFG:826-830`) documents it as "Maximum distance for updates sent from the *client to the server*", yet `PacketBuilder.scala:86-90` applies it to this server->client path. Packets go per player over the FML event channel `"OpenComputers"` (`PacketBuilder.scala:149,161`), deflated at `BEST_SPEED` for `CompressedPacketBuilder` (153). First page use sends the whole page as NBT (`TextBufferRamInit`, `TextBuffer.scala:799-805`, `OC/server/PacketSender.scala:689`), later blits only coordinates (`TextBufferBitBlt`, 676). The client replays commands on its own `util.TextBuffer` (`OC/client/PacketHandler.scala:614-640`). [V]

**Initial state.** On the client, `TextBuffer.load` only reads the node address and registers the buffer (`TextBuffer.scala:432-437`, `registerClientBuffer` 528-532), then sends `TextBufferInit` (client->server) immediately and every `syncInterval = 100` ticks until `markInitialized` (70, 102-106, 163-169). The server (`OC/server/PacketHandler.scala:355-377`) checks `isPlayerWatchingHost` (38-44, GTNH hardening) and that the screen is the multiblock origin, then unicasts a compressed full dump (`PacketSender.scala:748-755`), which the client loads and marks dirty (`client/PacketHandler.scala:593-612`). The tile description packet also carries `buffer.save` (`OC/common/tileentity/traits/TextBuffer.scala:49-52`, `writeToNBTForClient`), but the client ignores the cell data from it — and because `TextBuffer.save` does not check `SaveHandler.savingForClients`, every description packet also schedules an external `_buffer` file write and pauses every connected computer 0.1 s (see section 5). [V]

**Rendering.** `ScreenRenderer` is a TESR (`OC/client/renderer/tileentity/ScreenRenderer.scala`): only the origin renders (44-46), distance (`client.maxScreenTextRenderDistance = 20`, fade from 15; `RES/application.conf:20,26`) and facing culls (48-57), then `screen.buffer.renderText()` (190) -> `TextBuffer.renderText` (`@SideOnly`, `TextBuffer.scala:361`) -> `ClientProxy.render` -> `TextBufferRenderCache.render` (`OC/client/renderer/TextBufferRenderCache.scala:16-31`): regenerate glyph textures if dirty, then **always** `renderer.drawBuffer(...)` through the `Tessellator` (`OC/client/renderer/font/TextureFontRenderer.scala:38-118`: background runs merged per colour, then glyph quads per atlas texture). Line 27 comment: "Keep this uncached: display lists do not replay Tessellator vertex state reliably under Angelica." Upstream MC1.7.10 `TextBufferRenderCache` instead keeps a Guava-cached display list per buffer (2 s expiry) compiled with `GL_COMPILE_AND_EXECUTE` [W, summarised from the upstream file]. The GUI path (`OC/client/gui/Screen.scala:98-107`) uses `BufferRenderer.drawText`; `BufferRenderer` still compiles the GUI border into a display list with `glBegin/glEnd` (`OC/client/renderer/gui/BufferRenderer.scala:36-87`). Font choice `client.fontRenderer = hexfont` (`CFG:67`). [V]

**Multi-block screens.** `OC/common/tileentity/Screen.scala:183-246`: a deterministic BFS over adjacent `Screen` tiles with equal tier/pitch/yaw/colour, merged in sorted order (`tryMerge` 362-397, limits `misc.maxScreenWidth = 8`, `maxScreenHeight = 6`, `CFG:866-870`), run on both sides without any multiblock state being saved (client waits 40 ticks, 45). The origin's buffer node becomes `Visibility.Network`, the rest `Visibility.None` (228-237); the origin gets `setAspectRatio(width, height)` and a bigger render bbox (314-328); click coordinates are projected onto the origin's viewport (`toScreenCoordinates` 100-139, `click` 154-163). [V]

**Input flow.** Client GUI (`OC/client/gui/Screen.scala`) or in-world click -> `api.internal.TextBuffer.mouseDown/keyDown/...` -> `ClientProxy` -> `ClientPacketSender.sendKeyDown/sendMouseClick` (`TextBuffer.scala:686-736`) -> `server.PacketHandler.onKeyDown/onMouseClick/...` (`OC/server/PacketHandler.scala:189-271`; GTNH added NaN/Infinity rejection (36) and clipboard/drop-file size caps (34, 209-227)) -> `ComponentTracker.get(world, address)` (`OC/common/ComponentTracker.scala:19-46`, weak-valued cache keyed by node address) -> `ServerProxy`: keys are forwarded as node messages `"keyboard.keyDown"` to the neighbours of **every** screen block of the multiblock (`sendToKeyboards` 909-916), mouse events become `node.sendToReachable("computer.checked_signal", player, "touch"|"drag"|"drop"|"scroll", x, y, button[, name])` (887-906; sub-cell doubles in precision mode) after an 8-block reach check (`isUseableByPlayer` 407-414). `Machine.onMessage` turns `computer.checked_signal` into a signal only if `canInteract(player)` (`Machine.scala:645-653`). The keyboard component (`OC/server/component/Keyboard.scala:66-104`) converts `keyboard.keyDown` into `key_down` signals itself. A screen offers its node on every face except its front (`Screen.scala:64,67`); the front offers it when, and only when, the adjacent tile is an OC `Keyboard` (`:66-67`), so keyboards connect on any of the six faces and the front is keyboard-only. ### 5. Machine, threads, signals, marshalling, persistence

**Threading summary.** Direct callbacks: worker thread, concurrent with the server tick and with other computers; must be thread safe; `Node` network operations are not safe there (`Callback.java:52-57`). Non-direct: server thread inside `Machine.update`, blocking the tick for their duration. Heavy CPU work in a direct callback blocks only that worker (one of four) and that computer; the 5 s watchdog is a Lua hook and does not fire inside Java (`machine.lua:1519-1532`), so a runaway Java callback wedges a worker permanently. **Concurrency model for direct callbacks.** OC does not use fine-grained locking: `Hologram` wraps every direct callback (`get/set/fill`, `Hologram.scala:154-168`) and the dirty flush in `updateEntity` (399) in `this.synchronized`; `TextBuffer`'s `ServerProxy` appends to `pendingCommands` under `owner.synchronized` (`TextBuffer.scala:742-828`) and the per-tick flush in `update()` takes the same lock (158-161). A coarse per-component monitor plus "consume budget before mutating" is the whole model, and it is what an OpenGPU framebuffer must copy. World save interacts with execution: `Machine.save` bails out while executing and under `savingForClients` (`Machine.scala:821-830`), and `TextBuffer.save` pauses every connected `tileentity.traits.Computer` machine by 0.1 s (`TextBuffer.scala:471-490`) — without any `savingForClients` guard, so it also fires on every tile description packet. [V/I as marked above]

**Signals.** `Context.signal` (`API/machine/Context.java:158-184`): allowed arg types null/Unit/None, Boolean, numeric boxes (Character -> Integer, other Number -> Double), String, `byte[]`, `NBTTagCompound`, and maps with string keys/values (`Machine.convertArg` 317-332, `signal` 335-368); unsupported values are logged and dropped to `nil`. Queue limit `computer.maxSignalQueueSize` (`Machine.scala:110,339` returns `false` when full; default 256 in this build, 1024 since 1.12.64 [W]). Queued signals are persisted in the machine NBT (753-770 load, 821-870 save). Signals are popped one per resume (`NativeLuaArchitecture.scala:229-236`). [V]

**Lua <-> Java value marshalling.** Lua -> Java: `ExtendedLuaState.toSimpleJavaObject` (`OC/util/ExtendedLuaState.scala:106-112`): boolean -> `Boolean`, number -> `Long` if `lua.isInteger` else `Double`, **string -> `byte[]`** (no UTF-8 decode), table -> `java.util.Map` through JNLua's `DefaultConverter` (a lazy `AbstractTableMap` view, `C:\Users\astro\Downloads\OC-JNLua\...\DefaultConverter.java:361-376`; strings nested inside tables are converted to `java.lang.String` whenever they round-trip UTF-8 losslessly and stay `byte[]` only otherwise, so binary blobs inside tables are not reliably raw — pass them as top-level string arguments), userdata -> raw object. Java -> Lua: results first go through `Registry.convert` (`OC/server/driver/Registry.scala:165-246`: Scala numbers unboxed, arrays/`Seq`/`Product` -> lists, maps -> maps, `Value` passthrough, anything else via registered `Converter`s or `toString`) and then `ExtendedLuaState.pushValue` (27-69): `byte[]` -> Lua string via `pushByteArray`, `Array[_]` -> sequence table, `Map` -> table, `Value` -> userdata (if `debug.disableUserdata` is false). There is **no explicit string/result size limit**; memory accounting exists only inside the Lua allocator: JNLua `setTotalMemory(kernelMemory + RAM*ramScale)` (`NativeLuaArchitecture.scala:152-163`, applied only when `Settings.get.limitMemory` = `!debug.disableMemoryLimit` is true, `OC/Settings.scala:455` — servers that set `debug.disableMemoryLimit = true` have no memory accounting at all and OpenGPU result sizes would then be unbounded; the user's `CFG:335` has `false`; `ramSizes` default 192..1024 KB, `ramScaleFor64Bit = 1.8`, `maxTotalRam` 64 MiB — `RES/application.conf:242-273`; user config 256..8192 KB and 128 MiB, `CFG:229,251-258`). Pushing a result that does not fit raises `LuaMemoryAllocationException` -> "not enough memory" crash (`NativeLuaArchitecture.scala:295-298`). Java objects referenced from `Value` userdata are not accounted at all. OC-LuaJIT reuses exactly this path (`LuaJITArchitecture extends NativeLuaArchitecture`, `OC-LuaJIT\...\arch\LuaJITArchitecture.java:83`), but all numbers arrive as `Double`: `LuaStateLuaJIT` extends the base JNLua `LuaState` (`LuaStateLuaJIT.java:30`) without overriding `isInteger`, and the base `LuaState.isInteger` returns `false` (`OC-JNLua LuaState.java:921-923`); `lua_isinteger` is only wired up in the 5.3/5.4 subclasses. ## Design implications for OpenGPU

1. **Component shape.** Model the card as an `Item` driver (`Slot.Card`, tier from the stack, `HostAware` to Case/Server/Robot as desired, `createEnvironment` returning `null` client side) producing a `prefab.ManagedEnvironment` with `Visibility.Neighbors`; model the display as a tile entity hosting a `Visibility.Network` component. Register both in FML `preInit` or `init` (OC locks the driver registry in its own `postInit`, which under `required-after:OpenComputers` runs before the addon's). Give the display a `bind(address)` non-direct callback mirroring `gpu.bind`; optionally also implement `api.internal.TextBuffer` on the display so stock GPUs/OpenOS can bind it as a text console, since `gpu.bind` only checks that interface — if so, compile against OC >= 1.12.58-GTNH (the `dropFile` signature changed there) and stub the five `@SideOnly(CLIENT)` members.
2. **Budget semantics.** Make every drawing call `direct`, call `context.consumeCallBudget` **before** mutating state, and keep callbacks idempotent across the LimitReached retry; a budget overrun stalls the Lua thread until the next tick, which is the de-facto frame pacing. Prefer coarse commands (a command buffer or draw list passed as one byte string) over per-primitive calls so a frame costs few budget units; copy `bitblt`'s dynamic-cost + `pause` pattern for expensive calls (large blits, shader dispatches).
3. **Binary transport.** Pass vertex/pixel/shader data as Lua strings: they arrive as `byte[]` with zero copies, and `byte[]` results return as strings. Keep framebuffers, vertex buffers and compiled shaders **server side** behind handles (`Value` userdata or integer ids like VRAM pages) because Lua RAM is 192 KB-1 MB by default and a 32-bpp framebuffer does not fit; remember `Value` objects are not memory-accounted and must be `Persistable` with a default constructor, and that Lua 5.2/LuaJIT lacks `string.pack`, so provide Java-side packing helpers or accept tables for small data.
4. **Execution placement.** Shader/rasterisation work runs on the computer worker thread inside direct callbacks: fine for the server tick, but it must be self-bounded (max primitives/pixels per call, cost scaled by work) because the 5 s watchdog cannot interrupt Java. Never touch the node network or world from a direct callback; queue such work for `update()`. Copy OC's concurrency model as-is: one coarse monitor per component (`this.synchronized` around every direct callback and around the server-tick flush/save, as `Hologram` and `TextBuffer.ServerProxy` do), with budget consumed before the first mutation; a per-pixel lock-free design is not needed and is not what any OC display does.
5. **Sync protocol.** Reuse the TextBuffer design verbatim: server-authoritative state, dirty-region tracking, one compressed packet per display per tick on OpenGPU's own FML channel, delivered to players watching the chunk; client-initiated full resync (`TextBufferInit` style) validated with a watching-chunk check; command replay on the client for cheap operations, pixel/tile uploads for the rest. Design to the **portable** server->client payload cap of ~2 MB (Forge's binpatched 2,097,050-byte limit; GTNH packs with Hodgepodge raise it to 256 MiB, but a Forge-only server does not) — tile large framebuffer updates and compress; a 320x200 RGB frame compresses well but a 1024x768x32 bpp frame is 3 MiB raw and must be tiled or delta-encoded even on Hodgepodge-free servers — and the 32 KiB client->server cap (input only; it is not raised by any patch in this stack). A deliberate alternative worth evaluating: ship draw lists instead of pixels and rasterise on both sides deterministically (bandwidth-cheap, but the client renderer then needs the same software rasteriser or a GL re-implementation, and readback/persistence still need the server copy).
6. **Persistence.** Store framebuffers/VRAM outside chunk NBT (SaveHandler-style external files; `li.cil.oc.common.SaveHandler` is reachable but internal, so either depend on it via `MethodHandle` like OC-Wasm or implement an equivalent), check `SaveHandler.savingForClients` yourself (OC's own `TextBuffer.save` does not, which is why every screen description packet schedules an external write and pauses computers — do better: keep heavy saves and machine pauses out of `writeToNBTForClient`), and pause connected machines on real saves as `TextBuffer.save` does to avoid torn state. Keep item-NBT state tiny (handles, indices).
7. **Rendering under Angelica.** Use a TESR with VBOs or `Tessellator`; avoid display lists for anything built from `Tessellator` state; upload framebuffers with `glTexSubImage2D` into a persistent texture per display, cached with expiry and explicit deletion as `HologramRenderer` does; annotate any ISBRH with `@ThreadSafeISBRH`. Keep GL11/GL15-level calls so the Java 8/LWJGL2 and Java 17+/lwjgl3ify paths both work. Test the hologram renderer in-game under Angelica first: it is the closest existing VBO-based TESR and no issues were found in the fork's code, but neither was explicit Angelica handling.
8. **Input and multiblocks.** Reuse the keyboard flow by forwarding `keyboard.keyDown/keyUp/clipboard` node messages to neighbouring keyboards; implement in-world touch with server-side reach checks and `computer.checked_signal` so `canInteract` applies. Copy the deterministic multiblock merge if multi-block displays are wanted (no multiblock state is persisted; both sides recompute).
9. **Portability.** Ocelot-brain carries the same machine/GPU/VRAM/hologram abstractions (`totoro.ocelot.brain.entity.GpuTextBuffer`, `GenericGPU`, `HologramProjector`, `Machine.callBudget`), so a Minecraft-free core (framebuffer, rasteriser, shader compiler, command encoding) with thin OC and Ocelot adapters is both feasible and the right modularity boundary.
