# 07 — Feasibility, performance envelope, risks and candidate architectures

Researcher 7 of 8 · 2026-10-08 · Scope: quantitative feasibility of OpenGPU on OC 1.12.64-GTNH / Forge 10.13.4.1614 / Angelica 2.2.21, with explicit assumptions and arithmetic. Local checkouts cited as `path:line` (OC-GTNH checkout = tag 1.12.55-GTNH, HEAD f83bd95; installed jar is 1.12.64-GTNH — the GitHub changelog for .56–.64 contains no GPU/screen/budget/packet changes, only API additions and a signal-queue default of 1024, so the cited code is applicable). Numbers marked **[measured]** come from a source; **[derived]** are arithmetic on measured inputs; **[est.]** are my engineering estimates and must be validated in M0.

## Summary

1. The project is feasible on this stack, but only in a specific shape: a **batch-oriented, handle-based API** (one direct call carries a whole command buffer as a binary Lua string), a **software reference renderer on an OpenGPU-owned thread pool**, and **client-side GL replay of the same command stream for 3D**. Server-rendered full-motion 3D is not network-feasible beyond LAN; 2D UI streaming is cheap.
2. The call-rate wall is real but it is a stall, not a cliff: with the installed budgets `[1,2,4]` a T3 GPU gets 1,024 `gpu.set` per tick. The first over-budget call is re-issued as a synchronized call that the *next* `Machine.update()` executes on the server thread (`Machine.scala:286-294`, `machine.lua:1087-1101`, `Machine.scala:597-604`) — but that same `update()` has already refilled `callBudget` (`Machine.scala:532`, the only assignment) before it runs the deferred call, and the executor is rescheduled with a full budget `executionDelay=12 ms` later (`Machine.scala:966-968`). A tight loop therefore gets ≈ budget/cost + 1 calls per tick (T3 installed ≈ 1,025/tick, ≈ 20,500/s) and pays a ≤ 50 ms stall each time the budget runs out; it does not degrade to 20 calls/s.
3. OpenGPU's own callbacks can be unlimited (`limit` defaults to `Integer.MAX_VALUE`, cost 4.7e-10), so the real per-call wall is binding overhead — JNI upcall, `machine.lua` wrapper, argument/result marshalling; OC's callback dispatch itself is an ASM-generated trampoline, not reflection (measured by 11 §2: 4.2–4.5 µs empty, 5–9 µs with scalar args on OC's Lua 5.2/5.3/5.4, 1.5–2.4 µs on OC-LuaJIT); 1000 calls/frame at 20 FPS would burn ≈ 9–18 % of one of OC's four shared worker threads — hence batching.
4. Server CPU per frame **[est.]**: 2D UI 0.3 ms (320×200) / 1 ms (640×400); 1–2k textured triangles 2–3 ms / 8–10 ms; 64k-element compute kernel 0.2–0.6 ms compiled to bytecode vs 10–60 ms interpreted. Deflate of a full 640×400 16-bit frame costs ~5 ms by itself (zlib level 1 ≈ 100 MB/s).
5. Network: 2D UI ≈ 20–80 KB/s per viewer; full-motion 3D at 320×200/16-bit ≈ 1.0–1.7 MB/s per viewer (delta+deflate, ~2× ratio) — 10–50× over what OC's own screens burst (≤ ~20 KB/tick). The FML server→client payload cap is 2,097,050 bytes (verified in the FML 1.7.10 patch).
6. Angelica is the dominant external risk for client-side rendering: it rewrites every mod's GL calls (GLSMRedirector), emulates FFP under a GL 3.3 core profile that *is* active on the user's Java 8/LWJGL 2.9.4 instance (`fml-client-latest.log`: "Created GL 4.6 core profile context", "GL 3.3 core profile detected, enabling FFP shader emulation"), ships an opt-in SDL-GPU (Vulkan/Metal/D3D12) backend with GLSL cross-compilation since 2.2.0 that only exists on Java 17+/lwjgl3ify (on Java 8 the log reports `SDLGPURenderBackend could not be instantiated`, backend `OpenGL (LWJGL2)`), and OC-GTNH itself had to drop display lists for it (`TextBufferRenderCache.scala:28`). Architecture A's path (one `glTexSubImage2D` + textured quad) is the least exposed.
7. Persistence must not put framebuffers in tile/item NBT: OC already keeps screen buffers in side files via `SaveHandler` (`common/SaveHandler.scala:49-114`); GPU VRAM pages, by contrast, are saved inline (`GraphicsCard.scala:646-673`) and are tiny. Lua should hold only integer handles so OC-LuaJIT's serializer never sees OpenGPU userdata.
8. Proposed tiers: T1 160×100 @ 8-bit palette, 10 FPS; T2 320×200 @ 8-bit, 20 FPS; T3 640×400 @ RGB565, 20 FPS server-side (3D via client path). All are 16:10 and integer fractions of OC's T3 text raster (160×50 cells × 8×16 px = 1280×800).
9. M0 should de-risk, in order: (a) batched call + Lua-side encoding cost on 5.3/5.4/OC-LuaJIT (Ocelot harness exists), (b) streamed 320×200 framebuffer rendered in-game with Angelica on Java 8 and Java 21/lwjgl3ify, (c) a tiny shader-IR→JVM-bytecode compiler with loop budgets on both JVMs.

## Findings

### 1. Three candidate architectures

Common inputs. Resolutions R1 = 320×200 = 64,000 px, R2 = 640×400 = 256,000 px. Server tick = 50 ms. CPU reference: the user's bench box is a Ryzen 7 7840U (`OC-LuaJIT/bench/results-2026-09-01.md:7`), ~4–5 GHz single-core; a dedicated GTNH server is typically similar or slower. Compression reference **[measured, C]**: zlib level 1 ≈ 100 MB/s compress / 415 MB/s decompress, LZ4 ≈ 780 MB/s (lzbench, i7-9700K, Silesia; see Sources). The JDK's `Deflater` is zlib via JNI, so Java throughput is close to these. OC already uses `Deflater.BEST_SPEED` for screen packets (`common/PacketBuilder.scala:153`).

Per-frame cost model used throughout (**[est.]**, to be measured in M0):

| Stage | Formula | Assumed constants |
|---|---|---|
| 2D fills/blits | touched_px × c_fill | c_fill = 0.3 ns (solid, `Arrays.fill`-like) … 3 ns (alpha-blended glyph) |
| 3D vertex stage | verts × c_vtx | c_vtx = 30–50 ns (4×4 transform, divide, viewport; compiled shader inlined) |
| 3D raster | fragments × c_frag; fragments ≈ overdraw × covered_px | c_frag = 10–20 ns (z-test, affine/persp texel fetch, modulate, pack); overdraw 2 |
| Compute | elements × c_elem | c_elem = 2–10 ns compiled; 100–500 ns tree-walking interpreter |
| Delta detect | px × c_cmp | c_cmp ≈ 0.5–1 ns (int compare, C2 vectorised) |
| Deflate | bytes / 100 MB/s | zlib level 1 |

**Architecture A — server-authoritative software rendering, streamed framebuffer.**

Server CPU per frame **[derived from the model]**:

| Workload | 320×200 | 640×400 |
|---|---|---|
| (i) 2D UI (1.5× screen touched, 200 glyphs, 50 rects) | ≈ 0.2–0.5 ms | ≈ 0.8–2 ms |
| (ii) 1–2k textured tris, simple shaders (128k / 512k fragments + 3–6k verts) | ≈ 1.5–3 ms | ≈ 6–11 ms |
| (iii) compute kernel, 64k elements, ~30 ops each | 0.15–0.65 ms compiled; 6–30 ms interpreted | same |
| delta detect + deflate of a *full* 16-bit frame | 0.06 + 1.3 ms | 0.25 + 5.1 ms |

At 20 FPS a 640×400 3D display therefore costs ≈ 0.2–0.3 core-seconds per second *before* compression and ≈ 0.3–0.4 with it; ten such displays saturate 3–4 cores. 2D UI with dirty-tile compression is two orders of magnitude cheaper.

Network bytes/frame/viewer under delta+deflate **[derived]**. Entropy reasoning: flat-colour UI content deflates 5–10×; textured/shaded 3D frames deflate only 1.5–2.5× (16-bit) or 2–3× (8-bit indexed), and frame-to-frame XOR of a moving 3D scene gains little. Dirty-tile delta is what makes UI cheap.

| Content | 320×200 | 640×400 |
|---|---|---|
| 2D UI, ~5 % of tiles dirty per frame | 6.4 KB raw → ≈ 1 KB; 20 FPS → **20 KB/s** | ≈ 4 KB; → **80 KB/s** |
| 2D UI full repaint (menu switch) | 128 KB raw → 15–25 KB (one-off) | 512 KB → 60–100 KB |
| 3D full motion, 16-bit | 128 KB → 50–85 KB/frame; 20 FPS → **1.0–1.7 MB/s** | 512 KB → 200–340 KB; → **4–7 MB/s** |
| 3D full motion, 8-bit palette | 64 KB → 25–40 KB; → 0.5–0.8 MB/s | — |

OC precedent for "acceptable burst": a T3 screen full repaint is ~50 `set` calls batched per tick into one `TextBufferMulti` `CompressedPacketBuilder` (`common/component/TextBuffer.scala:74-78,158-161`): **[est.]** ≈ 8–24 KB pre-deflate per tick; a hologram full-area update is 48×48 columns × 2 ints = 18,432 B pre-deflate per tick (`Hologram.scala:36-55,396-416`, `PacketSender.scala:244-260`) and also goes through `CompressedPacketBuilder` (`PacketSender.scala:245`), so its wire size is smaller still. OC has lived with ≤ ~20 KB/tick (≤ 400 KB/s) *pre-compression* worst-case bursts per device and ~zero sustained. Architecture A's 3D numbers (already post-deflate) exceed that by 3–20× sustained, which is why A alone cannot carry 3D over the internet. Caveat: the 3D figures rest on the assumed 1.5–2.5× deflate ratio for 16-bit frames and nothing in the sources measures them; the LAN-only conclusion is engineering judgement on an **[est.]**, to be confirmed by M0.2's byte counts. Hard limit: FML's patched `S3FPacketCustomPayload` rejects server→client payloads > 2,097,050 bytes (`fml/patches/.../S3FPacketCustomPayload.java.patch`, verified); client→server stays at vanilla 32,767 — irrelevant here except for input events.

Client cost: inflate 50–340 KB (0.1–0.8 ms), one `glTexSubImage2D` of 256 KB–1 MB (0.1–0.5 ms), one textured quad. Memory per display, server: R1 ≈ 0.6 MB (16-bit front + previous frame 2×128 KB, int z-buffer 256 KB, deflate scratch) + textures; R2 ≈ 2.5 MB + textures; client: one RGBA texture (R2 = 1 MB). Latency Lua-call→pixels (LAN, **[derived]**): render 2–10 ms + encode 1–5 ms + wait for server-thread send 0–50 ms (avg 25) + decode/upload 0.5 ms + wait for client frame 0–16 ms ≈ **35–60 ms avg**; +20–80 ms on the internet. OC itself sends packets from its worker threads, but not from `beep` (a non-direct callback that runs in `Machine.update()` on the server thread, `Machine.scala:456-471, 597-604`): the direct callbacks `FileSystem.read/write/open/exists/size/isDirectory/lastModified` and `Drive.readSector/writeSector/readByte/writeByte` call `diskActivity()` → `ServerPacketSender.sendFileSystemActivity` → `OpenComputers.channel.sendTo` (`FileSystem.scala:172-195, 362-367`; `Drive.scala:93-133, 215-220`; `PacketSender.scala:132-169`), rate-limited to one packet per 500 ms per disk and tolerant of the `FMLEventChannel` attribute race (13 §1.3, §2.2). OpenGPU should not copy that path; it should hand finished `FMLProxyPacket`s to `NetworkManager.scheduleOutboundPacket`, which is the thread-safe queue every FML send ends in (13 §1.4-1.5). Sending from the OpenGPU pool thread that way removes the 25 ms average tick wait (≈ 15–30 ms LAN) at the cost of tick-atomic ordering only; per-connection order follows `execute()` order (13 §1.5). Multiplayer: `CPU_server = Σ_d f_d·(t_render,d + t_encode,d) + Σ_d f_d·n_d·t_send` (encode once per frame, not per viewer); `BW_out = Σ_d f_d·n_d·bytes_d`. Example: 10 displays × 3 viewers of 2D UI at 320×200 = 30 × 20 KB/s = 0.6 MB/s total (fine); the same with 3D = 30 × 1.3 MB/s = 39 MB/s (impossible).

**Architecture B — client-side hardware rendering, replicated command/resource stream.**

Server CPU per frame: validation of a 30–60 KB command buffer (bounds, handle checks) ≈ 0.05–0.2 ms **[est.]**; no raster. Readback (`getPixel`, screenshots) and compute need a server-side software path anyway, so (iii) costs what A costs. Network: with resident vertex/index buffers and textures uploaded once, a frame is uniforms + draw calls ≈ 0.2–2 KB → 4–40 KB/s per viewer; streaming 1k triangles every frame is 30 KB raw (int16 pos+uv) → ~20 KB deflated → 400 KB/s, so residency is mandatory. Client: 1–2k triangles are free for the GPU; the costs are shader compile (cached), FBO per visible display (R2 RGBA+depth = 2 MB VRAM), and the GL state churn Angelica has to track. Latency: validate 0.1 ms + send + client frame ≈ 20–40 ms LAN. Memory per display server-side: only the resource store (texture cap per tier dominates). Scaling: server CPU ∝ M (tiny), bandwidth ∝ Σ n_d × command bytes, client work ∝ *visible* displays only (cull by distance as OC does with `maxScreenTextRenderDistance=20`, installed config line 89 — a client render-cull setting). Note that the per-tick *recipient* set, and hence Σ n_d, is decided server-side by `PacketBuilder.sendToPlayersNearTileEntity` (players watching the chunk within `(viewDistance+1)*16` blocks, capped by `maxNetworkClientPacketDistance`, which is `0` = no cap in the installed config, line 830), not by the render distance.

**Architecture C — hybrid: software reference path everywhere + optional client acceleration on the same stream.** This is what OCLights2 (the OC port of CCLights2) did per call: every draw callback runs `gpu.processCommand(cmd)` into a Java2D `BufferedImage` and pushes the same command to a drawlist replayed on clients (`scratchpad/oclights2/.../TileEntityGPU.java:124-125`, `Texture.java:82`), with packets chunked at `Short.MAX_VALUE-100` bytes (`PacketChunker.java:38`) and 256×144 monitors. The stale `config/OpenGPU.cfg` in the user's instance (2026-08-04; `MonitorSize=256x144`, `TTrans`, `Tablet`) has that mod's config shape plus three categories (`external monitor`, `monitor`, `tablet`) that this OCLights2 revision does not write; OCLights2 names its config via `getSuggestedConfigurationFile()` under modid `OCLights2` (`OCLights2.java:22,51`) and the instance also holds a `config/OCLights2.cfg` (2026-07-19), so `OpenGPU.cfg` was written by a derived build registered as modid `OpenGPU`, not by OCLights2 itself (see Open question 5). C costs two renderers but buys: one API, one persistence model, deterministic readback/compute, A as the guaranteed fallback when Angelica rejects the GL path, and B's bandwidth for 3D. A single shader IR compiled to both JVM bytecode and GLSL keeps the two renderers from drifting; a conformance test (render the same stream in both, compare per-pixel within tolerance) is the maintenance control. **Recommendation: C**, with the software path authoritative for anything Lua can read back.

### 2. The OC call-rate wall

Mechanics (verified): `Machine.update()` resets `callBudget = maxCallBudget` once per server tick (`Machine.scala:532`). `maxCallBudget` is the *average* of the CPU's and RAM's `getCallBudget` (`Machine.scala:123-126`; `DriverCPU.scala:69`, `DriverMemory.scala:40` both return `Settings.get.callBudgets(tier)`). Every direct call subtracts `1/limit` (`Machine.scala:385-392`); OC's GPU additionally charges explicit costs via `consumeCallBudget` (`GraphicsCard.scala:63-69,100-107`). When `cost > callBudget`, `LimitReachedException` is thrown (`Machine.scala:286-294`), the native wrapper turns it into zero results (`NativeLuaArchitecture.scala:76-77`), and `machine.lua` re-issues the call as a *synchronized* call — `coroutine.yield(function() … end)` (`machine.lua:1087-1101`) — which `Machine.update()` executes on the **server thread** (`Machine.scala:597-604`) with the budget check bypassed, then reschedules the executor (`switchTo` → `threadPool.schedule(..., executionDelay=12 ms)`, `Machine.scala:966-968`). Crucially, the reset at `Machine.scala:532` runs unconditionally at the top of `update()`, *before* the `SynchronizedCall` branch at `:597`, so the deferred call is executed with a freshly refilled budget and the executor resumes with that full budget. Exceeding the budget therefore costs **one tick (≤ 50 ms) of executor stall plus a server-thread hop per overrun**; steady-state throughput of a tight loop is ≈ budget/cost + 1 calls per tick, not one call per tick. (Byte-identical in GTNH master as of 2026-09-30, so this holds for the installed 1.12.64; OC-LuaJIT inherits the same protocol, `OC-LuaJIT/docs/roadmap.md:199`.)

Budgets: installed `callBudgets=[1,2,4]` (`config/OpenComputers.cfg:143-147`); OC's shipped default is `[0.5,1.0,1.5]` (`application.conf:162-166`, `Settings.scala:71-77`). `gpu.set` costs `1/64, 1/128, 1/256` for GPU tiers 1–3 (`GraphicsCard.scala:66`).

| CPU+RAM tier (= GPU tier) | `gpu.set` per tick, installed | per second | OC default per tick | per second | tight loop past the budget (installed) |
|---|---|---|---|---|---|
| T1 | 1 ÷ 1/64 = **64** | 1,280 | 32 | 640 | ≈ 65/tick, 1-tick stall per overrun |
| T2 | 2 ÷ 1/128 = **256** | 5,120 | 128 | 2,560 | ≈ 257/tick, 1-tick stall per overrun |
| T3 | 4 ÷ 1/256 = **1,024** | 20,480 | 384 | 7,680 | ≈ 1,025/tick, 1-tick stall per overrun |

(`gpu.fill` is 2× dearer, `gpu.copy` 4×; `bitblt` of a dirty full-size page costs `0.5·2^tier` and is throttled with `context.pause()` when over budget — `GraphicsCard.scala:70-74,233-251` — a precedent OpenGPU can reuse for expensive calls.)

For OpenGPU's own `@Callback(direct=true)` methods `limit` defaults to `Integer.MAX_VALUE` (`api/machine/Callback.java:88`), i.e. cost 4.66e-10: the budget is not the limiter. The limiter is per-call overhead: JNLua C→Java upcall, `machine.lua` `invoke` wrapper (`table.pack`, `unwrapUserdata`, `processResult`), `Machine.invoke` → network node lookup (`Machine.scala:385-393`) → `Component.invoke` (`Registry.convert` + `new ArgumentsImpl`, `server/network/Component.scala:110-118`) → the callback's ASM-generated `CallbackWrapper` trampoline (`Callbacks.scala:120-123` `createCallbackWrapper(method)`; `CallbackWrapper.scala:26-70` emits CHECKCAST + INVOKEVIRTUAL into a private `GeneratedClassLoader`, cached per `Method`) → result push. GTNH OC does **not** use reflective `Method.invoke` on this path (that is upstream OC behaviour), so there is no reflection cost to eliminate. **measured 4.2–4.5 µs per empty call and 5–9 µs with scalar arguments** on OC's Lua 5.2/5.3/5.4, 1.5–2.4 µs on OC-LuaJIT, identical on JDK 8 and 17 (11 §2; the earlier 5–20 µs estimate contained the truth but its top end was 2–4× too pessimistic; OC-LuaJIT's component-bound test used *indirect* calls, which cost a full tick each regardless of VM — `results-in-machine-2026-09-03.md:51-61`). Consequence: a per-triangle or per-vertex API at 1,000 triangles/frame × 20 FPS = 20,000 calls/s ≈ 0.09 core-seconds per second on PUC (0.03 on LuaJIT) of OC's **shared** 4-thread executor for a single computer, plus 3,000 Lua table allocations per frame. The API must be batch-oriented: one call per frame (or per few hundred commands) carrying a binary string, and resources (meshes, textures, shaders) resident on the server/client and addressed by integer handles exactly as OC's VRAM buffers are (`allocateBuffer` returns an index, `GraphicsCard.scala:134-168`). `limit` can still be used deliberately: `present` with `limit=2` costs 0.5 → T1 default budget allows 1 present/tick, T3 installed allows 8, i.e. a tier-scaled frame cap for free — enforced by stalling the executor one tick per overrun (the over-budget `present` still runs, on the server thread, next tick), not by dropping to 20 calls/s.

Lua-side cost to build a 1,000-triangle command buffer per frame **[est., from OC-LuaJIT ratios]**: 3,000 vertices × `string.pack("<hhhhh", …)` (0.4–0.8 µs each on PUC 5.3) ≈ 1.2–2.4 ms, `table.concat` of 3,000 pieces ≈ 0.3 ms, plus 4.5 ms if vertex transforms are done in Lua (≈ 1.5 µs per 4×4 multiply) → **≈ 2–7 ms on Lua 5.3**, ~25 % less on 5.4 (geomean 1.36× standalone, `results-2026-09-01.md:33`). OC-LuaJIT with JIT on: the in-machine ratios are measured against a **PUC 5.2** baseline in ocelot-brain, not the Lua 5.3 the player runs (`results-in-machine-phase1-2026-09-04.md:68-77`): 11.5× (matmul) and 13.2× (mandelbrot) are the top of the range, while nqueens is 1.55×, trampoline 1.61×, binarytrees 3.24× and byte-shuffling `strings2` 2.95×; standalone against Lua 5.3 (`results-2026-09-01.md:30-34`) mandelbrot is 16.5× and strings2 3.7×. A realistic expectation for encoding/transform code is therefore a few ×, → **≈ 0.7–2.5 ms**, *provided* the encoding avoids JIT-hostile patterns (`{string.byte(s,i,i+63)}` / `string.char(unpack(t,1,64))` made LuaJIT 4× slower than 5.3, `results-2026-09-01.md:49-66`) and does not rely on `string.pack`, which LuaJIT (5.1 + 5.2 compat) lacks. Memory: the 60 KB string plus a 3,000-entry temp table (~150 KB) is unaffordable on a T1 machine (256–512 KB `ramSizes`, config line 251; ×1.8 `ramScaleFor64Bit`) → T1 needs small batches or resident meshes. The cheapest design pushes transforms into the server/client vertex shader so a frame is ~100 bytes of uniforms.

JNLua marshalling of a 100 KB string: OC converts Lua strings with `lua.toByteArray` (`ExtendedLuaState.scala:109`); natively that is `lua_tolstring` (no copy) + `NewByteArray` + `GetByteArrayElements`/memcpy/Release (`OC-JNLua/native/src/jnlua.c:919-960`) — one or two 100 KB copies ≈ **20–40 µs** plus ~1 µs JNI overhead **[derived, memcpy 5–10 GB/s]**; 100 KB of young-gen garbage per frame (2 MB/s per display at 20 FPS) is negligible. The callback must read it with `args.checkByteArray(i)` (`ArgumentsImpl.scala:179`); `checkString` would UTF-8-decode (`ArgumentsImpl.scala:169`), corrupting binary payloads and costing ~100–200 µs more. In the other direction (readback) `lua.pushByteArray` is the symmetric copy.

### 3. Tick budget and threading

What the server main thread must do per frame: nothing but hand-offs. Per active display per tick: check an `AtomicReference<EncodedFrame>` written by the OpenGPU pool, send it to viewers in range (OC's `sendToPlayersNearHost` range logic, `PacketBuilder.scala:72-100`), and run resource bookkeeping. **[est.]** 5–20 µs per display per tick + Netty write; 100 displays ≈ 1–2 ms of a 50 ms tick. Encode/deflate must never run here (5 ms for one 640×400 frame would be 10 % of the tick).

Rendering inside direct callbacks: direct callbacks run on `Machine.threadPool = ThreadPoolFactory.create("Computer", Settings.get.threads)` (`Machine.scala:1136`; installed `threads=4`, config line 295; threads are low priority, `ThreadPoolFactory.scala:16-24`) while holding the machine's monitor (`run()` is `Machine.this.synchronized`, `Machine.scala:981`). A 10 ms render inside a callback blocks 1 of 4 threads that *every* computer on the server shares; four 640×400 3D displays at 20 FPS = 0.8 thread-seconds/s = 20 % of the whole pool, and bursts delay unrelated computers' signal processing (the executor also waits `executionDelay=12 ms` between resumes). Save/load also waits on that monitor (`TextBuffer.save` pauses connected machines for exactly this reason, `common/component/TextBuffer.scala:473-488`).

Recommended policy: a separate OpenGPU pool (precedent: the Internet card's own pool, `InternetCard.scala:192`, `internet.threads=4`; `ThreadPoolFactory.createSafePool`, `ThreadPoolFactory.scala:50-54`), sized `max(1, cores/2)` and bounded. The direct callback only validates, copies the byte[] and enqueues a frame job, returning a frame id in ≤ 0.2 ms. Completion is signalled asynchronously with `machine.signal("gpu_frame", address, id)` — `Machine.signal` is thread-safe (`Machine.scala:335-345`) but returns `false` (drop) when the queue is full *or* whenever the machine is `Stopped`/`Stopping` (`Machine.scala:336-338`); `maxSignalQueueSize=256` is set explicitly in the installed config (line 268) and `Settings.scala:486` merely floors the value at 256, so the 1.12.64 default of 1024 only applies when the key is absent — this instance stays at 256 until the config is edited. Signal arguments pass through `convertArg` (`Machine.scala:317-333`), which accepts `Array[Byte]` but silently nulls unsupported types, which matters if readback results are ever delivered via signals. So coalesce to at most one pending frame signal per display and treat a `false` return as "display will resync on next present". Back-pressure: at most 1–2 frames in flight per display; `present` returns `nil,"busy"` otherwise, and repeated abuse is throttled with `context.pause()` as `bitblt` does. The Lua side must wait for a frame slot by *yielding* (`computer.pullSignal` / `os.sleep`), never by spinning: OC enforces `computer.timeout` (installed config line 302, `timeout=5` s) with a `debug.sethook` deadline check (`machine.lua:44-57,718`), so a frame-building or software-transform loop that blocks on "busy" without yielding crashes the machine with "too long without yielding" rather than merely stalling. Compute dispatches use the same pool with an instruction budget; readback is a non-blocking direct call that returns `nil,"pending"` until the job is done.

### 5. Resolution/tier proposal

OC's text tiers are 50×16 / 80×25 / 160×50 cells at 1/4/8-bit depth (`Settings.scala:525-526`), i.e. 2.5× and 4× steps, and VRAM is `w·h·vramSizes[tier]` = 1×/2×/3× on the GTNH pack and in the jar (`GraphicsCard.scala:74`; `vramSizes=[1, 2, 3]`, 10 F1-F2), 1×/2×/4× only under this instance's `vramSizes=[1,2,4]` override. OC's hex-font glyphs are 8×16 px (medium confidence: unifont-based `hexfont` renderer, config line 67), so a T3 screen is a 1280×800 raster — every proposed tier below is an integer fraction of it and keeps OC's 16:10 screen aspect.

| Tier | Resolution | Pixels | Depth | Raw frame | Typical 2D delta+deflate per viewer | Worst-case per frame (deflated) | FPS cap (server path) | Raster CPU/frame (2D / 3D) | Suggested VRAM cap |
|---|---|---|---|---|---|---|---|---|---|
| T1 | 160×100 | 16,000 | 8-bit palette (256 entries, programmable) | 16 KB | 0.3–0.5 KB → **5–10 KB/s** | 6–8 KB | 10 | <0.1 ms / 0.3–0.6 ms | 256 KB |
| T2 | 320×200 | 64,000 | 8-bit palette | 64 KB | 1 KB → **20 KB/s** | 25–40 KB | 20 (3D: 10) | 0.3 ms / 2–3 ms | 1 MB |
| T3 | 640×400 | 256,000 | RGB565 (client path may use 8888) | 512 KB | 4 KB → **80 KB/s** | 200–340 KB | 20 (3D server path: LAN-only or 10) | 1 ms / 8–10 ms | 4 MB |

Justification: the per-viewer sustained numbers for 2D match OC's own screen traffic class, and the worst-case T3 burst (≈ 300 KB) stays under 15 % of the FML payload cap; 3D on the server path is limited to T2/10 FPS (≈ 0.3–0.4 MB/s) or LAN, and otherwise routed through the client path. The FPS cap equal to the tick rate (20) is natural: budgets reset and OC flushes screen packets once per tick, and a `present` with `limit=2` yields tier-scaled call caps as computed in §2 (enforced by a one-tick stall per overrun, so the cap is soft and latency-shaped rather than a hard drop to 20/s). A per-viewer token bucket (16 KB/tick default) and adaptive frame skipping enforce the envelope regardless of content.

### 6. Verdict

Feasible, with the architecture constrained as follows.

Cheap: 2D API on the software path (sub-millisecond frames, tens of KB/s), handle-based resources, per-tick packet flushing (OC's `pendingCommands` pattern), tier/caps via existing OC mechanisms (`Callback.limit`, `consumeCallBudget`, `context.pause`), separate thread pool with signal-based completion, side-file persistence. Medium: the software 3D rasteriser (2–10 ms/frame; tiled multi-threading optional), the Lua-side encoding library and its LuaJIT-friendly variant, bandwidth governor. Hard: the shader language + compiler (one IR → JVM bytecode *and* GLSL 330, with budgets and a verifier), client GL renderer that survives Angelica's core-profile and SDL-GPU backends, and persistence/conformance testing across two renderers. Not feasible as specified: server-rendered full-motion 3D at 320×200+ over the internet for more than a couple of viewers.

M0 vertical slice (de-risks the top three uncertainties fastest):
1. **Batched call path** — a `present(bytes)` direct callback and a `readback()` on a dummy component; measure in Ocelot (OC-LuaJIT's harness already drives real OpenOS and has a sandbox speed meter) the Lua cost of encoding 1,000 triangles on Lua 5.3, 5.4 and OC-LuaJIT (JIT on/off), the per-call overhead (1 vs 1,000 calls), and the JNLua cost of a 100 KB argument. Success: ≤ 5 ms/frame on 5.3, ≤ 2.5 ms on LuaJIT, ≤ 50 µs marshalling. State the baseline VM of every ratio (the OC-LuaJIT in-machine tables use PUC 5.2).
2. **Streamed framebuffer in-game** — software-rendered 320×200 test pattern + moving sprite, dirty-tile delta + deflate on an OpenGPU pool thread, sent per tick, drawn as a textured quad by a TESR; run on Java 8/LWJGL2 and Java 21/lwjgl3ify with Angelica (`glProfile` AUTO and CORE, Iris shader pack on; the SDL-GPU renderer only on the lwjgl3ify leg, where it is opt-in via `-Dangelica.sdlgpu.enable=true` or the 2.2.29 video-settings selector — it cannot load on Java 8). Success: visible, no GL errors, ≤ 2 KB/frame for the UI pattern, ≤ 1 ms server-thread time per tick for 10 displays.
3. **Shader IR → bytecode** — a 200-line IR (float/int/vec arithmetic, texture fetch, loops with back-edge budget) compiled with ASM into an isolated class loader, executed as a 64k-element kernel and as a per-fragment shader in the rasteriser; same IR emitted as GLSL 330 and linked under Angelica. Success: ≤ 10 ns/element, budget abort works, identical output across JVMs, GLSL links under core profile.
Plus a persistence smoke test (save/load with a live framebuffer and an OC-LuaJIT machine holding handles).

## Design implications for OpenGPU

- One binary command/resource stream is the product; the software renderer and the client GL renderer are two consumers of it (Architecture C). Readback and compute are defined by the software path.
- Lua API: handles + strings only; `present(cmdbuf)` once per frame; resident meshes/textures/shaders; uniforms per frame; results via signals or non-blocking polls. Provide a Lua encoding library in 5.2-compatible, JIT-friendly style; never rely on `string.pack`.
- Threading: validate-and-enqueue in direct callbacks; render/encode on an OpenGPU pool; send from the pool thread through `NetworkManager.scheduleOutboundPacket` (13 §4; the FML channel's `send*` is server-thread-only; per-connection order is `execute()` order, so packets carry display/generation/frame ids and a `sendFromPool=false` switch restores tick-thread sending for diagnosis); frames in flight ≤ 2; coalesced completion signals.
- Caps are first-class config, tiered: resolution/depth, VRAM, command bytes, instruction budgets, FPS, per-viewer bandwidth, active displays.
- Client GL: core-profile-safe only, FBO + quad presentation, own GLSL generation, runtime fallback to the streamed framebuffer.
- Persistence: side files, resources + last frame; nothing large in NBT; nothing OpenGPU-specific in the Lua heap.
- Build: Java 8 bytecode, ASM from Forge, isolated loaders; CI matrix J8/LWJGL2 and J21/lwjgl3ify, Angelica on/off.
